# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Directory-scoped detail lives in nested CLAUDE.md files, loaded automatically when you're working in that subtree — this file stays high-level on purpose:
- `src/ziplex/extract/code/CLAUDE.md` — Tree-sitter code compression/extraction (`languages.py`/`parser.py`/`extractor.py`/`compressor.py`), one language per bullet (Python/Java/TypeScript/JavaScript/Lua/GDScript/Go/C++/Rust/C#/PHP/Ruby).
- `src/ziplex/extract/text/CLAUDE.md` — the non-Tree-sitter text compressors (json/yaml/markdown/txt).
- `src/ziplex/file/CLAUDE.md` — file collection, security scanning, and the dependency-graph API (`collector.py`/`scanner.py`/`selector.py`/`relationship.py`/`media.py`).
- `src/ziplex/gui/CLAUDE.md` — the local GUI: `gui_server.py` (Flask + pywebview), `pack_service.py` (the background job/review state machine), `watcher.py` (live filesystem watching for the staleness badge), and the frontend (`index.html`, the `js/` ES-module tree, `style.css`).

Packaging: this is a real installable package (`pyproject.toml`, src-layout — `src/ziplex/` is the actual `ziplex` package, not a flat script directory). Internal imports are package-relative (`from .file.collector import ...`, `from . import checkpoint as ckpt`); nothing under `src/ziplex/` imports a sibling module by bare name anymore. `pip install -e .` registers three console scripts: `ziplex` (the CLI), `ziplex-gui`, `ziplex-mcp`.

## What this is

Local project → `aif.json`: a token-reduced context format an AI reads instead of raw files. Pipeline: Tree-sitter compression/extraction → Gemini summarization → optional human correction. `aif.json` carries only summaries + relationships, never full per-file code — shape at the bottom of this file.

## Commands

Setup (Windows, matches the existing `venv/` in this repo):
```
venv\Scripts\activate
pip install -e .                 # editable install: reads pyproject.toml, registers the ziplex/ziplex-gui/ziplex-mcp console scripts
pip install -e ".[dev]"          # + pytest, for running the test suite
```
`pip install -r requirement.txt` (filename has no "s") still works as a lighter-weight alternative that skips packaging (dependencies only, no console scripts) — subcommands then run as `python src/cli.py ...` (see below) rather than `ziplex ...`.

Requires a `.env` with `GEMINI_API_KEY=...` (read via `python-dotenv` in `src/ziplex/llm.py`); optionally `GEMINI_MODEL=...` to override the default model (see the `llm.py` bullet below).

Run any subcommand from repo root (`ziplex ...` after `pip install -e .`; `python src/cli.py ...` works either way, editable-installed or not):
```
ziplex pack <project_path>                              # full pipeline, interactive file selection + correction
ziplex pack <project_path> --auto                       # skip interactive selection, include all safe files
ziplex pack <project_path> --auto-correct                # skip interactive correction, auto-accept LLM output
ziplex pack <project_path> --auto --auto-correct         # non-interactive*, for CI/scripted use
ziplex pack <project_path> --no-cache                   # force-resummarize every file, ignore any previous pack
ziplex pack <project_path> -o out.json                  # custom output path (also writes out.detail.json/out.cache.json)
ziplex pack <project_path> --include "src/**/*.py,*.md" --ignore "**/*.generated.*"  # one-off scope, on top of .ziplex.json
ziplex pack <project_path> --max-tokens 50000 --max-tokens-model GPT-4o  # CI guard: non-zero exit if the packed payload exceeds N tokens
ziplex pack <project_path> --auto --no-llm               # no GEMINI_API_KEY/network at all -- structural summaries only, rules/AI guide skipped
ziplex pack <project_path> --lang ko                     # packed CONTENT language (summaries/rules/AI guide) -- en (default/recommended) or ko

ziplex init <project_path>               # scaffold .ziplex.json (include/ignore patterns) -- see config.py
ziplex collect <project_path>            # just file collection + security scan
ziplex tokens <project_path>             # token count, before/after compression
ziplex tree <project_path>                # dependency tree only
ziplex search <project_path> <pattern> --context 2 --ignore-case  # regex search across safe files
ziplex detail <name>.detail.json <file-key> --start 10 --end 40   # partial read of one file's compressed body
ziplex freshness <project_path> <name>.cache.json                # hash-check aif.json against disk, no LLM calls
ziplex skill <name>.json                                          # export as a Claude Agent Skill (.claude/skills/<slug>/)
ziplex signatures|dependencies|api|compress|debug <single_file>
```
(`<project_path>` above is *any* target project being packed/inspected -- `--include "src/**/*.py"` is that target project's own `src/`, unrelated to Ziplex's own `src/ziplex/`.)

MCP server (exposes an already-packed project's `aif.json`/`detail.json`, read-only — see the `mcp_server.py` bullet below):
```
ziplex-mcp                                  # run directly, stdio transport
claude mcp add ziplex -- ziplex-mcp         # register with Claude Code
```

Local GUI (browse an already-packed project, or pack one interactively — see `src/ziplex/gui/CLAUDE.md`):
```
ziplex-gui                                            # native window (pywebview), landing page blank
ziplex-gui --aif out.json --project ./your-project    # prefill the landing page
ziplex-gui --no-window                                # plain browser tab instead of a pywebview window
```
*`--auto --auto-correct` makes `pack` fully non-interactive: `checkpoint.py`'s `handle_llm_failure()` and its `resume_checkpoint_choice()` prompt both take an `interactive` flag now (threaded from `--auto-correct`) and skip straight to their non-interactive default — checkpoint-and-exit, and always-resume, respectively — instead of calling `input()` against a closed stdin.

Tests (`tests/`, pytest via `pytest.ini` which puts `src/` on `pythonpath`, so `ziplex` is importable from source with no install required):
```
pip install -r requirement-dev.txt   # adds pytest on top of requirement.txt (or: pip install -e ".[dev]")
pytest
```
Covers the deterministic, non-LLM logic only — compressors, extractor, `file/collector.py`'s ignore/binary filtering (including `include`/`ignore` glob scoping), `config.py`'s `.ziplex.json` load/init, `file/relationship.py`'s graph ops, `edits.py`'s pure setters, `search.py`, `freshness.py`, `confidence.py`, `skill_export.py`'s pure generation, `text_references.py`, `tech_stack.py`'s manifest parsing, `cli.py`'s `_check_max_tokens()` and its `pack`/`analyze` subcommands' argument-level wiring (via `monkeypatch`-injected fakes, not real Gemini calls), `summarizer.py`'s batching/fallback logic, and `tokenizer.py`'s counting, plus `checkpoint.py`'s non-interactive failure handling (`handle_llm_failure`/`resume_checkpoint_choice` with `interactive=False`, monkeypatching `input` to assert it's never called). `tests/test_pack_integration.py` runs the *full* `pack()` pipeline end to end (checkpointing, parallel summaries, rules/prompt, token counting) against `llm.MockProvider` instead of Gemini — see the `llm.py` bullet below. `tests/test_mcp_server.py` checks the MCP-specific wiring (tool registration, docstring-as-description, `call_tool` dispatch) on top of that — see the `mcp_server.py` bullet below. `tests/test_pack_service.py` covers the GUI job-runner's state machine and concurrency guards (per-job locking, the `reviewing`→`finalizing` transition, cycle/cancel/error handling) against `llm.MockProvider`; `tests/test_gui_server.py` checks the Flask route layer on top of that (status codes, error-handler mapping, request→service wiring) — see `src/ziplex/gui/CLAUDE.md`. Nothing in the suite calls Gemini or needs `GEMINI_API_KEY`. `testfiles/` is separate — sample input for manual, ad-hoc CLI runs, not part of the test suite.

For a quick manual smoke test against a real project without waiting on Gemini: `LLM_PROVIDER=mock ziplex pack <project_path> --auto --auto-correct` runs the whole pipeline in well under a second, network-free.

## Architecture

`src/ziplex/cli.py` is a thin argparse dispatcher; all real logic lives in the modules it calls. The `analyze` subcommand (a lighter-weight preview: per-file summaries + rules + an AI guide, with no compression/relationships/tokens/saving/checkpointing) used to be the one exception -- its own bespoke per-file summarization loop called `llm.analyze_file_summary()` directly, one file at a time, with its own separate failure string (`"분석 실패"`) instead of `summarizer.py`'s `SUMMARY_FAILED_PLACEHOLDER`. Flagged by a full-codebase review (2026-08-24) as a real risk, not just a style nit: any future fix to the shared summarization pipeline (batching, retry, placeholder handling) would silently miss this code path. Fixed by delegating to `summarizer.generate_summaries()` -- the exact function `pack()` itself calls for this step -- restoring the thin-dispatcher rule for good. Its per-file loop got a second, related fix (2026-08-26): a media asset (`file/media.py`) used to fall through `extract_signatures`/`extract_dependencies` (both `[]` for it) straight into the "no signatures, no dependencies, skip" branch, silently vanishing from `analyze`'s own summary output despite being counted in its printed file total -- `classify_media_file()` now short-circuits it into the same free metadata summary `pack()` gives one, mirroring that fix exactly (see `packager.py`'s own bullet below). The `pack` command runs the full pipeline end to end:

1. **`file/collector.py`** → **`file/scanner.py`** → **`file/selector.py`** — collect, security-scan, and (unless `--auto`) interactively select files. `collect_files()` takes optional `include`/`ignore` glob-pattern params (see `config.py` below) to scope collection before security scanning or selection ever run. A recognized media asset (image/video/audio/font -- `file/media.py`) survives collection too despite being binary, always scans as safe, and gets its `summary` filled in with a free metadata-only description in `pack()`'s per-file loop rather than ever reaching Tree-sitter extraction or an LLM (let alone vision-model) call. Detail: `src/ziplex/file/CLAUDE.md`.
2. **`extract/code/*`** + **`extract/text/*`** — Tree-sitter signature/dependency/API extraction and body-stripping compression for code; structure-preserving compression for JSON/YAML/Markdown/plain text (YAML via `ruamel.yaml`'s round-trip mode, not a naive parse-and-redump — see that module's own bullet for why). Detail: `src/ziplex/extract/code/CLAUDE.md` / `src/ziplex/extract/text/CLAUDE.md`.
3. **`tokenizer.py`** — counts tokens per model (`tiktoken`). `analyze_tokens_with_compression` (the standalone `tokens` command) measures original vs. compressed body only; `analyze_tokens_with_payload` (used by `pack`) measures original vs. just the per-file `summary` — the only per-file field that actually ships in the saved `aif.json`. A media asset (`file/media.py`) has no readable "original" text -- correctly 0 on that side -- but its real `summary` still ships in `aif.json` exactly like any other file's, so `analyze_tokens_with_payload` counts it on the payload side unconditionally; a 2026-08-26 review caught it being skipped entirely (same `read_text()`-is-`None` branch guarding the original side), silently undercounting the real packed payload `pack --max-tokens`'s CI guard checks against.
4. **`llm.py`** — three real providers today (`GeminiProvider` default, `OpenAIProvider`, `ClaudeProvider`), plus `MockProvider` for tests, all behind `PROVIDERS`/`_active_provider()` (below). `GeminiProvider` calls Gemini's REST API directly (`gemini-flash-latest` by default, via `requests`, not the SDK) for per-file summaries, coding-rule inference, and the project-level AI guide. Model resolution -- **also** re-resolved fresh on every access, not just the key (2026-08-24 fix, see below for why) -- is a `url` `@property`, not a plain attribute baked in at `__init__`: an explicit `GeminiProvider(model=...)` constructor arg, then `settings.py`'s `resolve_gemini_model()` (the GUI's Options page), then a `GEMINI_MODEL` env var, then `GeminiProvider.DEFAULT_MODEL`. API key resolution follows the same shape via `_resolve_api_key()`: an explicit `GeminiProvider(api_key=...)` constructor arg, then `settings.py`'s `resolve_gemini_api_key()` (the GUI's Options page, GET/POST `/api/settings`), then the `GEMINI_API_KEY` env var / `.env` (unchanged from before this setting existed). Per-call resolution specifically because `_provider` (below) is a module-level singleton built once at import and stays alive for the whole process -- a key or model entered later via the Options page has to take effect on the very next pack, not only after a restart the way an env var change would need anyway. The model *used* to be treated as "nobody expects to change it mid-session" and resolved once at construction -- flagged as a real bug (2026-08-24) by a live external-tester report: someone who only entered an API key via a fresh GUI install had no way to move off `DEFAULT_MODEL` (a floating `-latest` alias with the documented 503-overload history below) short of an env var on their own machine, which a GUI-only user has no reason to know exists. Added after a real 503-frequency investigation traced it to `gemini-flash-latest` itself (a floating alias, not a pinned release) sitting on overloaded capacity at that moment — confirmed independently by the same model showing 503s in Google AI Studio directly, and by a pinned release (`gemini-3.5-flash`) returning clean 200s back-to-back at the same time `-latest` didn't. `DEFAULT_MODEL` stays `gemini-flash-latest` regardless (a snapshot of "what's overloaded right now" isn't a permanent verdict, and it's what most existing users already have working) — `GEMINI_MODEL`/`resolve_gemini_model()` are the escape hatches for a user who wants to pin something else without a code change, the GUI one now being the one that actually reaches a GUI-only user.

`GeminiProvider.generate()`'s request body always carries `generationConfig: {thinkingConfig: {thinkingBudget: 0}}` (2026-08-26, a real cost bug reported directly): Gemini's extended "thinking" mode is on by default for the 2.5+/3.x Flash generation `DEFAULT_MODEL`/`GEMINI_MODEL` point at, and none of `llm.py`'s prompts (short, single-shot, "JSON only" extraction tasks) benefit from it -- confirmed directly against the real API: a trivial one-word request billed `usageMetadata.thoughtsTokenCount = 142` (of a 150-token total) with no `thinkingConfig` set, and `0` (field absent, `totalTokenCount = 8`) with `thinkingBudget: 0` set, an ~18x difference on that one call. Traced from a user whose AI Studio billing jumped roughly 10x with no code or usage-pattern change on their end -- exactly the signature of `-latest` (a floating alias) starting to resolve to a thinking-enabled model version with zero code change anywhere. Sent unconditionally on every request regardless of which model `GEMINI_MODEL`/the GUI's model field actually names: every model reachable through the API at the time of this fix is from a thinking-capable generation (both older, non-thinking Flash releases tried during the investigation came back 404, already sunset), so there's no live model left to confirm the field is harmlessly ignored elsewhere rather than rejected outright -- worth revisiting if a future model ever errors on it. `OpenAIProvider`/`ClaudeProvider` are untouched -- neither has an equivalent "thinking" concept in this shape (Claude's own extended-thinking flag is a different API shape entirely, and wasn't implicated in the reported cost spike).

   `OpenAIProvider` and `ClaudeProvider` (2026-08-24) are the multi-provider expansion `LLMProvider`'s docstring always anticipated. `OpenAIProvider` speaks the Chat Completions request/response shape (`{"choices": [{"message": {"content": ...}}]}`) that's become the de facto standard almost every other provider also implements -- real OpenAI, Ollama, LM Studio, vLLM, llama.cpp's own server, OpenRouter, Groq -- so one class with a configurable `base_url` (`resolve_openai_base_url()`/`OPENAI_BASE_URL`, default `api.openai.com/v1`) plus `model` covers all of them, including a local Gemma/Llama/Mistral served through any of those: point `base_url` at wherever it's listening and set `model` to whatever name that server expects, no code change. `ClaudeProvider` is Anthropic's own Messages API (`x-api-key` header, required `max_tokens`, response text at `content[0].text`) -- different enough in shape from both Gemini and the OpenAI family that it isn't just another `OpenAIProvider` `base_url`. Both retry the same 429/5xx set `GeminiProvider` does (`ClaudeProvider` also retries Anthropic's own `529` overloaded status), checked on the HTTP status code rather than a response-body field for the OpenAI family specifically, since an OpenAI-compatible error body's `error.type` is commonly a string ("rate_limit_exceeded"), not Gemini's numeric `error.code`.

   `LLMProvider` (a `typing.Protocol`) is the seam for adding another model — implement `generate(prompt, retry) -> str` and register it in `PROVIDERS`. Retries on HTTP 429/503 with backoff, and (since a 2026-08-24 code-review finding) on a transport-level failure the same way -- a `requests.post()`/`response.json()` call wrapped in `try/except (requests.exceptions.RequestException, json.JSONDecodeError)`, since a network blip (DNS failure, connection reset, read timeout) or a non-JSON response body (a proxy's HTML error page) is exactly as transient as an explicit 503/429 and needs the same retry-with-backoff treatment; left uncaught, it used to propagate straight past every caller's checkpoint-on-failure path (`summarizer.py`'s thread pool, `packager.py`'s rules/prompt calls, `checkpoint.handle_llm_failure()`) and crash the whole `pack()` run instead of saving a resumable checkpoint first. Every provider's `requests.post()` call also carries an explicit `timeout=REQUEST_TIMEOUT` (60s, 2026-08-25) -- `requests` has no default timeout on its own, so a network path that's blocked or filtered (a firewall/proxy silently dropping the connection rather than refusing it) used to leave the call hanging on the socket read forever, with no exception ever raised to hit the retry logic above: a real external-user report of a GUI pack that printed `🤖 LLM 분석 중...` and then never produced another log line, not even a retry warning, traced to exactly this -- indistinguishable from the process having frozen. `requests.exceptions.Timeout` is already a `RequestException` subclass, so this needed no new except clause, just the timeout kwarg on each of the three providers' calls. `analyze_batch_summaries(items)` — what `summarizer.py` calls for per-file summaries (step 5) — bundles several files' signatures/dependencies (or truncated content, for text-only files) into one prompt, one `{"summaries": {name: "..."}}` response, cutting request *count* by roughly `summarizer.BATCH_SIZE` (what drives 429/503 retries, not total token volume). `analyze_file_summary`/`analyze_text_summary` (single-file) still exist as the batch's per-file fallback. `PROVIDERS["mock"]` (`MockProvider`) implements that seam network-free: pattern-matches the JSON field name in a prompt's trailing example (including `"summaries"`, regexing out each batch prompt's `File: <name>` lines) and returns a fixed, valid response. Select the process-lifetime default via `LLM_PROVIDER=mock`/`openai`/`claude` (read once at import into module-level `_provider`) — tests instead `monkeypatch.setattr(llm, "_provider", llm.MockProvider())`, which works regardless of import order since `generate()` looks it up fresh on every call. **Which provider actually handles a given call** is `_active_provider()`'s job, not `_provider` directly: `settings.py`'s `resolve_llm_provider_name()` (the GUI Options page's provider selector, `""` meaning "no override") wins over `_provider` when it names a real `PROVIDERS` key, constructing a fresh instance every call (cheap -- each provider's own `__init__` just resolves config strings, no network) so a provider switched in the GUI takes effect on the very next pack, same reasoning as the key/model resolution above. Every environment except a real GUI session that used the selector has `resolve_llm_provider_name()` returning `""`, so `LLM_PROVIDER`/`_provider`-based selection (every test, every CLI invocation) is unaffected.
5. **`checkpoint.py`** — `pack()`'s checkpoint/resume system, split out of `packager.py` to keep that module focused on the pipeline itself: `handle_llm_failure()` lets a failing LLM call be retried, answered manually, or checkpointed to `checkpoint/<project_name>-<hash>.json` for the next `pack` run on the same path to auto-detect and resume; `resume_checkpoint_choice()` is the matching question for a checkpoint found at the *start* of a run (resume it, or discard and start over). The `<hash>` suffix (`_checkpoint_path()`, first 8 hex chars of the resolved absolute path's sha256) is load-bearing, not cosmetic -- a bare `<project_name>.json` (pre-2026-08-24) let two different projects sharing a folder basename (`C:\clients\acme\backend` vs `C:\clients\other\backend`) silently load or overwrite each other's checkpoint, since non-interactive callers (the GUI, always) never got a resume-vs-discard prompt to catch the mismatch. Safe to key on the raw absolute path specifically because this file is purely local, ephemeral tool bookkeeping -- deleted on success, never committed the way `aif.json`/`detail.json`/`cache.json` are (see README's Team use section) -- unlike `freshness.py`'s own version of the same collision class below, which can't use a path fingerprint for exactly that reason. `pack(..., interactive=False)` (what `--auto-correct` sets) skips every prompt either function could otherwise raise — both default to their safe non-interactive behavior (checkpoint-and-exit; always-resume) instead of calling `input()`. `build_snapshot()` builds the `{project, rules, files_data}` dict `handle_llm_failure()` checkpoints, keyed by relative name to match what `load_checkpoint()`'s caller restores from. `pack()`'s `check_cancelled` param (see the `packager.py` bullet below) reuses this exact same `build_snapshot()`/`save_checkpoint()` pair for a *user*-requested "save and stop" -- a checkpoint from a repeated LLM failure and one from a human clicking "저장 후 취소" mid-run in the GUI are indistinguishable on disk, so the same auto-resume-on-next-`pack` behavior covers both for free. `build_snapshot(..., lang="en")`/`unpack_snapshot()` (2026-08-26) also carry `project.language` -- a real gap caught by code review: a checkpoint's restored `rules`/`prompt` used to be reused verbatim on resume regardless of what `lang` the *checkpoint itself* was saved under, so resuming under a different `--lang` than the interrupted run used could ship mixed-language content under one `project.language` value. `packager.pack()` now compares `unpack_snapshot()`'s returned `lang` against its own `lang` param (`lang_matches`) before trusting any restored `rules`/`prompt`/per-file `summary` -- see that bullet below for the full gating. `unpack_snapshot(None)` and a checkpoint predating this field both default to `"en"`, same convention `project.language`'s own missing-field default uses.
6. **`summarizer.py`** — per-file summary generation, split out of `packager.py` for the same reason: `generate_summaries(pending, root)` is `pack()`'s single entry point for step 5 when an LLM is available, batching `pending` into `BATCH_SIZE`-sized chunks (`chunked()`, by relative name) and submitting one future per chunk to a `MAX_WORKERS` thread pool (see `llm.py` above) — `request_batch_summaries()` falls back to `request_summary()` per-name for anything a batch response didn't cover, so a garbled response only costs what it actually failed on. `generate_structural_summaries(pending, root)` is the `pack(..., use_llm=False)` counterpart -- same signature and return shape, but no network call at all: each file's summary is a deterministic one-liner built purely from its own already-extracted `signatures`/`dependencies` (`_structural_summary()`), synchronous since there's no request latency to hide behind a thread pool. Both take a `lang: str = "en"` param (2026-08-26, threaded from `pack()`'s own `lang` -- see `packager.py`'s bullet above), passed to `llm.py`'s `analyze_*()` calls on the LLM path, and to `_structural_summary()`'s per-language `_STRUCTURAL_LABELS` dict on the structural-only path -- Ziplex's own fixed labels ("Defines"/"References"/the no-signatures note) follow the chosen language too, not just LLM-written text. `SUMMARY_FAILED_PLACEHOLDER` is now `SUMMARY_FAILED_PLACEHOLDERS: dict[str, str]` (one entry per supported language) plus `is_summary_failed_placeholder(summary)`, which every caller (`confidence.py`, `packager.py`'s cached-failure check) now calls instead of an equality check against a single constant -- it recognizes the placeholder in *any* supported language, not just the current run's own `lang`, since a cached previous-pack summary (`freshness.load_previous_summaries()`) may have been written under a different language selection than the run checking it now.
7. **`packager.py`** (`pack()`) — orchestrates 1–6, plus `text_references.py` for non-code files (see below): the pipeline stitcher itself, not owner of checkpointing or summary generation anymore. `pack(..., use_cache=True)` (the default; `--no-cache` turns it off) auto-detects a previous successful pack at the conventional `RESULT_DIR` path and reuses that file's `summary` for any file whose content hash still matches (via `freshness.load_previous_summaries()`, itself built on `freshness.check_freshness()`) instead of spending another LLM call on it — only `summary` is reused, `signatures`/`dependencies`/`api`/`compressed` are always freshly extracted so a human's prior manual reparenting (`corrector.py`'s `move_file()`) never silently rides along with a skipped file's stale dependency data; `relationships` is always rebuilt from scratch regardless. `use_cache=False` also discards a leftover checkpoint from an interrupted previous run before it's ever unpacked, short-circuiting past `resume_checkpoint_choice()` entirely (no interactive prompt either, even with `interactive=True`) — checkpoint auto-resume used to be a completely separate mechanism `use_cache` had no say over at all, so a non-interactive caller (the GUI, always) auto-resumed a leftover checkpoint regardless of this flag, which read as a bug from the outside (a "완전히 재패킹" checkbox not actually starting fresh) even though each half worked as designed in isolation. One exception to silent reuse: if any reused summary matches `summarizer.is_summary_failed_placeholder()` (true for `SUMMARY_FAILED_PLACEHOLDERS`'s entry in *any* supported language, not just the current run's own `lang` -- a previous pack's LLM call for that file failed and never got a real answer), `pack(..., interactive=True)` asks once whether to regenerate those specific files instead of quietly re-caching a miss forever (`_confirm_regenerate_failed_summaries()`, same numbered-menu shape as `checkpoint.resume_checkpoint_choice()`); non-interactive callers (`--auto-correct`, the GUI) keep the old behavior (leave it cached) with no prompt, since `confidence.py`'s 0.0 for that exact placeholder already guarantees a human reviewing the pack sees it flagged either way. `pack(..., use_llm=False)` (CLI: `pack --no-llm`) is the "structural-only" mode floated as a mitigation for the API-key onboarding barrier (see the `ziplex-roadmap` memory): skips every LLM call (summaries fall back to `summarizer.generate_structural_summaries()`, `rules` stays `[]`, `prompt` becomes the fixed `STRUCTURAL_ONLY_NOTE`) while every Tree-sitter/regex-based step runs exactly as normal — no `GEMINI_API_KEY`, no network, no rate limits. `use_cache` still applies independently under `use_llm=False`: a file whose previous *real* summary is still fresh gets that reused rather than downgraded to a structural placeholder. That `rules=[]`/`prompt=STRUCTURAL_ONLY_NOTE` contract used to only hold when there was no leftover checkpoint: `rules = restored_rules`/`prompt = restored_prompt` read a checkpoint's contents *before* either the `use_llm` check, so retrying with `--no-llm` a project whose earlier `use_llm=True` run got as far as inferring real rules before failing at the prompt step (`use_cache=True`, the default, auto-resumes it) shipped an `aif.json` with real coding rules sitting alongside a prompt asserting no LLM inference ever happened -- a direct self-contradiction in the same document. Fixed (2026-08-24) by gating both restores on `use_llm` itself (`rules = restored_rules if use_llm else []`, same for `prompt`), so `--no-llm` ignores a checkpoint's rules/prompt outright regardless of what an earlier LLM-enabled run left behind. Two more checkpoint-adjacent fixes from the same 2026-08-24 pass: the per-file loop's checkpoint-restore branch used to only check a restored file's `signatures` (not `dependencies`) before including it in `signatures_map` (`analyze_rules()`'s input) -- diverging from the fresh-extraction branch just below it, which checks `sigs or deps` -- so a file with real dependencies but no functions (a thin `index.ts` that's just top-level imports) was silently excluded from rules inference only when restored from a checkpoint, making the inferred rules depend on whether a run happened to get interrupted and resumed; both branches now use the same condition. Separately, the interactive rules-failure prompt's "직접 입력" (manual entry) turned an empty Enter-with-nothing-typed answer into `['']` (a one-element list holding an empty string -- `"".split(",")` is `['']`, not `[]`) instead of re-prompting, since `while not rules:` only re-loops on a genuinely empty list; the split now filters blank entries first. `pack(..., check_cancelled=...)` is `pack()`'s only way to be told to stop from *outside* its own thread -- polled at three checkpoints (once per file during extraction, once before the LLM summary step, once right after it -- the last one specifically so a stop requested *during* that typically-longest step still takes effect the moment it finishes, not never) via `_maybe_stop()`, which checkpoints (`ckpt.build_snapshot()`/`save_checkpoint()`, the exact same shape `handle_llm_failure()` uses) before returning `{}` unless told to discard instead. Only meaningful for a caller running `pack()` on a background thread with no other way to interrupt it -- see `gui/pack_service.py`'s `request_cancel()`/`src/ziplex/gui/CLAUDE.md`; a synchronous CLI run just leaves this unset. `pack(..., result_dir=...)` overrides `RESULT_DIR` as where the `use_cache` lookup above looks -- not where *this* run's own `aif.json` is saved (`save_aif()`'s own `output_path` handles that, unchanged and separate); `None` (the CLI's only call shape) keeps today's behavior exactly. Only meaningful together with a caller that also saves somewhere other than `RESULT_DIR`: `gui/pack_service.py`'s `start_pack_job()` resolves a project's effective output folder via `settings.py` once, up front, and passes that same folder both here and to `save_aif()` later, so a project with a configured output folder (see `settings.py`, above) gets correct cache reuse instead of silently missing it every single pack. `pack(..., lang="en")` (CLI: `pack --lang {en,ko}`, GUI: the pack form's language dropdown, 2026-08-26) picks which language every LLM-written value -- each file's `summary`, `rules`, `prompt` -- is actually written in, via a one-line instruction appended to each `llm.py` prompt (`llm.LANGUAGE_NAMES`, `_lang_name()`); "en" is both the default and the recommended choice, matching what every prompt/doc in this codebase is already written in. Deliberately distinct from the GUI's own display-language switcher (`js/i18n.js`, translates only the GUI's own chrome, never anything an LLM writes) -- this resolves the roadmap's long-deferred "translate a packed project's own content" question not by adding a second translation pass or a second API key, but by having the summarization LLM write in the target language from the start. Silently normalized to `"en"` for an unrecognized value rather than raising (CLI/GUI both already restrict input to `LANGUAGE_NAMES`'s keys, so this is a defensive fallback only). Also picks the language of Ziplex's own fixed strings that ship alongside LLM-written ones for consistency -- `STRUCTURAL_ONLY_NOTE`/`FORMAT_NOTES` (now per-language dicts, not bare strings) and `summarizer.SUMMARY_FAILED_PLACEHOLDERS` -- so a Korean-language pack doesn't ship English legend text next to Korean summaries. Recorded verbatim as `project.language` in the assembled aif, unconditionally attached the same way `tech_stack`/`security_scan`/`format_notes` already are, so a reader with no other context can tell what language a pack's own content is in.

A same-day code review caught two real cross-run inconsistencies the initial `lang` implementation missed, both the same self-contradiction class already fixed once for `rules`/`prompt` vs. `use_llm` (above), now reappearing for `lang`: (1) `load_previous_summaries()`'s incremental cache reuse had no notion of language at all, so re-packing an unchanged project under a *different* `--lang` kept the previous language's summaries verbatim while still stamping the new `project.language` onto them -- fixed by having `load_previous_summaries(..., lang=lang)` (`freshness.py`) compare the previous aif's own `project.language` against the requested one and return `{}` (a full cache miss, not a partial one) on any mismatch, defaulting a missing `language` field to `"en"` for an aif packed before this feature existed. (2) A checkpoint's restored `rules`/`prompt`/per-file `summary` were reused verbatim regardless of what `lang` *that checkpoint* was saved under -- fixed by threading `lang` into `checkpoint.build_snapshot()`'s `project.language` field too, and gating every restore point (`rules = restored_rules if (use_llm and lang_matches) else []`, same for `prompt`; a restored file's `summary` is discarded, not the rest of its data, on a mismatch) on `lang_matches = restored_lang == lang` -- computed once, right after `unpack_snapshot()`, alongside the existing `use_llm` gate. A third, lower-severity finding from the same review (the "supported languages" set duplicated across five independent dicts across `llm.py`/`packager.py`/`summarizer.py`, each with its own silent English fallback) wasn't consolidated into one registry -- judged a larger refactor than the bug's actual severity warranted -- but got a cheap mitigation instead: `tests/test_language_support.py` asserts every one of those dicts has exactly `llm.LANGUAGE_NAMES`'s key set, so adding a language to one without the others now fails a test immediately instead of silently degrading to English for whatever wasn't updated.
8. **`edits.py`** + **`file/relationship.py`** — the pure, I/O-free editing API (no `input()`/`print()`): field setters, `finalize_aif()` (builds `relationships`, prunes now-redundant `signatures`/`dependencies`/`api`), and the dependency-graph operations (`build_tree`/`move_file`/`has_cycle`). This is the seam `pack_service.py`'s GUI review flow calls directly with structured input instead of parsed terminal strings (`corrector.py` is the terminal equivalent, built on the same setters). Detail (especially `has_cycle`'s traversal direction — easy to get backwards): `src/ziplex/file/CLAUDE.md`.
9. **`corrector.py`** — the thin interactive CLI wrapper around 8: walks the user through project name/guide/rules/summaries/reparenting, calling the matching pure function for each accepted change. `--auto-correct` skips this module entirely and calls `edits.finalize_aif()` directly. The per-file summary step is triaged by `confidence.triage()` (see below) -- only files below `REVIEW_THRESHOLD` get prompted; the rest are auto-kept and just listed, since reviewing every single file doesn't scale past a handful of them. Each flagged file's prompt also prints its real extracted `signatures` (capped at 10, "+N more" past that) alongside the summary, so a human can see *why* it scored low without opening the file themselves -- always non-empty for a flagged file, since one with no signatures always scores 1.0 (see `confidence.py`).
10. **`packager.py`** (`save_aif()`) — splits two things out of `aif` into sibling files: `compressed` per file → `<name>.detail.json`, so the saved `aif.json` only ever carries `summary` per file (files with little to strip, like README/config/lang files, would otherwise cost more tokens shipped than they save); and the flat `_manifest` (a `{file: content hash}` map `pack()` attaches, see `freshness.py` below) → `<name>.cache.json`, packaging-internal bookkeeping that never appears in `aif.json` itself.

**`text_references.py`** extends `relationships` past code files, for free (no LLM call, unlike Tier 3's still-open "cross-type relationship analysis" roadmap item, which this is a narrower, cheaper first slice of -- see the `ziplex-roadmap` memory). A file with no Tree-sitter grammar always got `dependencies=[]` from `extract_dependencies()`, so it only ever showed up as a leaf in `relationships` even when it obviously referenced other project files -- a Godot scene's `[ext_resource path="res://player.gd"]`, a Markdown doc mentioning `player.gd`, a README documenting a project's own layout by filename. `find_text_references_for_file(file_path, name, all_names)` (the file-level entry point; `find_text_references(content, self_name, other_names)` underneath is the pure, already-loaded-content version, used directly by tests) matches against the *actual* collected-file list (the full relative path, or just the filename+extension, both word-boundary anchored so "player.gd" doesn't match inside "multiplayer.gd") rather than a generic "looks like a path" regex -- a bare stem like "player" is deliberately never matched, since common words/stems would produce far more noise than signal, and a file with a Tree-sitter grammar is skipped entirely (its own `dependency_handler` already covers it). Because a match is already a real collected file, it needs no separate resolve step the way `extract_dependencies()`'s raw import strings do; it ends up in that file's `dependencies` list, same as a resolved import would -- **but not immediately**: `pack()` keeps text-reference matches in a side dict (`text_refs_by_path`) through the whole per-file loop and the LLM summary step, only merging them into `files_data[fp]["dependencies"]` afterward. `summarizer.request_summary()`/`analyze_batch_summaries()` both switch a file's summary prompt from content-based to signature/dependency-based the moment `dependencies` is non-empty -- merging immediately used to silently swap a text file's content-based prompt for a signatures-empty/dependencies-only one the instant it picked up any reference, so Gemini summarized it having never seen its actual text (caught by review, fixed same session; `tests/test_pack_integration.py`'s prompt-capturing regression test guards this specifically, since `llm.MockProvider` ignores prompt content and wouldn't have caught it). Wired into `pack()`'s per-file loop and, separately, into the standalone `tree` CLI subcommand -- `tree` has its own (not `pack()`-shared) collection logic, which switched from raw `collect_files()` paths to `relative_key()`-normalized keys in the process, since `resolve_dependency()`'s exact-key-match branch requires that to resolve these correctly. Known limitation, not yet addressed: a prose mention (a README) and a structural reference (a Godot scene) land in the same `dependencies` list with no way to tell them apart in `relationships`/`get_blast_radius`/`get_dependents` -- see the module's own docstring for why that's deferred rather than fixed here.

**`tech_stack.py`** — free (no LLM call), manifest-file-based fact block: `detect_tech_stack(root_path)` scans the project root's top level (not recursive) for known package-manager manifests (`package.json`/`requirements.txt`/`pyproject.toml`/`Cargo.toml`/`go.mod`/`Gemfile`/`composer.json`/`pom.xml`) and reads out each one's declared top-level dependency names (version specifiers stripped, capped at `MAX_DEPENDENCIES`, deduped). Complements `rules` rather than replacing it — `rules` is an LLM *guess* at conventions from Tree-sitter signature shape; this is a direct, deterministic read of what a manifest actually declares. `pack()` attaches its result unconditionally (`[]` if no manifest found) as `aif["project"]["tech_stack"]`, which `finalize_aif()` never touches (it only prunes per-file fields) and `skill_export.py`'s `references/overview.md` renders as an extra section when present (older `aif.json` files packed before this field existed just skip the section). Deliberately shallow: no lockfile resolution, no transitive walking — "what does this project say it depends on," not a full dependency graph. `_read_text()` (2026-08-24) delegates to `file/textutil.py`'s shared `read_text()` rather than its own `path.read_text(encoding="utf-8")` catching only `OSError` -- a non-UTF-8 manifest (a real case for a legacy Windows-authored file) raised `UnicodeDecodeError` uncaught, breaking this module's own "never raises, by contract" guarantee; `file/textutil.py`'s version already catches both.

`cli.py`'s `pack --max-tokens N [--max-tokens-model MODEL]` is a CI-guard flag, not a pipeline module: after a normal pack completes and `aif["tokens"]` is populated, `_check_max_tokens()` (pure, testable without argparse) compares the chosen model's actual packed-payload token count (the same `tokens[model]["compressed"]` figure the human-readable token summary already prints) against `N` and `main()` turns a failing/unknown-model result into a non-zero exit — for a build pipeline that wants to fail loudly if a project's context budget creeps past what a target model can hold, rather than silently shipping an oversized `aif.json`. That check only ever ran inside `if aif:` -- `pack()` returning `{}` (a checkpoint-and-exit on a repeated LLM failure, or a cancelled/empty run) skipped the whole block and let `main()` exit 0 by default, exactly the scenario this flag exists to catch (a CI pipeline silently passing despite `pack()` never actually completing). Fixed (2026-08-24) with an `elif args.max_tokens is not None:` sibling that exits 1 when `--max-tokens` was requested but there's no `aif` to check at all; behavior is unchanged when the flag isn't passed.

**`freshness.py`** sits outside the `pack` sequence like `search.py` below, but is also called *by* it (see step 5): `check_freshness(file_paths, root, manifest)` re-hashes a project's current files and diffs them against a loaded manifest into a `FreshnessReport` (`changed`/`added`/`removed`/`unchanged`, plus an `is_stale` property), with no Tree-sitter parsing and no LLM calls. `hash_file()` hashes a recognized media asset's raw bytes (`file/media.py`'s `is_media_file()`) instead of decoded text -- the one exception to "no text, no hash," matching `collect_files()`'s own media exception, so incremental cache reuse and staleness checks both still work on a project's images/video/audio/fonts. Two consumers: `pack()` uses `.unchanged` to decide which files' summaries are safe to reuse (see step 5); the `freshness` CLI subcommand and the MCP server's `check_freshness` tool use the full report as a read-only "is this pack still trustworthy" check, without triggering a re-pack themselves.

`freshness_candidate_files(scan_result, root, manifest)` (2026-08-26) is what every one of `check_freshness()`'s three real callers (the `freshness` CLI subcommand, `query_service.check_freshness()` for the GUI/MCP, `gui/watcher.py`'s live recompute) actually passes as `file_paths` now, instead of `collect_and_scan()`'s bare `["safe"]` list each used to pass directly -- a real bug reported directly: a file `scan_files()` flags as sensitive can still have been included in the pack for real (a human opted back in via `selector.py`'s `review_dangerous_files()`, the GUI's per-file "include anyway" checkbox, or a `preselected` caller naming it directly), in which case it has a genuine entry in that pack's manifest. Re-scanning always re-flags that same file as dangerous regardless of the earlier decision, though, dropping it from `collect_and_scan()`'s own `"safe"` list every single time -- so `check_freshness()`, which only ever sees what it's handed, reported it as permanently `removed` forever after, even though it's unchanged and still on disk. The fix unions `scan_result["safe"]` with any `scan_result["dangerous"]` entry whose relative key is already present in `manifest` -- checked against the manifest specifically, not unioned in unconditionally, so a dangerous file that's *never* been packed (correctly, deliberately excluded every time, a real `.env` with live secrets) doesn't flip to spurious `"added"` noise just because it exists on disk. Also owns `load_previous_summaries(root_path, selected, result_dir, lang="en")`, the actual staleness-stage-2 cache-reuse lookup `pack()` calls before deciding what's `pending` for summarization -- lives here rather than in `summarizer.py` since "what still counts as fresh" is this module's own subject, not a concern of how a summary (LLM or structural) actually gets produced once something's decided to need one. `lang` (2026-08-26) rejects the entire previous manifest (returns `{}`, not a partial result) when the previous pack's own `project.language` doesn't match the requested one -- a real gap caught by code review: without this, re-packing an unchanged project under a different `--lang` reused the previous language's summaries verbatim while still stamping the *new* `project.language` onto the result, the same self-contradictory-aif.json class `checkpoint.py`'s own `lang` handling (above) fixes for a resumed run. A previous aif with no `language` field at all (packed before this feature existed) defaults to `"en"`, same convention `checkpoint.unpack_snapshot()` uses. Guards against the same cross-project collision class `checkpoint.py`'s `_checkpoint_path()` fixes with a path hash, but can't use that fix here: two projects sharing a result-directory basename (both named "backend", both packed to the same `result/` or GUI-configured output folder) could otherwise have one's cached summary applied to the other for any file whose content hash coincidentally matches (a boilerplate `.gitignore`, an empty `__init__.py`) -- and unlike `checkpoint.json`, `aif.json`/`cache.json` are meant to be committed and shared across machines (README's Team use section), so a teammate re-packing the *same* project from a different absolute path must still get cache hits; a path fingerprint would break that. Instead (2026-08-24), `load_previous_summaries()` requires at least `_MIN_OVERLAP_RATIO` (0.5) of the *current* file set to already appear in the previous manifest at all (hash match or not) before trusting any of it -- a low overlap is the signal that the previous manifest probably belongs to an unrelated project, not that this one just changed a lot.

The `freshness` CLI subcommand (2026-08-24) exits 1 when `report.is_stale`, not just 0 always -- same "fail loudly for CI" shape as `pack --max-tokens`'s `_check_max_tokens()`, added specifically so `ziplex freshness <project> <name>.cache.json` can double as a free PR/CI gate (no LLM calls, no `GEMINI_API_KEY`) on a project that commits its Ziplex output (README's Team use section): fail the check when the committed `aif.json` has drifted from disk, forcing a human to `pack`+review before merging, rather than auto-`pack`ing in CI itself -- deliberately rejected as the more automated alternative, since rules/prompt regenerate via real LLM calls on *every* `pack()` call with no cross-run cache (unlike per-file summaries, which `use_cache` does reuse), making an auto-repack-on-push workflow a real, unbounded, and silent-review-skipping cost. A copyable GitHub Actions template lives at `docs/ci/freshness-gate.yml` (Ziplex's own repo doesn't commit its own `aif.json`, so nothing here is wired to actually run it).

**`search.py`** sits outside the `pack` sequence — pure query functions over an already-collected file set or an already-generated `detail.json`, built as MCP prep (see `ziplex-roadmap` memory: benchmarked against repomix's `grep_repomix_output`/`read_repomix_output` MCP tools before writing any MCP code). `search_files()` regex-searches original file content, not `compressed` — a match inside a body-stripped function would otherwise be invisible. `read_detail_range()` slices a `detail.json` entry's `compressed` text by 1-based line range instead of returning it whole. Exposed via the `search`/`detail` CLI subcommands, and (see below) wrapped directly by the MCP server rather than reimplemented there.

**`confidence.py`** — a free (no LLM call) heuristic for whether a summary is worth trusting: `estimate_confidence(summary, signatures)` tokenizes both (camelCase/snake_case-aware, single-suffix-"s" stemmed so "register"/"registers" count as the same word — added after a real Gemini summary scored 0.0 on nothing but that grammatical mismatch) and scores 0.0-1.0 by keyword overlap, capped at 3 matches so a file with many functions isn't penalized for a summary that abstracts over most of them. 1.0 when there are no signatures to check at all (text files) -- nothing to contradict -- **except** when `summary` is exactly `summarizer.SUMMARY_FAILED_PLACEHOLDER`, checked before that shortcut and forced to 0.0 regardless of signature count: a signature-less file (a thin `index.ts` that's just top-level imports, a real case hit in testing) whose summary generation flat-out failed would otherwise get the same free 1.0 a legitimately trivial file gets, silently skipping `correct_aif()`'s review -- the one path that placeholder's own docstring says is supposed to catch it. Called once per file in `pack()` (step 5, after summaries are final, reused or not) and stored as `confidence` alongside `summary` -- unlike `signatures`/`dependencies`/`api`, this **does** survive `finalize_aif()`'s pruning and ships in `aif.json`, since it's meant to be read by whoever consumes a summary, not just by the packing pipeline. `triage(files)` splits by `REVIEW_THRESHOLD` into (needs_review, auto_kept) for `corrector.py`'s per-file loop (step 7) and is the same function the review-scaling design leans on: not a correctness guarantee (a summary can use different words for the same idea and still be right, and this can't tell), and only as complete as `signatures` is -- a file whose real behavior lives in field initializers rather than method declarations (Java registry classes are a real example hit in testing) will score lower than it deserves, since Tree-sitter extraction only sees declared methods.

**`query_service.py`** — the transport-agnostic read-query core `mcp_server.py` and `gui_server.py` both sit on top of (same "N transports, 1 core" shape as `cli.py`/`mcp_server.py` already sharing `edits.py`/`search.py`/`freshness.py`). Holds eight functions (`get_overview`, `list_files`, `get_relationships`, `get_dependents`, `get_blast_radius`, `get_detail`, `check_freshness`, `search_project`) over `edits`/`file/relationship`/`search`/`freshness`'s existing pure functions, plus `_stale_warning()`. `get_relationships` is `get_dependents`/`get_blast_radius`'s whole-graph sibling -- the entire `relationships` field verbatim, for a caller (the GUI's post-pack Relationships page; see `src/ziplex/gui/CLAUDE.md`) that wants the project's overall shape in one call instead of walking it file by file. Read-only by design: every function reads an already-packed `aif.json`/`detail.json`/`cache.json`, or (for `search_project` and `check_freshness`) re-collects and re-security-scans the project fresh from disk on every call — none of them re-pack or re-correct a project, since that would bypass the human-correction step that's core to Ziplex's identity (see the `ziplex-roadmap` memory's "deliberately not copied" note re: repomix's per-call reconfigurable packing). `get_dependents`/`get_blast_radius` are the differentiated addition repomix doesn't have: graph queries over the *human-corrected* `relationships` tree, not just flat summary/detail lookup — `get_blast_radius` can legitimately include the queried file itself when it participates in an import cycle (verified against a real two-class mutual-import case; see `file/relationship.py`'s docstring). `get_overview`/`list_files` take an optional `project_path` -- when given, `_stale_warning()` runs the same hash-comparison `check_freshness` does (no LLM calls) and adds a `"_stale"` key only if the pack has actually drifted; omitting `project_path` skips the check entirely. Deliberately only on these two "orientation" functions -- `get_detail`/`get_dependents`/`get_blast_radius` return a bare `str`/`list[str]` with no room for a sibling field, and re-hashing on every fine-grained follow-up call would be redundant IO once the first check already surfaced drift.

**`config.py`** — an optional per-*target*-project `.ziplex.json` (not in Ziplex's own repo -- in whatever project `pack` is pointed at), analogous to repomix's `repomix.config.json` but always optional: `load_config()` never raises (missing file, bad JSON, or a non-object value all fall back to `DEFAULT_CONFIG` unchanged), so `pack()` behaves identically to before this existed with no config file at all. Scoped narrowly on purpose -- just `include`/`ignore` glob-pattern lists, the gap flagged comparing against repomix's CLI (file selection used to be all-or-nothing: everything safe via `--auto`, or one file at a time via the interactive picker, with no way to scope a pack to e.g. just `src/**` without clicking through everything else to exclude it). `pack()` loads it via `load_config(root_path)` and unions it with any `include`/`ignore` params of its own (sourced from `--include`/`--ignore` CLI flags) before calling `collect_files()` -- CLI flags augment the config file, never silently replace it. `pack_service.py`'s `list_selectable_files()` (GUI) loads the same config the same way, so the checklist a human sees in the browser can't offer a file `pack()` itself wouldn't have collected. `init_config()` (the `init` CLI subcommand) scaffolds a starter file; idempotent -- never overwrites an existing one. Living in the target project (not keyed by path inside Ziplex's own repo) means it's committable there the same way a team already commits `aif.json`/`detail.json`/`cache.json` (see README's "Team use").

**`settings.py`** — `config.py`'s per-*user* counterpart, not per-target-project: one `~/.ziplex/settings.json` (outside the repo entirely, unlike `.ziplex.json`) holding where the GUI's new-pack screen saves by default, plus the Gemini API key. Two layers `resolve_output_dir()`/`resolve_output_path()` resolve together: a global `output_dir` (the Options page's own field, GET/POST `/api/settings`) and per-project pins in `project_output_dirs` (keyed by absolute project path) that override it -- a pin is only ever written by `set_project_output_dir()`, called from `gui/pack_service.py`'s `start_pack_job()` exactly once, when a human types an explicit output path while packing that project; merely resolving and using the global default never creates one, so an unpinned project keeps tracking later changes to that default instead of silently freezing onto whatever it resolved to the first time. Neither layer configured at all resolves to `""`, at which point `packager.pack()`'s own `result_dir` param stays unset and its built-in `RESULT_DIR` default applies -- a fresh install with no `settings.json` behaves identically to before this module existed. `resolve_gemini_api_key()`/`resolve_gemini_model()` and their `openai_*`/`claude_*`/`llm_provider` siblings (2026-08-24) are the rest: all flat strings, no per-project layer (a provider choice/credential isn't project-scoped the way an output folder can be), read by `llm.py`'s per-provider `_resolve_api_key()`/`GeminiProvider.url` and `_active_provider()` fresh on every LLM call rather than once (see that module's own bullet for why). `llm_provider` alone decides which provider's fields are actually live -- `""` means "no override, `LLM_PROVIDER` env var / Gemini default applies," so an unrelated field being non-empty (an OpenAI key saved once, then switched away from) is inert until `llm_provider` names it again, rather than needing to be cleared. `_resolve_field(key, settings=None)` is the shared body all six of the newer resolvers call (`resolve_gemini_api_key()` stays its own separate function, nothing new depends on it, so it wasn't folded in). `load_settings()`'s no-file/bad-file fallback is `_fresh_defaults()`, not `dict(DEFAULT_SETTINGS)` -- a real bug caught in the same pass that added these fields: a shallow copy leaves `project_output_dirs` aliased to `DEFAULT_SETTINGS`'s own `{}`, so `set_project_output_dir()`'s in-place mutation of that key would silently corrupt the module-level default for the rest of the process the first time it ran with no `settings.json` yet on disk. `load_settings()` never raises, same spirit as `config.py`'s `load_config()`. See `src/ziplex/gui/CLAUDE.md` for the Options-page/pack-form wiring.

**`skill_export.py`** — a third distribution channel alongside the MCP server and the GUI, for Claude Code users who haven't (or can't) register the MCP server: `export_skill(aif_path)` turns an already-corrected `aif.json` (+ its sibling `detail.json`) into a Claude Agent Skill directory (`.claude/skills/<slugified project name>/` by default — `SKILL.md` plus `references/overview.md`/`files.md`/`relationships.md`/`detail.json`), which Claude Code progressively loads on its own with no server process running at all. Inspired by repomix's `--skill-generate` (see the `ziplex-roadmap` memory), but deliberately narrower: repomix's generated `files.md` embeds every file's full raw source; this module never does — `references/files.md` stays to summaries + confidence, exactly what `aif.json` itself already restricts to, and the *compressed* (not raw) per-file body only ships as `references/detail.json`, copied verbatim from the pack's own sibling file. Shipping full source in an always-committed skill directory would undo the entire reason Ziplex compresses in the first place. Pure generation (`generate_skill_files(aif, detail)`, returns `{relative_path: content}`) is split from the I/O wrapper the same way `edits.py`/`packager.py` split, so it's directly testable without touching a filesystem. Exposed via the `skill` CLI subcommand.

**`mcp_server.py`** — the MCP server: registers `query_service`'s eight functions directly as `@mcp.tool()`s (`mcp.tool()(query_service.get_overview)`, etc.) rather than wrapping them, so each tool's docstring — what the MCP SDK reads as its description — lives in exactly one place instead of a copy kept in sync here too. Uses the official `mcp` SDK's `MCPServer` (`from mcp.server import MCPServer`; note the class was renamed from the older `FastMCP` in SDK 2.x — don't go looking for `mcp.server.fastmcp`, it no longer exists). Run with `ziplex-mcp` (or `python -m ziplex.mcp_server`; stdio transport, the default `mcp.run()` picks).

**`src/ziplex/gui/`** (`gui_server.py`, `pack_service.py`, and the static frontend) — a local GUI, positioned for environments where Claude Code (or MCP generally) isn't available but browser-based AI chat is (see the `ziplex-roadmap` memory). Read-only browse routes sit on `query_service.py` (the same core `mcp_server.py` sits on); the `/api/select_files` + `/api/pack*` family is a write path that runs `packager.pack()` itself, so a project can be packed from the GUI without a prior CLI run. Full detail (the job/review state machine, the concurrency fixes it needed, the master-detail relationship editor, native OS dialogs): `src/ziplex/gui/CLAUDE.md`. Run with `ziplex-gui [--aif PATH] [--project PATH] [--port 5321] [--no-window]` (or `python -m ziplex.gui.gui_server ...`).

The final `aif.json` shape: `{ project: {name, prompt, tech_stack: [...], security_scan: {flagged, included_anyway, excluded}, format_notes, language}, rules: [...], tokens: {...}, files: {name: {summary, confidence}}, relationships: {...} }`, with siblings `<name>.detail.json` shaped `{ file-name: {compressed}, ... }` and `<name>.cache.json` shaped `{ file-name: content-hash, ... }` (both flat, same file-name keys as `files` — not nested under a `files` key).

**`project.security_scan`/`project.format_notes`** (2026-08-24, prompted by comparing a repomix-packed dump of Ziplex's own repo against `aif.json`'s own shape): two small, free (no LLM call) additions to `project`, both attached unconditionally in `packager.py`'s step 7, for the same underlying reason -- `aif.json` is meant to survive outside any one tool session (committed to a repo, handed to a colleague, pasted cold into a web chat with none of Ziplex's own docs loaded alongside it; see the `ziplex-known-limitations` memory's item 7), and neither of these facts was visible to a reader in that position before. `security_scan` (`{flagged, included_anyway, excluded}`) answers "was this scanned, and what happened to anything it found" -- computed from step 2's `scan_files()` result (`dangerous`) intersected against the final `selected` list (not the CLI-only `included_anyway` variable, which misses a GUI/`preselected` caller naming a dangerous file directly), `{0, 0, 0}` when nothing was ever flagged rather than the field being absent. The pack log's own per-run "⚠️ 민감 파일 제외" print (step 3) used to be sourced from that same CLI-only `included_anyway` variable instead of `selected` -- a real bug reported directly (2026-08-26): a GUI user who explicitly checked a dangerous file's "include anyway" box still saw it listed as excluded in the pack log, even though `preselected` correctly folded it into `selected` and the pack itself (and `security_scan`'s own count) was never wrong, only this one message. Fixed by moving the print to right after `selected` is finalized and computing `excluded` from `dangerous` files actually missing from `selected`, matching `security_scan`'s own already-correct approach exactly. the same "always present, zero when N/A" convention `tech_stack` already established -- a stronger transparency guarantee than repomix's own on/off security-check toggle, since Ziplex's scan always runs and this reports real counts instead of a flag. `format_notes` is a single fixed constant per language (`packager.FORMAT_NOTES[lang]`, identical across every pack in that language, unlike `security_scan`/`tech_stack` which are per-run facts) explaining the format itself to a cold reader with no other context: what `confidence`'s threshold means, and what `detail.json`'s `⋮----` marker stands for. `skill_export.py`'s `references/overview.md` renders `security_scan` as an extra section (same backward-compat skip-if-absent guard as `tech_stack`'s own section) — `format_notes` is left aif.json-only, not duplicated into the Skill's already-prose `SKILL.md`/`overview.md`. `project.language` (2026-08-26, see `packager.py`'s own bullet above for the full `lang` story) is the same "always attached, cheap fact" pattern applied to which language `prompt`/`rules`/every file's `summary` -- and `format_notes` itself -- were actually written in.

Every LLM-facing function in `llm.py` follows the same contract: prompt says "JSON only, nothing else," caller does `json.loads()` and falls back to a default (`{}`, `[]`, `""`) on `JSONDecodeError` — callers in `packager.py` loop until they get a non-empty result or the user intervenes via `checkpoint.handle_llm_failure`. Each one (except `analyze_relationships`, unused dead code -- `relationships` is built purely from `dependencies` by `edits.build_tree()`, never by an LLM call) also takes a `lang: str = "en"` param and appends one line naming the target language (`llm.LANGUAGE_NAMES`) to its prompt, so the *value* side of the JSON is written in that language while the JSON key itself always stays English -- see `packager.py`'s `pack(..., lang=...)` bullet above for where this ultimately comes from.
