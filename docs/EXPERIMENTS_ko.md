# 실험 로그 — 모델 / 검색(retrieval) 방식 비교

[English](EXPERIMENTS.md) | **한국어**

*이 프로젝트든 다른 타깃 프로젝트든* 그 프로젝트에 대한 질문에 답하는 여러 방식을 비교한 비정형 기록 -- Claude Code 단독 탐색 vs. Ziplex MCP/Skill, 서로 다른 LLM 프로바이더/모델, 서로 다른 `aif.json` 패킹 설정 등. 일부러 "benchmark"라고 부르지 않음: 고정되고 반복 가능한 테스트 스위트가 없고, 회차마다 조건(어떤 모델, 어떤 프로젝트, "단독" 쪽이 사전 컨텍스트를 얼마나 갖고 있었는지)이 달라서 각 회차가 실제로 무엇을 통제했는지 읽어봐야만 두 회차를 비교할 수 있음. `docs/HISTORY.md`와 같은 컨벤션으로 자동 로드되지 않음 -- 어떤 방식/모델을 쓸지 결정하기 전, 또는 새 비교 회차를 돌리기 전에 열어서, 의미가 있다면 이전 회차의 프로젝트/설정을 재사용할 것.

## 왜 이 문서가 필요한가

회차의 *결론*("Ziplex 쪽이 더 저렴했음")만 남으면 몇 달 뒤엔 거의 쓸모가 없어짐 -- 양쪽이 같은 모델이었는지? 같은 프로젝트를 실제로 어떻게 패킹했는지? Claude Code가 이 코드베이스를 대화 중에 이미 본 적이 있었는지(그러면 "단독" 쪽이 실제보다 강해 보임)? 한 줄 결론만 적어두면 사라져버릴 이런 조건들을 남기기 위해 이 문서가 존재함.

## 항목 추가 방법

아래 템플릿 블록을 복사해서 새 `### #N YYYY-MM-DD <제목>` 항목으로 채우고(값이 없으면 지우지 말고 "n/a"라고 쓸 것), 요약 표에도 같은 내용의 행을 추가해서 매 항목을 열어보지 않아도 훑어볼 수 있게 유지할 것. 원시 숫자(토큰 수, 턴 수, 성공/실패)를 남길 것 -- "Ziplex 쪽이 더 저렴했음"처럼 숫자 없는 문장은 나중에 재사용할 수도, 이후 회차 결과와 어긋날 때 재검토할 수도 없음.

이 파일과 `EXPERIMENTS.md`(영문)는 항상 같이 갱신할 것 -- 같은 항목을 양쪽에 (번역해서, 단순 복붙이 아니라) 추가하고, 한쪽만 앞서가게 두지 말 것.

## 항목

### 템플릿 (이걸 복사해서 채울 것, 위 표 직접 수정 금지)

- **비교 대상**: 예) Claude Code 단독 탐색 vs. Ziplex MCP 서버 연동 / Ziplex Skill export vs. MCP / Gemini vs. Claude summarizer
- **Ziplex 버전**: `git describe`나 커밋 해시 (`ziplex --version` 출력 그대로) -- 패킹 결과 형태가 버전마다 달라질 수 있어서 필수
- **사용 모델**: 비교 양쪽에 실제로 쓰인 모델 id 전부 (provider 포함). 양쪽이 다른 모델이면 그 차이가 결과에 섞여 들어간다는 걸 명시
- **분석 대상 프로젝트**: 프로젝트명(또는 익명화한 설명), 언어, 대략적 파일 수/규모
- **Claude Code 사전 학습 정도**: 비교의 "단독" 쪽이 이 프로젝트를 이전에 얼마나 읽었는지 -- 같은 대화에서 전체 코드베이스를 이미 훑은 뒤였는지, 완전히 새 컨텍스트로 시작했는지. 이게 다르면 "단독 탐색"이 실제보다 유리하거나 불리하게 보일 수 있어서 반드시 기록
- **Ziplex 패킹 상태**: `pack` 커맨드 옵션(`--auto`/`--no-llm`/`--lang`/`--no-cache` 등), 캐시 재사용 여부, `aif.json`/`detail.json` 크기(토큰 수), 평균 confidence
- **측정 지표**: 무엇을 어떻게 셌는지 -- 입력/출력 토큰, 턴 수, 정답 정확도, 걸린 시간 등. 지표를 어떻게 셌는지도 한 줄 (예: "`ziplex tokens` 커맨드로 측정" / "Anthropic 콘솔의 실제 사용량")
- **결과**: 숫자로. 방향(어느 쪽이 이겼는지)만 말고 격차 크기까지
- **비고**: 위 필드로 안 잡히는 것만 -- 이번 회차에서만 튄 특이값, 재현성에 영향 줄 만한 조건(네트워크 재시도, 503 등), 다음 회차에 다르게 해볼 것

### #1 2026-09-15 — Ziplex Skill/CLI vs. Claude Code 단독, 토큰 효율성

- **비교 대상**: 조건 A "Ziplex-assisted" -- pre-exported Claude Skill(`.claude/skills/ziplex/`)과 `ziplex` CLI를 주 조사 도구로 사용하도록 지시. 조건 B "Claude Code 단독" -- ziplex skill/CLI/`.ziplex/` 접근을 명시적으로 금지하고 순수 Grep/Glob/Read/Edit만 사용.
- **Ziplex 버전**: 실험 당시 main, 이후 병합된 수정 커밋(`29f2c1d`, `c91e5c8`) 반영 전 -- 정확한 커밋 해시는 기록되지 않음 (다음 회차부터는 `ziplex --version`/커밋 해시를 반드시 남길 것)
- **사용 모델**: 기록되지 않음 -- 당시 세션의 기본 서브에이전트 모델 (정확한 model id 미기록, 회고성 기록이라 복원 불가)
- **분석 대상 프로젝트**: Ziplex 자기 자신의 repo (self-pack)
- **Claude Code 사전 학습 정도**: 매 라운드 완전히 새로 스폰한 `general-purpose` 서브에이전트(포크 아님 -- 포크는 대화 컨텍스트를 물려받아 답을 흘릴 수 있어 배제) + 격리된 `git worktree`. 라운드 2/3은 버그가 있는 파일/함수명을 전혀 알려주지 않는 blind 태스크; **라운드 1은 결함 있는 설계**로, 버그 파일명을 프롬프트에 직접 명시해 "이미 위치를 아는 상태에서의 비용"만 측정한 것으로 사후에 무효 판정
- **Ziplex 패킹 상태**: 조건 A는 사전에 export된 Claude Skill(`references/relationships.md` 등 포함)을 그대로 사용 -- 이번 회차 자체에서 새로 pack하지 않음, 옵션/캐시 상태 기록 없음
- **측정 지표**: 하니스(harness)의 서브에이전트 완료 알림 `<usage>` 블록 -- `subagent_tokens`/`tool_uses`/`duration_ms`. 에이전트 자기보고 아님. 모든 "수정 완료" 주장은 coordinating 세션이 직접 재검증(로직 재실행, 테스트 재실행)한 뒤에만 신뢰
- **결과**:
  - 라운드 1 (무효 -- 파일명 사전 노출): A 174,169 tok/40 calls/347s vs B 129,872 tok/27 calls/368s
  - 라운드 2 (blind): A 181,074 tok/40 calls/391s vs B 143,068 tok/24 calls/247s -- 서로 **다른** 실버그를 각각 하나씩 발견 (겹치는 발견 없음, 직접 재검증)
  - 라운드 3 (blind, 2026-09-15): A 184,908 tok/51 calls/804s vs B 175,412 tok/34 calls/555s -- 같은 버그를 둘 다 발견했지만 **B의 수정은 불완전**(자기 테스트는 통과했지만 더 일반적인 케이스를 놓침), A의 수정이 실제로 더 정확한 일반 수정이었음
  - 종합: 토큰 비용은 baseline(단독)이 3/3 라운드 모두 저렴 -- "효율성" 가설은 이 태스크 종류(디버깅/근본원인 분석)에 대해 반증됨
- **비고**:
  - 대신 발견된 다른 가치: pre-aggregated 구조화 데이터(관계 그래프 문서)가 특정 버그 유형(구조적 이상 패턴)을 눈으로 훑을 때 더 잘 드러나게 할 수 있다는 "커버리지 상호보완" 가설 -- n=1, 미확정
  - 이 실험에서 실제 버그 3건 발견/수정 (`extract/code/languages.py`의 `from . import X` 해석 버그, `file/relationship.py`의 언어 간 동일 stem 충돌, `resolve_dependency()`의 절대 import 경로 미검증) -- 전부 main에 병합
  - **가장 중요한 교훈**: "서브에이전트가 테스트 통과시켰다"는 "수정이 완전하다"의 증거가 아님 -- 라운드 3에서 B의 불완전한 수정과, 병합된 라운드 1 수정 자체의 회귀 버그(불필요한 `"."`/`".."` 항목이 항상 추가되던 문제)가 전체 테스트 스위트 통과 상태에서도 존재했고, 코디네이터의 독립 재검증으로만 발견됨
  - `isolation: "worktree"`가 코디네이팅 세션에서 방금 전환한 로컬 브랜치를 못 따라간 사례 발견 (라운드 3 초반 설계 결함) -- worktree 기반 서브에이전트를 쓸 때 실제 base ref를 나중에라도 직접 확인할 것

### #2 2026-09-16 — Ziplex 패킹 데이터 vs. Claude Code 단독, 실제 대형 외부 프로젝트에서

- **비교 대상**: 조건 A "Ziplex-assisted" -- 대상 프로젝트를 미리 패킹해둔 `aif.json`/`detail.json`/`cache.json`과 `ziplex` CLI를 주고, raw Grep/Read로 넘어가기 전에 이걸 먼저 쓰도록 지시. 조건 B "Claude Code 단독" -- `ziplex` CLI나 미리 패킹된 파일을 쓰지 말라고 명시적으로 지시; 순수 Grep/Glob/Read/Edit/Bash만. (이번 회차는 Claude Skill을 안 씀 -- 아래 비고 참고.)
- **Ziplex 버전**: main `57a412a` (`ziplex 0.5.0`). 참고: 이번 회차의 pack 실행 자체가 같은 날 나온 수정 커밋(`57a412a`)을 만들어낸 계기임 -- 비고 참고.
- **사용 모델**: 양쪽 모두 `claude-sonnet-5` (두 서브에이전트 실행 모두 `model: "sonnet"`을 명시적으로 지정해서 고정/기록함 -- 라운드 1에서 기록 안 됐던 부분을 보완)
- **분석 대상 프로젝트**: [scrapy/scrapy](https://github.com/scrapy/scrapy) (실제로 활발히 유지보수되는 오픈소스 Python 웹 크롤링 프레임워크), 커밋 `86bec33cd3e6311b8481eac7d02e3ab0ec06f394` (2026-09-15) 기준 클론. `.py` 502개, 전체 696개 파일, ~8.7MB. Ziplex 자기 자신의 repo(#1)보다 일부러 더 큰 걸 골랐음 -- "baseline이 더 저렴하다"는 이전 결론이 grep만으로도 충분히 훑을 수 있는 작은 코드베이스라서 나온 결과인지 확인하기 위함. 이미 패킹해둔 실제 프로젝트를 재사용하는 대신 "유명한 대형 오픈소스 repo"를 쓰기로 한 건 사용자의 명시적 선택이었고, 그로 인해 모델이 사전학습으로 이 코드를 이미 부분적으로 "알고 있을" 위험을 감수하기로 한 것 (비고 참고).
- **Claude Code 사전 학습 정도**: 완전히 새로 스폰한 `general-purpose` 서브에이전트 2개(포크 아님), 각자 독립된 클론 복사본(`scrapy_A`/`scrapy_B`, 일반 디렉터리 복사 -- Ziplex repo 밖에서 파일을 수정하므로 Ziplex repo의 git worktree 격리는 여기 해당 안 됨)에서 작업. 둘 다 이 정확한 클론을 이전에 본 적 없음. 둘 다 "scrapy 내부에 대한 사전/훈련 지식을 실제 코드로 검증하지 않고 그대로 믿지 말 것"이라고 명시적으로 지시함 -- 위에서 언급한 사전학습-친숙도 위험을 부분적으로 완화하려는 조치(완전히 없애지는 못함).
- **Ziplex 패킹 상태**: `ziplex pack <scrapy_A> --auto --auto-correct` (실제 Gemini 호출, `gemini-3.5-flash`, 기본 출력 경로 `.ziplex/`) -- 완료까지 체크포인트에서 두 번 재시작 필요(비고 참고). 최종 패킹: 665개 파일 요약, 토큰 분석 결과 `GPT-4o: 1,148,518 → 42,122 (96.3% 절감)` / `Claude (근사치): 1,200,250 → 39,927 (96.7% 절감)`. 이 패킹은 두 서브에이전트를 실행하기 *전에* 끝냈으므로 조건 A의 측정 비용에는 포함되지 않음 -- #1과 같은 컨벤션.
- **측정 지표**: 하니스 자체의 서브에이전트 완료 `<usage>` 블록(`subagent_tokens`/`tool_uses`/`duration_ms`), 자기보고 아님. 정확성은 코디네이팅 세션이 직접 재검증: (1) 각 복사본의 변경을 원본 클론과 diff, (2) 두 에이전트 중 누구의 스크립트에도 없던 케이스 2개를 포함한 5가지 케이스를 다루는 별도 검증 스크립트를 새로 작성해 실행, (3) 대상 프로젝트 자체의 실제 기존 테스트 파일(`tests/test_utils_response.py`, `tests/test_http_response_text.py`, `tests/test_linkextractors.py`)을 두 수정본과 원본 baseline에 각각 실행.
- **결과**:
  - 조건 A (Ziplex-assisted): 65,565 tok / tool call 16회 / 262.6초 (~4.4분)
  - 조건 B (Claude Code 단독): 63,876 tok / tool call 19회 / 214.9초 (~3.6분)
  - baseline이 토큰도 **약 2.6% 더 적게** 쓰고 시간도 **약 18% 더 빠름** -- 그런데 tool call 수는 오히려 더 많음(19 vs 16). A의 `ziplex` CLI 서브프로세스 호출 하나하나가 B의 네이티브 Grep/Read보다 이 태스크 유형에서는 개별적으로 더 비싸고/느렸다는 뜻으로 보임 -- A가 일을 덜 했다는 뜻은 아님.
  - 두 조건 모두 정확히 같은 실버그([scrapy/scrapy#3017](https://github.com/scrapy/scrapy/issues/3017), 2017년에 등록되어 아직도 열려 있음 -- `scrapy/utils/response.py`의 `get_base_url()`/`get_meta_refresh()`가 `<base>`/meta-refresh 태그를 찾기 전에 응답 본문을 첫 4096자로 강제 잘라내는 문제)를 똑같이 빠르게 찾음. 조건 A는 `ziplex search` 한 번으로 바로 그 truncation 라인에 도달했고, 조건 B는 repo 전체 Grep(`base href|<base|_baseurl|...`)으로도 거의 바로 도달함. **#1의 라운드 2/3처럼 이번엔 두 조건이 서로 다른 버그를 찾는 일이 일어나지 않았음** -- 이 버그는 어느 방식으로든 빠르게 찾을 수 있는 종류였음.
  - **그런데 정확성은 갈렸음**: 코디네이터의 독립 검증 스크립트(5가지 케이스, `get_base_url`/`get_meta_refresh` 둘 다, `</head>`가 전혀 없는 문서, 회귀 체크, `<base>` 태그 없을 때 fallback 체크 포함)로는 **두 수정 모두 5/5 통과**. 하지만 대상 프로젝트 자체의 *기존* 테스트 스위트를 두 복사본에 각각 돌려보니, **조건 A의 수정이 실제 기존 테스트 하나를 깨뜻렸음**(`tests/test_utils_response.py::test_get_meta_refresh` -- `<meta>` 태그가 `<noscript>` 안에 있고, noscript의 실제 닫는 태그보다 앞에 문자열 그대로의 `</head>`가 등장하는, 일부러 지저분하게 만든 HTML 픽스처). A의 수정은 검색 대상 텍스트를 첫 번째 `</head>` 매치 지점에서 잘라내는데, 이 픽스처에서는 그게 `</noscript>` 닫는 태그를 잘라버려서 `w3lib`의 `ignore_tags` 제거 로직이 그 태그를 보지도 못하게 되고, 결과적으로 무시돼야 할 meta 태그가 그대로 잡힘. 조건 B의 수정(4096자 truncation을 다른 경계로 바꾸는 대신 통째로 제거)은 이런 실패 모드가 없어서 기존 스위트를 100% 통과(해당 파일 26/26, 더 넓은 범위 파일 2개 277/277) -- 회귀 0건. 원본(pristine) baseline도 26/26 전부 통과함(기존 픽스처 중 원래 버그를 유발할 만큼 큰 문서가 없었으므로) -- 즉 이건 A의 수정이 새로 만들어낸 회귀이지, 원래 있던 flaky 테스트가 아님.
- **비고**:
  - **500개 이상 파일짜리 실제 프로젝트를 이번 회차용으로 패킹해보려다가, 그 자체로 진짜 Ziplex 버그를 발견/수정하게 됨**: `packager._extract_rules()`가 수집된 모든 파일의 signature를 크기 제한 없이 `analyze_rules()` 프롬프트에 그대로 밀어넣고 있었음(다른 프롬프트용으로는 이미 `_build_architecture_summary()`에 `MAX_ARCHITECTURE_FILES` 캡이 있었는데, 이건 별개 함수라 캡이 없었음). 이 프로젝트 기준으로 캡 없는 `signatures_map`의 repr만으로도 ~94k 토큰이 나왔고, 모델이 이걸 완전한 JSON 응답으로 돌려주지 못했음 -- 그런데 이게 HTTP 레벨에서는 매번 "성공"으로 처리돼서(429/503처럼 `generate()`가 재시도하는 종류의 실패가 아님), 비대화형 `pack()`은 이걸 진짜 영구적 실패와 구분할 방법이 없어서 시도할 때마다 결정적으로 체크포인트 후 중단됨 -- 이걸 진단하고 고치기 전까지 두 번 반복됐음(같은 날 커밋 `57a412a`, 수정 후 테스트 897/897 통과). 이 수정이 없었다면 조건 A용 사전 패킹 데이터 자체가 존재하지 못했을 것 -- 이건 정확히 #1(Ziplex 자기 자신의 ~115개 파일 repo self-pack)로는 절대 드러날 수 없었던 "진짜 큰 프로젝트"급 결함.
  - **#1의 "테스트 통과 ≠ 수정 완료" 교훈이 이번엔 더 공들인 쪽에서 재현됨**: 조건 A의 수정이 둘 중 더 정교했음(새 정규식 + 헬퍼 함수, `</head>` 경계라는 근거를 명시적으로 설명, 스스로 "엣지 케이스" 3개를 확인했다고 보고) -- 그런데도 실제 회귀를 냈음. 조건 B의 수정은 더 단순했음(truncation을 그냥 삭제, 응답별 캐싱이 이미 있으니 비용 걱정 없다는 논리) -- 회귀 없음. 두 에이전트 중 누구의 자체 테스트도 A의 회귀를 못 잡았음 -- 코디네이터가 두 에이전트 누구의 자체 repro 스크립트도 아닌, *대상 프로젝트 자체의* 기존 테스트 스위트를 수정본에 돌려봐서만 드러남. "자기보고가 더 꼼꼼해 보임"이 실제 정확성의 신뢰할 만한 신호는 아니었음.
  - **계획과 실제 실행 사이의 방법론적 차이**: 조건 A는 원래 #1처럼 "미리 export된 Claude Skill"을 쓰도록 설계했는데, Claude Code의 Skill 자동 인식은 *메인 세션의* 프로젝트 루트(이 Ziplex repo) 기준으로 스코프되고, 서브에이전트가 별개의 외부 경로에서 작업 중일 때는 적용이 안 됨 -- 이 repo 밖에서 동작하는 서브에이전트에게 "scrapy" skill을 자동으로 인식시킬 방법이 없었음. 대신 `aif.json`/`detail.json` 파일 경로 + `ziplex` CLI를 직접 주고 "이걸 주 도구로 써라"라고 설명하는 방식으로 대체함. 이게 오히려 skill 패키징/자동인식 레이어 없이 패킹된 데이터 자체의 유용성을 더 직접적으로 테스트한 셈일 수도 있지만, #1의 설계와는 실제로 다른 부분이니 두 항목을 너무 문자 그대로 비교하기 전에 알아둘 것.
  - **사전학습 친숙도 위험, 감수했지만 없애진 못함**: scrapy는 꽤 유명한 라이브러리라, 두 서브에이전트 다 원칙적으로는 실제 조사 없이 훈련 데이터에서 기억해낸 답으로 때울 수 있었음. 둘 다 기억에 의존하지 말고 실제 코드로 검증하라고 명시적으로 지시했고, 기록된 tool call 수(16/19)와 조건 B가 실제 `w3lib` 소스를 직접 열어본 점 등을 보면 진짜 조사가 이뤄진 것으로 보이지만 -- 이 위험은 완화됐을 뿐 완전히 배제된 건 아니고, 이건 정확히 "이미 패킹된 프로젝트 재사용" 대신 "유명 오픈소스 repo"를 고른 선택이 감수하기로 한 트레이드오프임.
  - 이 버그/프로젝트 기준 n=1, #1과 동일한 유보 사항 -- 이건 *이* 프로젝트의 *이* 버그에서 baseline이 더 저렴하고 빠르고(별개의 솔루션 설계 선택을 통해, 툴링 자체가 원인은 아니게) 더 정확했다는 것만 확인해줌. Ziplex-assisted 조사가 일반적으로 더 느리거나 비싸거나 품질이 낮다는 걸 확립하는 건 아님.

### #3 2026-09-18 — Ziplex 패킹 데이터 vs. Claude Code 단독, 디버깅 대신 이해도(고정 Q&A) 측정

동기: #1/#2는 둘 다 *디버깅* 태스크를 측정했는데, 이건 정답이 자기검증되는(테스트 통과/실패) 종류임. 이번 항목은 "토큰당 순수 프로젝트 이해도"를 측정하는 쪽으로 바꿈 -- 실제로 검증하고 싶었던 건 "Ziplex가 프로젝트를 이해하는 데 필요한 토큰을 줄여준다"는 원래의 핵심 주장이지, "패킹된 산출물 자체가 작다"(이건 `ziplex tokens`로 이미 그 자체로 증명되고 애초에 의심된 적 없음)가 아니라 "그걸 쓰는 에이전트가 실제 프로젝트 질문에 답할 때 결국 더 싸지거나/더 정확해지는가"임.

- **비교 대상**: 조건 A "Ziplex-assisted" -- 미리 생성된 Ziplex 패킹(`aif.json`/`detail.json`)과 `ziplex` CLI를 주고, raw Grep/Read로 넘어가기 전에 이걸 먼저 쓰도록 지시. 조건 B "Claude Code 단독" -- 사전 처리된 요약이 전혀 없다고 명시하고 Glob/Grep/Read/Bash만 쓰도록 지시. 양쪽 다 코드베이스에 대한 *같은 고정 12문항 질문지*(아키텍처, 특정 함수 동작, 의존성/설정 사실)를 한 번에 받고, 왕복 없이 한 번에 12개 다 답하도록 요청.
- **Ziplex 버전**: main `7b4857b` (`ziplex 0.5.0`)
- **사용 모델**: 양쪽 모두 `claude-sonnet-5` (두 서브에이전트 실행 모두 `model: "sonnet"` 명시)
- **분석 대상 프로젝트**: [spf13/cobra](https://github.com/spf13/cobra) (실제로 활발히 유지보수되는 오픈소스 Go CLI 빌딩 라이브러리), 커밋 `adbc8813901bba65827259daa8e22ff94ec1f30e` 기준 클론. `.go` 36개, 전체 66개 파일 -- scrapy(#2)보다 *덜 유명한* 실제 OSS 프로젝트를 일부러 골라서 사전학습-암기 위험을 줄이면서도 진짜/비trivial한 프로젝트로 유지함. 사용자가 검토한 후보 목록(예: `pallets/click` 대신)에서 골랐고, #1/#2가 둘 다 Python이었던 것에서 벗어나 Ziplex의 Go 지원도 같이 검증하려는 의도.
- **Claude Code 사전 학습 정도**: 완전히 새로 스폰한 `general-purpose` 서브에이전트 2개(포크 아님), 각자 독립된 일반 디렉터리 복사본(`cobra-a`/`cobra-b`, 둘 다 `.git` 제거)에서 작업. 둘 다 이 정확한 클론을 이전에 본 적 없음.
- **Ziplex 패킹 상태**: `ziplex pack <cobra-a> --auto --auto-correct` (실제 Gemini 호출). 첫 시도의 rules 추출 단계가 실패하고 체크포인트됨(비대화형 모드는 LLM 실패 시 추측하는 대신 항상 체크포인트 후 종료) -- 한 번 재시작 후 깔끔하게 완료. 최종 패킹 토큰 분석: `GPT-4o: 168,711 → 3,501 (97.9% 절감)` / `Claude (근사치): 159,095 → 3,326 (97.9% 절감)`. 패킹은 두 서브에이전트를 실행하기 전에 끝냈고 조건 A의 측정 비용에는 포함 안 됨.
- **측정 지표**: 하니스 자체의 서브에이전트 완료 `<usage>` 블록(`subagent_tokens`/`tool_uses`/`duration_ms`), 자기보고 아님. 정확성: 12문항, 24점 만점(문항당 0/1/2점) 답안지를 coordinating 세션이 *실제 소스를 직접 읽고*(command.go, args.go, flag_groups.go, active_help.go, completion 생성 파일들, go.mod, doc/*.go) 두 서브에이전트를 실행하기 *전에* 작성 -- 어느 쪽 답변에도 영향받지 않도록. 각 서브에이전트의 최종 답을 이 동일한 고정 답안지로 채점.
- **결과**:
  - 조건 A (Ziplex-assisted): 84,785 tok / tool call 13회 / 65.6초 -- 24/24 (12문항 전부 완벽, 정확한 파일/라인/함수 인용 포함)
  - 조건 B (Claude Code 단독): 64,926 tok / tool call 21회 / 85.3초 -- 24/24 (동일하게 전부 완벽)
  - **정확도는 완전 동점** -- 양쪽 다 미묘한 문항(예: `flag_groups.go`의 정확한 세 annotation 상수와 각각을 설정하는 메서드, 또는 `legacyArgs`가 서브커맨드 없는 커맨드/서브커맨드 있는 root 커맨드/서브커맨드 있는 non-root 커맨드에서 각각 어떻게 분기하는지)까지 포함해서 모든 문항을 정확히 맞춤.
  - **baseline이 토큰에서 약 23% 더 저렴**(64,926 vs 84,785) -- tool call은 오히려 더 많은데도(21 vs 13) -- #2에서 이미 본 "ziplex CLI 서브프로세스 호출이 native Grep/Read보다 건당 더 비싸다" 패턴과 같은데, 이번엔 격차가 더 큼.

- **비고**:
  - 디버깅이 아니라 *이해도*를 테스트한 첫 항목이고, 조건 간 발산(#1처럼 서로 다른 버그를 찾거나, #2처럼 한쪽 수정이 더 나쁘거나) 없이 **완전 동점**이 나온 첫 항목 -- #1/#2와는 결과 양상 자체가 다름.
  - 동점의 가능한 설명(미확정): cobra 소스는 질문지가 참조한 거의 모든 함수에 이례적으로 꼼꼼한 doc comment가 달려 있음(Go 컨벤션의 모범 사례) -- 그래서 *어떻게* 답을 찾았는지와 무관하게 어느 쪽이든 정답을 맞출 수 있었을 가능성. 즉 이 질문지가 진짜 이해도 격차를 드러낼 만큼 어렵지 않았을 수 있음. 여러 파일을 종합해야 하는(단순히 잘 문서화된 함수 하나를 찾는 게 아니라) 더 어려운 질문지가 자연스러운 다음 단계.
  - 패킹 중 rules 추출 체크포인트/재시작은 더 깊이 조사하지 않음("❌ rules 코딩 룰 생성 실패" 외에 로그된 에러 상세 없음) -- 이게 일시적 Gemini 이슈인지, `_extract_rules()`가 더 우아하게 처리해야 할 문제인지 확인할 가치 있음. 특히 #2 자체 조사에서 훨씬 큰 프로젝트에 대해 같은 함수의 실제 관련 버그(`57a412a`, 프롬프트 크기 제한 없음)를 발견했던 만큼. cobra는 scrapy보다 훨씬 작아서 정확히 같은 캡-오버플로우 버그일 가능성은 낮지만, 실패 양상(HTTP 레벨에서는 "성공"한 것을 체크포인트 후 종료) 자체는 같은 모양.
