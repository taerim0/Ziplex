# 실험 로그 — 모델 / 검색(retrieval) 방식 비교

[English](EXPERIMENTS.md) | **한국어**

*이 프로젝트든 다른 타깃 프로젝트든* 그 프로젝트에 대한 질문에 답하는 여러 방식을 비교한 비정형 기록 -- Claude Code 단독 탐색 vs. Ziplex MCP/Skill, 서로 다른 LLM 프로바이더/모델, 서로 다른 `aif.json` 패킹 설정 등. 일부러 "benchmark"라고 부르지 않음: 고정되고 반복 가능한 테스트 스위트가 없고, 회차마다 조건(어떤 모델, 어떤 프로젝트, "단독" 쪽이 사전 컨텍스트를 얼마나 갖고 있었는지)이 달라서 각 회차가 실제로 무엇을 통제했는지 읽어봐야만 두 회차를 비교할 수 있음. `docs/HISTORY.md`와 같은 컨벤션으로 자동 로드되지 않음 -- 어떤 방식/모델을 쓸지 결정하기 전, 또는 새 비교 회차를 돌리기 전에 열어서, 의미가 있다면 이전 회차의 프로젝트/설정을 재사용할 것.

## 왜 이 문서가 필요한가

회차의 *결론*("Ziplex 쪽이 더 저렴했음")만 남으면 몇 달 뒤엔 거의 쓸모가 없어짐 -- 양쪽이 같은 모델이었는지? 같은 프로젝트를 실제로 어떻게 패킹했는지? Claude Code가 이 코드베이스를 대화 중에 이미 본 적이 있었는지(그러면 "단독" 쪽이 실제보다 강해 보임)? 한 줄 결론만 적어두면 사라져버릴 이런 조건들을 남기기 위해 이 문서가 존재함.

## 알려진 공백: 패킹 비용이 어디에도 안 잡힘 (#2-#5 항목)

**앞으로의 라운드용으로는 고침(main `27384c1`)**: `llm.py`의
`usage_tracker`가 이제 각 provider의 실제 응답에서 과금된 입력/출력 토큰을
직접 캡처함(Gemini의 `usageMetadata`, OpenAI/Claude의 `usage` 필드);
`pack()`이 실행마다 한 번씩 리셋하고, `cli.py`의 `pack` 서브커맨드가 기존
"토큰 분석" 블록 바로 다음에 스냅샷을 출력함. 아래에 적힌 달러 환산 문제는
아직 미해결(provider별 raw 토큰 수만 보여줄 뿐, provider 간 달러 합산은
아직 안 됨)이고, #2-#5 항목들은 이 기능이 생기기 전에 이미 돌린 거라
그 패킹 비용은 여전히 기록 안 된 채로 남아있고 패킹을 다시 돌리지 않고는
복원 불가. #6+ 라운드부터는 이 숫자를 캡처/기록해야 함.

#2부터 모든 항목이 패킹 자체를 만드는 비용(`ziplex pack ... --auto
--auto-correct`, 실제 Gemini API 호출)을 조건 A의 측정 비용에서 제외함 --
각 항목 비고에 명시적으로 적혀있음("이 패킹은 두 서브에이전트를 실행하기
전에 끝냈으므로 조건 A의 측정 비용에는 포함되지 않음"). 이 관례는 "이미
패킹이 존재한다고 가정했을 때 그걸 쓰는 게 값어치가 있는가"를 측정하려는
의도로는 맞는데, 지금까지의 모든 항목이 실제로는 "한 번 새로 패킹해서
딱 한 번만 쓰고 임시 클론째로 버려지는" 시나리오였다는 점에서, 한 번만
쓰고 마는 패킹의 진짜 총비용을 조용히 숨기고 있음.

각 항목에 기록된 건 *패킹된 산출물의 크기*(ziplex 자체의 "토큰 분석" 줄,
예: "GPT-4o: 168,711 → 3,501")뿐임 -- 이건 원본 파일 토큰 대비 압축된
출력 토큰이지, Gemini API가 그걸 만들어내는 배치 요약 호출들에서 실제로
과금한 토큰 수(각 배치의 전체 입력 -- signature, dependency, 잘린
content 등 -- 를 포함하지, 최종 요약 텍스트만이 아님)가 **아님**.
`llm.py`는 현재 Gemini의 `usageMetadata`(prompt/candidates/total 토큰
수)를 어디에서도 캡처/로깅하지 않아서, #2-#5의 어떤 패킹에 대해서도 그
진짜 숫자가 기록된 적이 없고, 패킹을 다시 돌리지 않고서는 사후에 복원할
수도 없음.

설령 그 숫자가 있었더라도 단위 불일치 문제가 남음: 패킹은 Gemini 토큰을
쓰고 질의는 Claude Sonnet 토큰을 쓰는데, 이 둘은 가격이 같지 않음 --
공정한 "총 실비용" 비교를 하려면 provider 간 raw 토큰 합산이 아니라
달러 환산이 필요함.

이 노트 작성 시점까지 미수정 상태. 간단한 수정(Gemini의 실제
`usageMetadata`를 호출마다 로깅해서 pack 실행 전체에 합산, 기존
토큰-분석 블록 옆에 출력)은 이 실험 로그와 별개로 `pack()` 자체에도
실질적 가치가 있는 개선 -- 여기서 바로 하지 않고 후속 작업으로 추적.

## 항목

### 템플릿 (이걸 복사해서 채울 것, 위 표 직접 수정 금지)

- **비교 대상**: 예) Claude Code 단독 탐색 vs. Ziplex MCP 서버 연동 / Ziplex Skill export vs. MCP / Gemini vs. Claude summarizer
- **Ziplex 버전**: `git describe`나 커밋 해시 (`ziplex --version` 출력 그대로) -- 패킹 결과 형태가 버전마다 달라질 수 있어서 필수
- **사용 모델**: 비교 양쪽에 실제로 쓰인 모델 id 전부 (provider 포함). 양쪽이 다른 모델이면 그 차이가 결과에 섞여 들어간다는 걸 명시
- **분석 대상 프로젝트**: 프로젝트명(또는 익명화한 설명), 언어, 대략적 파일 수/규모
- **Claude Code 사전 학습 정도**: 비교의 "단독" 쪽이 이 프로젝트를 이전에 얼마나 읽었는지 -- 같은 대화에서 전체 코드베이스를 이미 훑은 뒤였는지, 완전히 새 컨텍스트로 시작했는지. 이게 다르면 "단독 탐색"이 실제보다 유리하거나 불리하게 보일 수 있어서 반드시 기록
- **Ziplex 패킹 상태**: `pack` 커맨드 옵션(`--auto`/`--no-llm`/`--lang`/`--no-cache` 등), 캐시 재사용 여부, `aif.json`/`detail.json` 크기(토큰 수), 평균 confidence
- **측정 지표**: 무엇을 어떻게 셌는지 -- 입력/출력 토큰, 턴 수, 정답 정확도, 걸린 시간 등. 지표를 어떻게 셌는지도 한 줄 (예: "`ziplex tokens` 커맨드로 측정" / "Anthropic 콘솔의 실제 사용량")
- **결과**: 숫자로. 방향(어느 쪽이 이겼는지)만 말고 격차 크기까지
- **비고**: 위 필드로 안 잡히는 것만 -- 이번 회차에서만 튄 특이값, 재현성에 영향 줄 만한 조건(네트워크 재시도, 503 등), 다음 회차에 다르게 해볼 것

### #6 2026-09-19 — 패킹이 반복 재사용으로 회수되는가? (amortization 테스트)

#5 직후 사용자가 "#1-#5의 대부분 부정적/혼재된 결과를 보면 Ziplex의 핵심 토큰 절감 홍보 문구가 여전히 의미 있나"라고 직접 물은 것과, 별개로 (#4/#5 이후 약하고 줄어드는 니치로 기각된) "파일시스템 접근 없음" 대신 "한 번 패킹하고 여러 쿼리에 재사용"이 더 나은 대안인지 물은 것에서 바로 이어짐. 이 항목이 그 가설의 첫 실제 테스트고, godot-open-rpg(#4와 동일 프로젝트/커밋)를 써서 #4에서 이미 측정한 쿼리당 비용을 처음부터 다시 재는 대신 출발점으로 재사용함.

**2단계 설계:**

- **1단계(대수적 계산, 저비용)**: godot-open-rpg의 실제 1회성 패킹 비용을 사상 처음으로 측정(이전 항목들은 패킹된 *결과물*의 크기만 있었지, LLM API가 실제로 과금한 비용은 없었음 -- 위 "알려진 공백" 섹션 참고), 그 다음 #4에 이미 기록된 토큰 격차를 이용해 조건 A의 amortized 평균 비용(pack_cost/N + A 자체의 쿼리당 비용)이 조건 B의 고정 쿼리당 비용 밑으로 내려가는 재사용 횟수 `N`(break-even)을 계산.
- **2단계(실증)**: 같은 패킹 결과물에 대해 독립적인 10문항 라운드를 2개 더(#4의 원래 12문항과 일부러 다른 서브시스템을 다룸 -- 아래 참고) 돌려서, 1단계 계산이 의존하는 쿼리당 비용 격차가 다른 진짜 질문들에서도 실제로 안정적인지, 아니면 #4의 특정 질문 세트에만 국한된 것인지 확인.

- **Ziplex 버전**: main `4adf379` -- 1단계를 가능하게 하려고 이 세션에서 바로 전에 만든 `usage_tracker` 기능(`27384c1`)이 포함됨. `pack()` 중 각 provider가 실제로 과금한 입력/출력 토큰을 로깅함.
- **사용 모델**: 모든 서브에이전트(양쪽 조건, 새 라운드 둘 다) `claude-sonnet-5`; 패킹은 `gemini-3.5-flash`(`describe_active_provider()`로 `GEMINI_MODEL`의 floating 기본값이 현재 이걸로 해석되는 걸 확인).
- **분석 대상 프로젝트**: [gdquest-demos/godot-open-rpg](https://github.com/gdquest-demos/godot-open-rpg), #4와 *동일한* 커밋(`19bd328fae9e4b534d3bb6db380a3d871d6ea58f`)으로 재클론 -- #4의 원래 클론/패킹은 그 항목 자체의 정리 작업에서 이미 삭제됐으므로, 이건 #4 파일의 문자 그대로의 재사용이 아니라 새로 클론+패킹한 것이지만 동일한 프로젝트 상태임.
- **Claude Code 사전 학습 정도**: 새 라운드 2개에 걸쳐 완전히 새로 스폰한 `general-purpose` 서브에이전트 4개(포크 아님), #3/#4/#5와 같은 독립된 일반 디렉터리 복사본 패턴(`rpg-a`/`rpg-b`).
- **Ziplex 패킹 상태**: `ziplex pack <rpg-a> --auto --auto-correct`, 실제 Gemini 호출. #3/#4/#5의 "첫 시도는 항상 실패"(#5에서 언급된 rules 추출 체크포인트 실패 3전 3패) 패턴과 달리, 이번 실행은 첫 시도부터 바로 성공함 -- 즉 그 실패 패턴이 보편적/결정적인 게 아니라는 뜻, 나중에 조사할 사람을 위한 또 하나의 데이터 포인트. **처음으로 측정한 실제 패킹 비용**: 실제 LLM 요청 572회, 입력 토큰 370,010개, 출력 토큰 67,475개(`llm.get_usage()`의 스냅샷) -- `gemini-3.5-flash`의 공식 요금(입력 100만 토큰당 $1.50, 출력 100만 토큰당 $9.00, 2026-09-19에 실시간 조회, 기억으로 추정 안 함) 기준 **$1.1623**.
- **라운드2 질문**(10개, Inventory/Cutscene/UI 서브시스템 -- #4의 Combat/Overworld-core 세트와 일부러 다른 파일): `Inventory`(`Resource` 상속, 6개 값 `ItemTypes` enum, `user://inventory.tres`에 저장), `Trigger`/`Interaction`이 공유하는 `Cutscene extends Node2D` 베이스, `UIInventory extends HBoxContainer`, `PlayerController extends GamepieceController extends Node2D`, `Pathfinder extends AStar2D`, `MusicPlayer extends Node`/`ScreenTransition extends CanvasLayer`. 답안지는 #3-#5와 마찬가지로 두 서브에이전트 실행 전에 실제 소스로 작성.
- **라운드3 질문**(10개, camera/events/유틸리티 서브시스템, 세 번째의 또 다른 영역): `FieldCamera extends Camera2D`, `FieldEvents` autoload signal bus의 살아있는 signal 7개 전부, `CollisionFinder`/`Directions` 둘 다 `extends RefCounted`, `Directions.Points`의 4개 값과 `angle_to_direction()` 변환 함수, `Pathfinder extends AStar2D`(라운드2와 다른 각도로 재질문), 입력-일시정지 vs 인터랙션-선택 중 UI가 어느 `FieldEvents` signal을 들어야 하는지.
- **측정 지표**: 라운드별 서브에이전트 비용은 이전 모든 항목과 같은 하니스 `<usage>` 블록; 실제 패킹 비용은 새 `usage_tracker`. 달러 환산은 공식적이고 실시간으로 조회한(추정 아님) 가격 사용: Gemini 3.5 Flash 입력/출력 100만 토큰당 $1.50/$9.00; Claude Sonnet 5 입력/출력 100만 토큰당 $2/$10(둘 다 2026-09-19에 조회, 나중에 바뀌어도 이 항목이 갱신되진 않음). **바로 실제 한계에 부딪힘**: 하니스 자체의 서브에이전트 `<usage>` 블록이 단일 합산 `subagent_tokens` 숫자만 보여주고 input/output 분할은 어디에도 노출 안 함 -- Claude Sonnet 5의 입력/출력 가격이 5배 차이 나서 그 분할 없이는 라운드별 정확한 달러 비용을 계산할 수 없음, 그래서 1단계의 break-even 표는 하나의 숫자 대신 가정한 input 비율(0%~100%) 전체에 걸친 *범위*로 보고함 -- Gemini 쪽은 패킹-비용 수정으로 정확해진 것과 달리, 이건 사실이 아니라 명시적으로 가정임을 표시.
- **결과**:
  - **1단계(대수적)**: #4 자체의 토큰 격차(A: 66,692 vs B: 70,322 tok)와 실제 패킹 비용 $1.1623을 이용하면, break-even `N`은 32회(비현실적인 100%-output 가정)에서 160회(비현실적인 100%-input 가정)까지 범위이고, agentic 코딩 태스크에 가장 그럴듯한 input 비중(85%~95%)에서는 **100~133회** 근처에 자리잡음. 즉: 가장 현실적으로 그럴듯한 경우에도, #4에서 관측된 쿼리당 절감액이 1회성 비용을 갚으려면 같은 패킹을 100회 넘게 독립적으로 재사용해야 함.
  - **2단계(실증) -- 이게 진짜 발견**: #4 자체의 쿼리당 우위가 재현되지 않음. 라운드2: A 65,015 tok/19회/41.6s vs B 62,460 tok/13회/33.1s -- **baseline이 더 저렴**. 라운드3: A 59,935 tok/8회/30.7s vs B 57,527 tok/9회/29.9s -- **또 baseline이 더 저렴**. 같은 패킹에 대한 3개 독립 라운드(#4 + 라운드2 + 라운드3) 전체 평균: 조건 A 63,881 tok, 조건 B 63,436 tok -- **평균적으로 baseline이 약 0.7% 더 저렴**, #4 단독이 시사했던 ~5% Ziplex 우위가 아니라 사실상 완전 동점에 baseline 쪽으로 근소하게 기움.
  - 정확도는 내내 동점 유지: 12/12(#4) + 10/10(라운드2) + 10/10(라운드3) = 양쪽 다 32/32, 이 항목 전체에 걸쳐 어느 시점에도 발산 없음.
- **비고**:
  - **핵심 발견은 "amortization이 안 통한다"가 아니라, "amortize할 대상 자체가 애초에 없었다"는 것**. 1단계의 break-even 계산은 #4의 ~5% Ziplex-우위 격차가 이 프로젝트의 실재하고 안정적이고 활용 가능한 속성이라고 가정했는데, 2단계는 동일한 패킹에 대해 다른(하지만 똑같이 실제인) 질문으로 다시 측정하면 그 격차가 살아남지 않는다는 걸 보여줌. 어느 라운드가 "이겼는지"보다 표본 크기가 더 중요함 -- #3/#4/#5 자체의 단일 라운드 비교도 이제 같은 조심성으로 읽어야 함: 단일 라운드의 승자는 진짜 효과만큼이나 쉽게 노이즈일 수 있고, 이건 이 프로젝트의 실험 로그가 지금까지 직접 테스트한 적 없던 것임.
  - **앞으로의 라운드를 위한 구체적인 방법론적 교훈**: 단일 질문 세트의 비용 비교를 프로젝트 수준의 판정으로 믿지 말 것. 가능하면 방향성 있는 결론을 내리기 전에 같은 프로젝트/패킹에 대해 독립적인(겹치지 않는 질문의) 라운드를 최소 2~3개 돌릴 것 -- 정확히 이 항목이 한 일이고, #3/#4/#5가 개별적으로는 보여줄 수 없었던 불안정성을 드러낸 방법.
  - **서브에이전트 input/output 분할 공백은 여기서는 고칠 수 없는 진짜 한계**(Ziplex 자체 코드였던 패킹-비용 공백과 달리) -- Claude 쪽에서 정확한 달러 수치를 내려면 하니스 자체의 `<usage>` 블록이 그 분할을 노출해야 함. 이 항목에서는 깃발만 꽂고 고치진 않음.
  - 이 결과는 사용자 자신의 "이 프로젝트 아직 의미 있나" 질문(같은 세션에서, 이 항목을 설계하기 직전에 직접 물었음)을 다시 읽는 방식도 바꿈: #4/#5의 프로젝트-의존적 갈린 결과 이후 가장 유망한 미검증 효율성 방향으로 띄웠던 재사용-amortization 각도가, 적어도 godot-open-rpg에서는 제대로 측정하고 보니 실재하지 않는 프로젝트별 비용 우위에 의존하고 있었던 것으로 드러남. 이게 *다른* 프로젝트(Ziplex의 쿼리당 우위가 단일 라운드가 아니라 여러 독립 라운드에 걸쳐 실재하고 재현되는 프로젝트)에서 amortization이 통할 가능성을 완전히 배제하는 건 아니지만, amortization 주장을 세우기 전에 그 우위를 여러 라운드로 *검증*해야 한다는 뜻임 -- #4처럼 유리했던 단일 라운드 하나만으로는 근거가 부족함.

### #7 2026-09-19 — Ziplex vs repomix, 사실 조회형 질문, 진짜 도구 접근 없는 시나리오

#6 직후 사용자가 실제로 인기 있는 경쟁 도구(repomix -- GitHub ⭐28.4k, npm 월 다운로드 ~32.4만)가 같은 비용 문제를 어떻게 다루는지 물음. 조사해보니 repomix는 이 로그의 모든 이전 항목과 **완전히 다른** 시나리오를 겨냥하고 있었음: 패킹된 파일을 파일시스템/도구 접근이 **아예 없는** 컨텍스트(웹챗, 배치 API 호출)에 붙여넣는 것이지, "이미 저렴한 Grep/Read를 가진 에이전트"가 아님. repomix는 LLM 호출을 전혀 안 함 -- 순수 Tree-sitter 구조적 압축(signature/import 보존, body 제거)일 뿐, `ziplex pack --no-llm`이 이미 제공하는 것과 같은 무료 티어이고, 요약도 관계그래프도 confidence 점수도 freshness 추적도 없음. 이 항목이 처음으로 Ziplex를 repomix의 실제 시나리오에서, (#1-#6이 공유했던, 이제 명백히 틀린 비교 대상인) 도구 있는 에이전트가 아니라 repomix 자체와 직접 비교함.

- **비교 대상**: repomix(`npx repomix --compress`, 무료) vs. Ziplex 출력 3가지 형태 -- 전부 이전 어떤 항목보다 *더 엄격한* 도구-접근-없음 강제 하에 소비: 각 조건의 서브에이전트에게 오직 그 조건에 해당하는 패킹 파일 하나만 든 샌드박스 디렉터리를 줌(디스크에 다른 건 아무것도 없음), 프로젝트의 실제 이름이 내용에서 드러나더라도 Bash/Glob/Grep/WebFetch/WebSearch/git를 절대 쓰지 말라고 명시적으로 지시.
  - **조건 A1 "aif+detail"**: `aif.json`(요약/confidence/관계/rules)과 `detail.json`(압축된 본문) 둘 다 -- `pack()`이 원래 만드는 정상 분리 형태.
  - **조건 A2 "aif만"**: `aif.json`만, 압축 코드는 전혀 없음.
  - **조건 A3 "flatten"**: 분리 자체가 비용 원인인지 직접 테스트하려고 만든 새 통합 단일 파일(아래 참고).
  - **조건 B "repomix"**: `repomix --compress`, XML 파일 하나, LLM 전혀 관여 안 함.
- **Ziplex 버전**: main `caa8d6f` -- 조건 A3를 위해 라운드 중간에 만든 새 `flatten` 기능(`src/ziplex/flat_export.py`, `ziplex flatten <name>.json`) 포함.
- **사용 모델**: 모든 서브에이전트 `claude-sonnet-5`; 패킹은 `gemini-3.5-flash`.
- **분석 대상 프로젝트**: [zk-org/zk](https://github.com/zk-org/zk) 재사용, #5/#6와 동일 커밋(`1400956bfb591a4872dd6485378bf4b163d5a3f6`)으로 재클론.
- **Claude Code 사전 학습 정도**: 조건별로 완전히 새로 스폰한 `general-purpose` 서브에이전트(포크 아님), 이전 어떤 라운드와도 컨텍스트 공유 없음.
- **Ziplex 패킹 상태**: `ziplex pack ... --auto --auto-correct --ignore "docs/assets/media/**"`(`--ignore`가 `docs/assets/media/` 아래 데모 스크린샷 SVG 약 20.9만 토큰을 제외 -- 아래 repomix 실행에도 동일하게 적용해서 양쪽이 같은 파일 세트를 패킹함). 실제 패킹 비용(`usage_tracker`): 246회 요청, 입력 157,934 + 출력 28,533 = 186,467 토큰(gemini-3.5-flash 공식 요금 기준 약 $0.49). 이번엔 첫 시도부터 패킹 성공 -- #3/#4/#5의 "3전 3패 첫 시도 실패 후 재시작" 패턴과 달리, 그 실패가 결정적이지 않다는 걸 재확인.
- **repomix 실행**: `npx repomix --compress --ignore "docs/assets/media/**"` -- 466개 파일, 165,744 토큰(repomix 자체 집계), LLM 호출 전혀 없이 무료.
- **측정 지표**: 서브에이전트별 하니스 `<usage>` 블록; 정확도는 #5에서 그대로 재사용한 12문항/24점 답안지로 채점(같은 프로젝트, 같은 커밋이라 여전히 유효).
- **결과**:
  - 조건 A1(aif+detail): 130,210 tok / 21회 / 124.9s -- ~23.5/24 (repomix와 정확도 동점)
  - 조건 A2(aif만): 85,446 tok / 30회 / 139.0s -- **19/24** (실제로 정확도 손실: "Note struct 필드 5개 나열"도 "go.mod의 replace 지시문"도 전혀 답 못 함 -- 지어내지 않고 정직하게 인정했는데, 이건 답할 수 없는 질문에 대한 *올바른* 행동이지만 그래도 실제 능력 공백임)
  - 조건 A3(flatten): 193,225 tok / 17회 / 180.1s -- ~23.5/24(A2의 정확도 손실은 회복됨, raw 코드가 다시 인라인으로 들어가서 -- 근데 4개 조건 중 *가장* 비쌈, A1보다도 나쁨)
  - 조건 B(repomix): **77,748 tok** / 20회 / 123.1s -- ~23.5/24
  - **repomix가 시도한 Ziplex 변형 전부를 비용에서 이겼고**, Ziplex가 실제 코드를 포함했을 때(A1, A3)는 정확도가 같았고, 포함 안 했을 때(A2)는 정보가 확실히 더 적은데도 오히려 repomix보다 비쌌음.
- **비고**:
  - **flatten 실험이 자기 자신의 가설을 반박함.** 시작할 때의 작업가설은 "aif.json/detail.json이 두 파일로 나뉘어 있어서 낭비적인 대조가 강제된다 -- 합치면 격차가 줄어들 것"이었음. A3가 이걸 직접 테스트했는데 격차가 *더 벌어짐*(193,225 vs A1의 130,210). 진짜 원인은 다른 데 있는 것 같음: 총 정보량(repomix가 이미 갖고 있는 것과 사실상 같은 코드 *위에* 요약+폴더요약+관계그래프+rules가 더해짐)과/또는 하나의 큰(~740KB, ~20,700줄) 파일을 스캔하는 읽기당 오버헤드. `ziplex flatten` 자체는 실제로 동작하고 테스트된, 독립적으로 유용한 기능으로 코드베이스에 남겨둠(그 자체의 커밋 참고) -- 다만 원래 만들려던 해결책은 아니었음.
  - **가장 날카로운 단일 데이터 포인트는 A2(aif만)가 여전히 repomix에 진 것.** aif만은 raw 코드가 *전혀* 없음 -- 순수 자연어 요약, confidence 점수, 관계그래프, rules뿐 -- 그런데도 repomix의 실제 압축 소스보다 10% 더 비쌌고, 정답도 2개 더 적었음. 이건 **특히 사실/구조 조회형 질문에서**, 구조적 사실을 영어 산문으로 번역하는 게 그 사실 자체보다 *더 손실 많고 더 비싼* 재인코딩이라는, 이 로그 전체에서 가장 깔끔한 증거임: `class_name X extends Y`는 같은 관계를 설명하는 문장보다 더 밀도 높고 더 정밀하게 grep 가능하고, 산문을 읽어서 사실을 다시 뽑아내는 건 사실을 직접 읽는 것보다 토큰이 더 듦(A2가 tool call도 가장 많이 씀, 30회 -- signature가 공짜로 줬을 사실을 산문 속에서 더 힘들게 찾은 것과 일치).
  - **이건 #1-#6의 결과 전부를, 이 항목만이 아니라, 재해석하게 만듦.** 여섯 항목 전부 암묵적 전제("Ziplex의 요약+관계 층이 에이전트를 사실 조회에서 더 싸거나 더 낫게 만든다") 위에 서 있었는데, 이 항목의 통제되고 repomix로 벤치마크된 테스트가 이제 왜 그게 계속 실패했는지에 대한 구체적이고 메커니즘적인 설명을 제공함: 이 층은 이 질문 유형에 대해 무손실 압축이 아니라, 손실 있고 더 비싼 재포맷임. 이건 "baseline이 더 저렴했다" 그 자체보다 더 날카롭고 유용한 발견임.
  - 아직 테스트 안 됨: 이 결론이 *이* 프로젝트에 국한된 건지, 일반적으로 성립하는지 -- repomix 비교 자체는 n=1 프로젝트(다만 #1-#6을 합쳐서 보면 "요약이 사실 조회형 질문에서 진다"는 더 넓은 패턴은 세 프로젝트에 걸친 n=6 라운드).

### #8 2026-09-19 — 같은 도구, 같은 프로젝트, 사실 대신 종합형 질문 (2라운드)

#7 발견의 직접적인 후속: 자연어 요약이 raw 코드가 이미 직접 말해주는 사실을 더 손실 많고 더 비싸게 재인코딩해서 *사실* 조회형 질문에서 진다면, 반대로 *종합*형 질문 -- 어느 파일 하나도 직접 말해주지 않는 것(아키텍처, 위험 평가, "어디서부터 시작해야 하나")을 여러 파일에 걸쳐 추론해야 하는 질문 -- 에서는 이기지 않을까? 이건 정확히 폴더 요약, confidence 점수, 관계그래프가 만들어진 이유인 질문 유형이고, 지금까지 한 번도 테스트 안 됨 -- 이전 모든 항목(#1-#7)이 디버깅 아니면 사실-조회형 질문만 물었음.

### #9 2026-09-19 — 같은 종합형 질문, 이번엔 도구 접근이 완전한 Claude Code 상대 -- repomix 상대 승리가 유지 안 됨

  - 답변 품질은 둘 다 비슷했지만, 근거 스타일은 #8과 같은 방식으로 갈림: 도구-baseline 에이전트는 targeted `grep`으로 찾은 정확한 파일/줄 번호를 인용함(예: #8에서 repomix도 찾았던 것과 같은 `graph.go:90`의 `// FIXME; bad error check`, 그리고 `wc -l`로 실시간 계산한 패키지별 정확한 test-vs-impl 줄 수 비율), 반면 Ziplex의 aif만 답변은 자체 관계그래프 in-edge 수와 confidence 점수에 기댐 -- grep으로는 구조적으로 얻을 수 없는 진짜 다른 신호이지만, 이번 라운드는 소비 에이전트가 실제 파일을 직접 읽을 수 있는 상황에서는 그 신호가 비용을 정당화하지 못한다는 걸 보여줌.
- **비고**:
  - **이건 #8이 다음으로 가장 가치 있다고 스스로 지목했던 질문에 직접 답하며, 답은 "아니오"임.** repomix 상대 종합형 질문 승리(#8)는 실제 파일시스템 접근이 있는 에이전트로는 일반화되지 않음. 도구를 가진 에이전트는 `grep`/`Read`로 그 질문에 관련 있다고 판단한 파일만 선택적으로 읽지, 실제로 물어본 7문항과 무관하게 프로젝트 *전체*의 요약+폴더요약+관계그래프+rules가 들어간 Ziplex의 ~13.5만 토큰짜리 `aif.json` 전체를 컨텍스트에 올리지 않음. 이게 #1-#6의 사실 조회형 질문에서 baseline이 이겼던 것과 같은 역학이고, repomix가 아니라 도구를 쓰는 에이전트를 상대할 땐 종합형 질문에서도 똑같이 성립함이 드러남.
  - **이건 #8의 근거를 더 정밀한 것으로 좁힘.** #8은 Ziplex가 repomix를 종합형 질문에서 이긴다는 걸 보여줬음; 이 항목은 그 승리가 repomix 고유의 도구-접근-없음 프레이밍에 국한된 것이지, 파일시스템을 읽을 수 있는 어떤 에이전트를 만나도 살아남는 속성이 아니라는 걸 보여줌. #7(Ziplex는 사실 조회형 질문에서도 repomix에게 짐)과 합치면, 아홉 개 항목을 통틀어 확인된 실질적인 니치는 이제 다음과 같음: **파일시스템 접근이 전혀 없는 소비자(채팅 붙여넣기, 배치 API 호출, grep이 없는 다운스트림 도구)가 구체적으로 여러 파일에 걸친 종합/판단형 질문을 묻는 경우** -- 이 맥락에서 Ziplex는 repomix를 이기고(#8), 같은 맥락에서 사실 조회형 질문엔 repomix에게 지며(#7), 질문 유형과 무관하게 실제 도구를 쓰는 에이전트 상대로는 짐(#1-#6, #9). 이건 진짜지만 프로젝트가 시작할 때 내세웠던 "패킹하면 토큰이 절감된다"는 일반적 전제보다 훨씬 좁은 니치임.
  - **정직성 차원에서 짚어둘 것**: 도구-baseline 에이전트는 라운드2에서 Ziplex가 필요로 했던 읽기 수(24)보다 더 많은 tool call(40)을 썼는데도 전체 토큰은 더 저렴하게 끝남 -- #1-#6의 원래 발견("개별 tool call 자체는 저렴하다")과 일치함; 비싼 건 컨텍스트에 대량의 내용을 한 번에 무조건 올리는 것이고, 이게 바로 실제로 어떤 질문이 오든 상관없이 `aif.json` 전체 페이로드 하나가 하는 일이며, targeted `grep`/`Read`가 정확히 피하는 방식임.
  - 아직 테스트 안 됨: 이 결과가 다른 프로젝트 형태(godot-open-rpg 또는 cobra)에서도 성립하는지 -- 도구-baseline-대-종합형-질문 비교 자체는 여전히 n=1 프로젝트, repomix로 벤치마크한 다른 모든 항목(#7, #8)이 갖고 있던 것과 같은 한계.
