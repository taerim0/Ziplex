# Ziplex: notable decisions and bug fixes

This is the detailed "why did we end up doing it this way" record that used to live directly in `CLAUDE.md`. It's **not auto-loaded** by Claude Code — the root and nested `CLAUDE.md` files stay a lean current-state map, and this file is where the historical narrative behind non-obvious choices lives instead. Open it when the "why" actually matters for what you're about to change; skip it otherwise. Full detail for anything below (exact numbers, live-verification steps, commit-level diffs) is in git history — this file is a condensed index into that, not a replacement for it.

Organized to mirror the `CLAUDE.md` files' own structure: root-level pipeline modules first, then each nested directory.

## Root pipeline (`src/ziplex/*.py`)

- **`cli.py`'s `analyze` subcommand** used to have its own bespoke per-file summarization loop (calling `llm.analyze_file_summary()` directly, with its own separate failure string) instead of delegating to `summarizer.generate_summaries()` — a full-codebase review flagged this as violating the "cli.py is a thin dispatcher" rule, since a future fix to the shared summarization pipeline would silently miss this path. Fixed by delegating to the same function `pack()` itself uses. A related fix: a media asset used to fall through `analyze`'s loop into a "no signatures, no dependencies, skip" branch, vanishing from its summary output despite being counted in the file total — `classify_media_file()` now short-circuits it the same way `pack()` does.
- **`tokenizer.py`'s `analyze_tokens_with_payload`** used to skip a media asset entirely on the payload side (same `read_text()`-is-`None` guard used for the "original" side), silently undercounting the real packed payload that `pack --max-tokens`'s CI guard checks against — a media asset has no readable original (correctly 0 there) but its real `summary` still ships in `aif.json` and needs counting.
- **`llm.py`'s model/key resolution** used to be resolved once at provider construction, not per-call — a real bug for a GUI-only user who entered an API key but had no way to move off `DEFAULT_MODEL` short of an env var they had no reason to know about. Traced `DEFAULT_MODEL`'s (`gemini-flash-latest`) frequent 503s to it being a floating alias sitting on overloaded capacity at the time, confirmed independently via AI Studio and a pinned release returning clean 200s at the same moment.
- **Gemini's "thinking" mode** was silently on by default for the 2.5+/3.x Flash generation, billing hidden output tokens on every single-shot "JSON only" extraction call that never needed it — traced from a user's ~10x AI Studio billing jump. Confirmed directly: a trivial one-word request billed 142 of 150 tokens as hidden thinking with `thinkingConfig` unset, 0 with `thinkingBudget: 0` set. Fixed by sending that field unconditionally on every Gemini request.
- **The retry/backoff log** used to print `(attempt/max)`, which looked broken the moment a caller's own retry chain (a batch request exhausting its retries, handing off to a per-file fallback) started a *new* counter from `(1/N)` again — read as if the loop ignored its own stated limit. Replaced with a capped wait time (`min(5*(attempt+1), 50)`, no counter) and a `[label]` naming which item is retrying, since a failing pack previously gave no indication of which file was the problem.
- **`llm.py`'s transport-level exception handling** (`RequestException`/`JSONDecodeError`) and the explicit `timeout=REQUEST_TIMEOUT` (60s) were both added after real incidents: a network blip left `pack()` crashing uncaught past every caller's checkpoint-on-failure path; a firewall silently dropping a connection (no default `requests` timeout) left a GUI pack looking frozen forever, with no retry log at all.
- **`_IDENTIFIER_FIDELITY_NOTE`** (the "keep identifier names untranslated" prompt instruction) was added after packing this same repo scored ~17 low-confidence files in English but ~63 in Korean — `confidence.py`'s word-overlap heuristic only finds a match "for free" when the summary's language and the identifiers' language are the same. Narrowed the gap significantly but didn't close it; see `confidence.py`'s own note below and the open GitHub issue for why a full fix isn't straightforward.
- **`checkpoint.py`'s `<hash>` filename suffix** replaced a bare `<project_name>.json`, which let two different projects sharing a folder basename silently overwrite each other's checkpoint (non-interactive callers never got a resume-vs-discard prompt to catch it).
- **`checkpoint.py`/`freshness.py`'s `lang_matches`/language-aware cache rejection** were both added the same day a code review caught the same self-contradiction class twice: a resumed checkpoint's restored `rules`/`prompt`/summaries, and a reused previous-pack summary, could each end up written in a *different* language than the `project.language` field claiming to describe them, if a run's `--lang` differed from the interrupted/previous one.
- **`summarizer.py`'s per-file `✅`/`❌` log** used to print `✅` unconditionally regardless of whether the summary was real or a failure placeholder — a placeholder-substituted failure looked exactly like a success in the pack log, with nothing pointing at the one place (`correct_aif()`'s review) meant to catch it.
- **`packager.py`'s `use_llm=False` + checkpoint interaction**: a checkpoint's restored `rules`/`prompt` used to be read before the `use_llm` check, so retrying `--no-llm` on a project whose earlier `use_llm=True` run had gotten as far as inferring real rules shipped an `aif.json` with real rules sitting next to a prompt asserting no LLM inference ever happened. Fixed by gating both restores on `use_llm` itself.
- **The "⚠️ 민감 파일 제외" pack-log line** used to be sourced from a CLI-only `included_anyway` variable that a GUI/`preselected` caller never populated — a user who checked a dangerous file's "include anyway" box in the GUI still saw it listed as excluded in the log, even though `security_scan`'s own count (computed against the final `selected` list) was already correct. Fixed by moving the print to use the same `selected`-based computation.
- **`freshness.freshness_candidate_files()`** was added after a real bug: a file flagged sensitive but included anyway (via `review_dangerous_files()`, the GUI checkbox, or `preselected`) still has a genuine manifest entry, but re-scanning always re-flags it as dangerous regardless — every freshness caller used to pass only `scan_result["safe"]`, so such a file was reported as permanently `removed` forever, even unchanged and on disk.
- **`freshness.check_freshness_scoped()`** consolidated four independent call sites (the `freshness` CLI subcommand, `query_service.check_freshness()`, `query_service._stale_warning()`, `gui/watcher.py`'s recompute) that had each open-coded the same `collect_and_scan → freshness_candidate_files → check_freshness` sequence — a code review flagged this duplication as exactly what let the `freshness_candidate_files()` fix above land cleanly in one call site while a second, independent copy of the bug went unnoticed in `_stale_warning()` until reported separately (symptom: a GUI project briefly showed "changed" for a previously-included dangerous file on load, self-correcting a moment later once the already-fixed live watcher caught up).
- **`analyze_prompt()`'s always-empty `architecture` parameter**: an external user testing the GUI's project-understanding tab reported difficulty understanding a project from it. Traced to `packager.py` always calling `analyze_prompt(architecture=[], ...)` -- a dead parameter, never populated anywhere, meaning the AI guide's only real inputs were the project name and a list of coding-style rules (naming conventions, etc.). Structurally guaranteed to read like a style blurb rather than a "what is this project" summary. Fixed by building real architecture context (`_build_architecture_summary()`: tech_stack plus every file's own already-generated summary, capped at `MAX_ARCHITECTURE_FILES`) and by making the prompt instruction itself explicit that the summary should focus on purpose, not style. Verified directly against the real Gemini API on `testfiles/webdev-project`: before, effectively untested since `architecture` had never been populated; after, a genuine "this project is a full-stack web app... solving the problem of managing user data" summary. Same investigation added `folder_summary.py` (one sentence per folder describing its role, `aif["folders"]`) as a second, complementary fix for the same reported gap -- a single best-effort batched LLM call, deliberately not wired into the checkpoint/resume system rules/prompt/per-file summaries all get (see that module's own docstring for the reasoning).
- **`confidence.py`'s cross-language limitation**: manually inspecting real low-confidence flags (both English and Korean, via the real Gemini API) showed the flagged files were almost always *accurate* summaries — the heuristic can't tell "no overlapping words" apart from "abstracted well," and a non-English summary abstracts into genuinely different vocabulary with essentially no chance of literal overlap. Explored and rejected: lightweight multilingual embedding models (too heavy a dependency for this project's scope), existing EN-KO IT dictionaries (too noisy, not CS-specific), and a hand-curated EN-KO CS-vocabulary glossary + substring matching (implemented and validated — worked well for generic tooling code, but a large share of what Ziplex packs has domain-specific identifiers, like a game mod's `spawn_enemy`, that no shared glossary could ever cover). Tracked as an open GitHub issue rather than shipped as a partial fix.

## `extract/code/` — Tree-sitter extraction & compression

- **Go/Rust/C#/PHP/Ruby** were added from a shortlist after noticing `tech_stack.py` already detected their manifests (`go.mod`/`Cargo.toml`/`composer.json`/`Gemfile`) while `extract/code` had zero grammar support for any of them — real code in those languages was passing through completely uncompressed.
- **C++'s `_unwrap_declarator()`** was the first genuinely new extraction mechanism needed beyond a `languages.py` config entry — this grammar nests a function's name/parameters one level inside a `"declarator"` sub-node. Adding it surfaced a real regression: the C++-specific `"type"` return-type field check initially applied unconditionally, silently appending `-> int`-style suffixes to every Java signature too (Java's own `method_declaration` also has a field named `"type"`) — no test asserted the *absence* of a suffix for Java, so this shipped unnoticed until a code review caught it. Fixed by gating the check on `sig_node is not node` (structural evidence an unwrap happened, not a language-name check).
- **C++ also surfaced `file/relationship.py`'s `build_stem_map()` bug** (see that module's own history entry) — a header/implementation pair sharing a stem is common in C/C++ but no earlier language ever exercised two collected files sharing an exact stem.
- **Rust's `mod_item` dependency handler** initially matched every `mod_item` unconditionally, which both emitted a bogus dependency for an inline `#[cfg(test)] mod tests { ... }`'s own name *and* stopped recursion before ever seeing the real `use`/`mod` declarations nested inside it. Fixed by gating on an *absent* `"body"` field (a real submodule declaration has none; an inline module does). A second bug in the same handler's `use`-path splitting: alias-stripping ran before checking whether the argument was actually a `{...}` group, truncating a group containing an aliased sibling (`use foo::{bar as baz, qux}`) mid-string and silently dropping `qux`.
- **C#'s `using`-path resolution** initially searched the whole node for an identifier/qualified_name child unconditionally, which meant a type alias whose right-hand side isn't itself an identifier (`using MyInt = int;`, `using IntArray = int[];`) found nothing after `"="` and silently fell back to matching the *alias name itself* as a bogus dependency. Fixed by scoping the search to children after `"="` specifically for the aliased form.
- **Python's stdlib-import misresolution**: a plain `import json` anywhere in Ziplex's own repo was wrongly resolving as an internal dependency on `extract/text/json.py` (a same-named local file), inflating its apparent in-degree to 27 and — combined with a GUI dependency-tree rendering bug (see `gui/AGENTS.md`'s history) — hanging the review screen outright when packing Ziplex's own repo. Fixed with `_is_stdlib_import()`, checked against the running interpreter's own `sys.stdlib_module_names`.
- **TS/JS arrow functions** were completely invisible to both signature extraction and body compression before `function_types` grew to include `arrow_function`/`function_expression` — a real, confirmed gap, since arrow functions are the dominant way modern JS/TS is actually written.
- **GDScript's `constructor_definition`** (`_init`) was an accepted gap in the original GDScript support commit (its grammar gives it no `"name"` field at all) until `implicit_names` existed as a clean, non-language-hardcoded mechanism to fix it properly.
- **Java's `field_handler` (call-initialized class-level fields)**: motivated by a real, previously-documented gap -- a registry-style class's *actual* primary behavior (defining constants via a factory call, e.g. `RUBY_TOOL = register(...)`) lives in field declarations, invisible to `method_declaration`-only extraction. Live-reproduced and closed against the exact real fixture that originally surfaced it (`testfiles/game-mod-project`'s `ModItems.java`): its real, accurate historical Gemini summary scored confidence 0.33 (below `REVIEW_THRESHOLD`, falsely flagged for human review) using only the one incidental helper method Tree-sitter had ever captured; 1.0 once field registrations were included. Two real bugs caught by code review before this shipped, both from the same root cause (a second, separate tree traversal appending field entries only *after* every method signature, regardless of actual source order): (1) a field registration declared after 10+ methods could be silently pushed past `corrector.py`'s/`summarizer.py`'s fixed-count display caps; (2) an early "fully handled" return on a matched `field_declaration` skipped a legally-nested one inside an anonymous class body's own initializer, reproducing the exact same low-confidence bug one syntactic layer deeper. Fixed by merging field detection into `extract_signatures()`'s existing single traversal (document order, no separate pass) rather than patching either symptom at its own call site.

## `extract/text/` — non-Tree-sitter compressors

- **`yaml.py`'s round-trip design** (vs. a naive PyYAML parse-and-redump, `json.py`'s own approach) was chosen after live-reproducing YAML 1.1's implicit scalar typing corrupting real values — an unquoted `3.10` became the float `3.1`, `NO` became `False` (the "Norway problem," a real GitHub-Actions-`python-version` gotcha).
- **The `<<: *anchor` merge-key bug**: `_compress_value()`'s in-place mutation initially made ruamel treat an already-merged-in key as newly explicit the moment its (unchanged) value was reassigned, duplicating every merged key in every service of a real `docker-compose.yml` fixture. Fixed by skipping any key listed in a map's own `.merge` attribute.
- **The shared-object aliasing bug**: a plain `*alias` referencing a whole list/map is the *same Python object* as its `&anchor` in ruamel's round-trip mode, not a copy — without a visited-object guard, a shared container got mutated (and its own truncation marker mis-read as real data) twice, understating how much was actually elided. Fixed with a per-call `_seen` set of `id()`s.

## `file/` — collection, security scan, selection, dependency graph

- **`is_media_file()` vs. `classify_media_file()`**: originally one gate — a real code review caught two consequences of conflating a cheap extension check with a strict content-verified one: `scanner.py` skipped secretlint scanning entirely for anything merely carrying a media extension (a real security gap — a secrets file renamed to `.mp3` would ship unflagged), and `packager.py` replaced a real Git-LFS-pointer file's actual text content with a bogus metadata-only summary instead of ever reading it.
- **`_jpeg_dimensions()`'s marker-skip range** was `0xD0`-`0xD8` before a review caught `0xD8` (SOI) folded in incorrectly, which would misparse a concatenated/malformed JPEG whose embedded SOI reappears mid-stream.
- **`build_stem_map()`'s single-file-per-stem bug**: mapped a stem to one file name, so two files sharing a stem (a header/implementation pair, first exercised by adding C++ support) let whichever was collected last silently overwrite the other's entry — the other file became permanently unresolvable as an import target. Fixed to map a stem to every file sharing it, with `_pick_candidate()` preferring a header extension on a genuinely ambiguous bare-stem match.
- **`has_cycle()`'s traversal direction** was inverted for a while before a test walking a 3-file transitive chain (`z→y→x`, moving `z` under `x`) caught an undetected cycle — the walk has to start from `from_file`, not `to_file`, since `move_file()` is about to add the edge in the *other* direction.
- **`build_tree()`'s self-reference handling**: a file resolving a dependency back onto itself used to land in `external` instead of being dropped entirely — the existing test asserting this, despite its name, never actually checked the `external` side.

## `gui/` — local GUI

- **The in-app pack-job navigation guard** went through several rounds of real user feedback and code review before landing on its current shape:
  1. First version: warned before leaving a "running"/"reviewing" job, but a "running" job could still be left running unsupervised in the background with no way to find it again. User feedback: leaving should *always* stop it.
  2. Same feedback round: `window.confirm()`'s native dialog couldn't offer more than OK/Cancel, needed for the 3-way save/discard/stay choice — replaced with `showConfirmModal()`, an in-page themed dialog.
  3. That rework surfaced a real regression in the *original* guard, missed by its own testing: a declined Back-navigation attempt was calling `route()` unconditionally on the "settling" hashchange, which for the pack-job route silently wiped out in-progress "reviewing" form edits. Fixed by making that case a pure no-op.
  4. Two separate code-review passes (one on the original guard, one on the modal rework) each caught four more real issues: the guard never clearing itself after a confirmed leave (causing a still-ticking `poll()` loop to re-nag on every later click); the guard only covering clicks, not Back/Forward; the guard arming before the first status poll ever resolved; a `poll()` request in flight during a "stop" decision still landing and re-arming the guard; no re-entrancy protection against a fast double Back-press; the modal missing `role="dialog"`/focus management; and a Back-navigation revert using a plain `location.hash =` assignment (which pushes a spurious history entry) instead of `history.replaceState()`.
- **The dependency-tree overview's `seen`-set dedup**: originally guarded only against a *true cycle* on the current branch (`ancestors`), not a file legitimately shared by many different dependents — a widely-shared file's entire subtree re-expanded in full at every reference, compounding at each level. Combined with the Python stdlib-import bug above (which inflated one file's in-degree to 27), this hung the GUI review screen outright when packing Ziplex's own repo. Fixed with a second, flat `seen` set shared across the whole tree render — a file's subtree expands once, anywhere; every later reference renders as a shallow "already shown" row. A follow-up review caught the same check missing from the top-level *root* loop itself, so a fully-cyclic component with no natural root (two files mutually importing each other) still double-expanded once.
- **The freshness-badge detail**: originally a bare count ("⚠️ 3개 변경"), then a hover-only `title` tooltip listing real filenames, then upgraded again to a real clickable/keyboard-operable `<button>` + detail panel after a user flagged the tooltip itself as an accessibility gap (invisible to keyboard/touch users).
- **The dangerous-file review UX**: a flagged file's own explanatory line and separate select-all checkbox were added after direct user feedback that the section lacked any explanation of what checking a box actually does, had no way to bulk-include reviewed files, and had checkboxes with too small a hit target. A follow-up code review caught the new dangerous-list select-all syncing two-way (reflecting individual unchecks) while the pre-existing safe-list one only ever synced one-way — fixed by bringing the safe list up to the same two-way behavior.
- **The Files page's flat-table-to-folder-tree redesign**: reported alongside the `analyze_prompt()` architecture bug above (same external-user feedback session) -- the Files page was a flat, sortable table with zero directory-structure signal at all, compounding the difficulty of understanding a project from the GUI. Redesigned as a collapsible folder tree reusing `graph.js`'s existing `<details>`/`.tree-node` CSS rather than inventing a parallel component. First version showed each nested folder's *full path* as its label (`backend/services`, `frontend/src/api`, ...) instead of just its own name -- redundant with the visual nesting already showing ancestry, and (worse) the main cause of ugly mid-word-wrapped rows once a folder's own summary text was appended alongside a long path. Fixed to show only the last path segment. That fix then surfaced the real underlying CSS issue: `.tree-name`'s `overflow-wrap: anywhere` (needed by the *dependency* tree for a genuinely long lone name with nothing else in the row) was letting a folder/file name wrap mid-word rather than the trailing summary text wrapping instead, once a row had both a name and a long appended description. Fixed with two new, additively-scoped classes (`.tree-name-fixed`, `.tree-desc`) rather than changing the shared `.tree-name` class's own behavior, which would have risked regressing the dependency tree's original long-lone-name case.
