# Ziplex 전면 재점검 — 성능 · 방향성 분석 및 재설계 (2026-10-14)

HEAD `7340765` (v0.5.0) 기준. 서브에이전트 5개가 역할을 나눠 작업했습니다.

| 역할 | 결과물 |
|---|---|
| 런타임 성능 | 실측 + cProfile (Ziplex / hono / scrapy / django) |
| 제품 효과성 | EXPERIMENTS #1–#14 재분석, 출력물·MCP 실측, held-out 그래프 정확도 검사 |
| 경쟁·연구 조사 | 경쟁 도구 25개 이상, 관련 논문·벤치마크 |
| 아키텍처·범위 | LOC·커밋 분포, 구조 결함, 테스트 상태 |
| 설계 종합 | 위 네 가지를 묶은 재설계안과 로드맵 |

실제 LLM은 호출하지 않았습니다(`--no-llm` 또는 mock). 핵심 주장 일부는 직접 다시 확인했습니다. 근거 데이터와 스크립트는 세션 scratchpad의 `perf/`, `value/`, `arch/`에 있습니다.

## 1. 결론

**"성능이 아쉽다"는 평가에는 원인이 두 가지 섞여 있습니다.**

1. **실행 속도.**
   - 중소형 저장소에서는 괜찮습니다. 약 100 files/s 수준입니다.
   - 대형 저장소에서는 무너집니다. django(5,691 파일)가 224초, 668MB였습니다.
   - 원인은 대부분 **사소한 구현 버그**이고, 두세 개만 고치면 약 50초까지 내려갑니다.
2. **제품 효과.** "AI 에이전트가 더 잘하고 싸고 빨라지는가"의 문제입니다. 이건 구조적인 원인이라 더 심각합니다.
   - 14번의 실험 동안 **LLM 요약·규칙·가이드는 도구를 쓰는 에이전트를 한 번도 이기지 못했습니다.**
   - 정확도는 모든 라운드에서 동점이었습니다. Ziplex가 답을 더 정확하게 만든 적은 없습니다.
   - 반복해서 이긴 것은 **LLM 없이($0) 만드는 해석 완료 다언어 의존성 그래프** 하나뿐이었습니다. 시간과 도구 호출은 17–65% 줄었고, 모노레포에서는 토큰도 35% 줄었습니다.

**"방향성이 불확실하다"는 평가는 정확합니다.**
- 코드·문서·README·노력은 모두 "LLM 요약 컨텍스트 파일"에 맞춰져 있습니다.
- 반면 증거는 "그래프" 쪽을 가리킵니다.
- 그래프는 지금 요약 파이프라인의 부산물입니다. `edits.finalize_aif()`에서 사후에 만들어지고, 심볼·라인 정보는 버려지며, 매번 처음부터 다시 만듭니다.

**제안 방향 (B on A):**

> "이 파일을 바꾸면 누가 영향을 받고, 어떤 테스트를 돌려야 하는가"를 Python/TS/JS/Go 저장소에 대해 설정 없이, 실제 툴체인처럼 해석해서, 에이전트나 CI에 한 번의 호출로 답한다.

- LLM 요약은 선택 기능(`ziplex enrich`, `[llm]` extra)으로 내립니다.
- 게임 모드 언어 지원은 유지하되 포지셔닝 축으로 쓰지 않습니다.

### LLM 경로

- **폴더 요약이 상한 없는 단일 호출입니다.** django는 프롬프트가 약 255K자인데 `REQUEST_TIMEOUT=60s`(`llm.py:29`)라서 타임아웃 후 재시도가 반복될 가능성이 높습니다. 추정치입니다.
- **rules 프롬프트가 58K자입니다.** signatures를 `repr`로 그대로 덤프하기 때문입니다.
- rules → guide → folders가 직렬로 실행됩니다.

### 문제없는 부분

- 그래프 쿼리(ms 단위), 시작 시간(0.4s), 중형 저장소 메모리, 요약 캐시.

## 3. 제품 효과성 진단

### 3.1 실험 #1–#14가 말하는 것

| 주장 | 결과 |
|---|---|
| 패킹하면 토큰이 절약된다 | **기각** (#1–#6, #9) |
| 한 번 패킹해서 재사용하면 비용이 회수된다 | **기각** (#6: 패킹 $1.16, 쿼리당 이득 없음) |
| 요약이 사실 확인 질문에 유리하다 | **기각** (#7: repomix보다 +10~148% 토큰, 정확도도 손실) |
| 요약이 종합 질문에 유리하다 | 도구 없는 붙여넣기에서만 성립 (#8). 도구가 있으면 역전 (#9) |
| 해석된 그래프로 시간·도구 호출이 준다 | **유지** (#10–#14 모두) |
| 해석이 어려운 저장소에서 토큰이 준다 | **유지** (#12 −35%, #14 −16% vs depcruise+grimp) |
| 다언어 그래프 하나가 언어별 도구 묶음보다 낫다 | **유지** (#14). Ziplex 고유의 유일한 증거 |

**방법론상 약점:**
- 측정 대상 저장소에서 resolver를 먼저 고친 뒤 측정했습니다. held-out 저장소가 없습니다.
- 표본이 작고 모델은 하나뿐입니다.
- 그래프 쪽에만 "그래프를 먼저 써라"라고 지시했습니다.
- **실제로 배포한 MCP 채널은 한 번도 측정하지 않았습니다.** Python 원라이너로만 측정했습니다.

### 3.2 외부 연구도 같은 방향

- **AGENTS.md 평가 연구** (ICLR 2026, arXiv 2602.11988): LLM이 생성한 컨텍스트 파일은 성공률을 약간 낮췄고 비용을 20% 이상 늘렸습니다.
- **그래프 인덱스 연구**: 강한 grep 에이전트와 비교하면 도구 호출과 시간은 줄이지만 토큰과 정확도는 거의 개선하지 못했습니다. 효과는 다중 파일 변경, 저장소 크기, 해석 난이도에 비례했습니다.
- **에이전트는 라우팅하지 않으면 그래프 도구를 무시합니다.** nefayran 벤치마크, repowise 비교, 그리고 Ziplex 자체의 #10 pilot 모두 같았습니다.

### 3.3 지금 실제로 나가는 출력물의 문제

- **그래프 정확도 (held-out으로 확인):**
  - mcp SDK는 376/384였습니다. resolver 버그 2개가 있었습니다. 같은 파일에서 하위 모듈도 import하면 `__init__` 재export edge(`from mcp.server import Server`)가 누락됩니다.
  - 나머지 6개 누락은 스캐너가 제외한 파일 때문이었습니다.
- **스캐너가 그래프를 깎습니다.**
  - 가짜 크리덴셜이 들어 있는 테스트 파일 10개를 통째로 제외했습니다. 직접 재확인했습니다.
  - 그 결과 Ziplex의 Python edge 244개 중 **41개(17%)가 소실**됐습니다.
  - `get_dependents(query_service.py)`는 실제 7개 중 2개만 반환합니다.
- **산문 언급(text ref)이 기본값으로 섞여 있습니다.**
  - `blast_radius(query_service.py)`가 32개를 반환하는데, 그중 약 27개가 README, AGENTS.md, `.gitignore`입니다.
  - 기본값도 도구마다 다릅니다.
- **no-LLM 요약은 거의 쓸모가 없습니다.** 소스 순서대로 앞쪽 시그니처만 나열해서 private 헬퍼가 공개 API를 밀어냅니다. 그런데도 aif.json 토큰의 60%를 차지합니다.
- **confidence는 no-LLM에서 항상 1.0**이라 아무것도 측정하지 않습니다.
- **MCP 도구 10개의 정의가 약 5K 토큰**이고, 등록만 해도 매 세션 지불합니다. 설명문에 개발 히스토리까지 들어 있습니다. 이 비용이 그래프로 얻는 이득과 같은 규모입니다.
  - 유지할 가치가 있는 도구는 `get_graph_summary`, `get_dependents`, `get_blast_radius` 정도입니다.
  - `search_project`, `get_detail`, `list_files`, `get_folders`는 Grep/Read와 겹칩니다.

## 4. 아키텍처 진단

**규모:**
- src 16.1K줄 중 실제 코드는 6,978줄이고, **주석·docstring이 7,091줄**로 더 많습니다. 대부분 경위를 설명하는 서술형입니다.
- 에이전트 문서가 185KB이고, `src/ziplex/AGENTS.md` 하나가 57KB(약 14K 토큰, 자동 로드)입니다. 토큰을 줄이자는 제품으로서는 아이러니입니다.

**노력 배분:**
- 커밋 384개 중 **43%가 AGENTS/CLAUDE.md를 수정**했습니다.
- GUI 85개, LLM/리뷰 66개, **그래프 resolver 44개**이고, resolver 작업은 맨 마지막(09-26/27)에 몰려 있습니다.

**구조 결함:**
1. **그래프가 요약 파이프라인의 부산물입니다.**
   - `edits.py:95`에서 사후에 생성되고, `:97-101`에서 signatures / api / dependencies가 폐기됩니다.
   - 그래서 심볼, specifier, 라인, provenance가 없습니다.
2. **`pack()`이 543줄짜리 god function입니다** (`packager.py:844-1386`). 파라미터 13개 중 상당수가 GUI 전용(checkpoint / cancel)입니다.
3. **`summarizer.py:115`의 프롬프트 분기 때문에 text-ref merge 우회 코드가 필요합니다** (`packager.py:1148`, `1303-1315`).
4. **그래프 파이프라인이 `cli._cmd_tree`(`cli.py:683-719`)에 중복**되어 있고, 이미 내용이 갈라졌습니다(세 번째 drift).
5. **편집 API 2벌, 리뷰 UI 2벌**이 있습니다(`corrector.py`, `pack_service`).
6. **증분 처리가 전혀 없습니다.**
7. **레이어 위반:**
   - `llm.py`가 GUI 설정을 읽습니다.
   - 스캐너가 GUI 언어로 지역화되어 있어서 캐시 키에 언어가 들어갑니다.
   - `pack_service`가 진행 상황을 얻으려고 stdout을 전역 락으로 가로챕니다.
8. **테스트가 hermetic하지 않습니다.**
   - `tokenizer.py:29`의 tiktoken이 캐시가 비어 있으면 네트워크로 다운로드합니다. 그래서 GUI pack 테스트 4개가 10초 타임아웃으로 실패합니다.
   - `test_pack_integration`의 84개 테스트 중 그래프 테스트는 1개뿐입니다.
9. **AGENTS.md가 존재하지 않는 `python src/cli.py`를 안내합니다.**

## 5. 목표 설계

### 5.1 패키지 구조

```
src/ziplex/
  core/        content.py(1회 읽기) collect.py scan.py(사유 코드, 지역화 없음) languages.py
               parse.py(단일 트리 순회 → imports/symbols/exports)
               resolve/{context,generic,python,ts,go,textref,tests}.py
               index.py(SQLite, 유일한 writer) graph.py(순수 알고리즘) diff.py(git) api.py
  enrich/      llm, providers, summaries(content hash 키, enrich.db), rules   ← [llm] extra
  export/      aif.py(v1 호환 뷰) compress/ skill.py flat.py
  cli.py  mcp_server.py(도구 5개)  hook.py  gui/(읽기 전용, [gui] extra)  dev.py
```

- **core 의존성:** tree-sitter, pathspec, mcp
- **`[llm]` extra:** requests, dotenv, tiktoken
- **`[gui]` extra:** flask, pywebview, watchdog
- **레이어 규칙은 import 검사 테스트로 강제합니다.** core는 enrich, export, gui, cli, settings, i18n을 import하지 않습니다.

### 5.2 인덱스 (`<project>/.ziplex/index.db`, 폐기 가능한 캐시)

| 테이블 | 담는 내용 |
|---|---|
| `files` | path, hash, lang, kind, is_test, flag_code, parse_status |
| `symbols` | file, name, kind, line, exported |
| `imports` | **import 문 단위**: specifier, kind(import/reexport/dynamic/type_only/text_ref…), names, dirty |
| `probes` | 해석 시도가 조회한 모든 키(`path:` `stem:` `pymod:` `gopkg:` `base:`). 실패한 조회도 기록하고, 무효화의 근거가 됨 |
| `edges` | src, dst 또는 external, **method**, **tier** (`certain` / `heuristic` / `mention`) |
| `text_tokens`, `context_files`(tsconfig, go.mod, workspace 해시), `scan_cache`, `meta` | — |

요약은 별도의 `enrich.db`에 둡니다. 인덱스를 다시 만들어도 비용을 들인 요약은 남습니다.

### 5.3 증분 갱신

1. stat 비교 → hash 비교
2. resolver 컨텍스트(tsconfig, go.mod, workspace, `.ziplex.json`)가 바뀌었으면 전체 import를 dirty로 표시합니다. 재파싱 없이 재해석만 하므로 1초 미만입니다.
3. 파일 삭제: 그 파일을 가리키던 import와 해당 probe를 dirty로 표시합니다.
4. 파일 추가: probe 키가 일치하는 import를 dirty로 표시합니다. 이전에 external/stem으로 처리됐던 import가 정확한 edge로 승격되는 경로가 여기입니다.
5. 변경된 파일만 파싱
6. dirty import만 재해석
7. 1 트랜잭션으로 커밋하고 generation 증가

**안전장치:**
- "증분 결과 ≡ 전체 재빌드" 속성 테스트(무작위 시퀀스 500개)를 Phase 2의 게이트로 둡니다.
- 의심스러울 때 `ziplex index --verify`로 확인할 수 있게 합니다.

### 5.4 정확성 정책

- **edge tier:**

| tier | 의미 | 기본 포함 여부 |
|---|---|---|
| `certain` | 툴체인과 동일하게 해석됨 | 포함 |
| `heuristic` | stem/suffix 추정 | 포함하되 `?` 표시 |
| `mention` | 산문 언급 | **모든 쿼리에서 기본 제외** |

- **스캐너 정책 전환:** 스캐너는 "그래프에 넣을지"가 아니라 "내용을 노출할지"만 결정합니다.
  - flag된 파일도 경로, import, 심볼 이름은 인덱싱합니다.
  - 본문, 요약, detail, 스니펫, LLM 프롬프트에는 절대 넣지 않습니다.
  - 그대로 제외하고 싶은 사용자를 위해 `.ziplex.json`에 opt-out 옵션을 둡니다.
- **Python import 문 단위 처리:** mcp SDK 재export 버그를 해결합니다.
- **심볼 단위 질의:** "누가 이름 X를 쓰는가"를 재export 체인(barrel, `__init__`)을 따라가며 질의 시점에 계산합니다.

### 5.5 MCP v2 — 도구 5개, 정의+지침 1K 토큰 미만

```
graph_overview(scope="")                         저장소/폴더 레이어링, 허브, 순환, 미해석 핫스팟
who_depends_on(files, depth=1, symbol="", include_mentions=false, limit=60)
dependencies_of(files, external=false)            라인 번호 포함
impacted_tests(files=[], diff="")                 diff: worktree|staged|HEAD~1|main...  → 바로 실행할 pytest/jest/go test 명령 포함
dependency_path(source, target)                   최단 import 체인 + 각 hop의 라인
```

- 응답은 JSON 대신 압축된 줄 단위 텍스트로 바꿉니다. 토큰이 약 40–50% 줄어듭니다.
- 매 호출마다 `ensure_fresh()`를 실행해서 수동 freshness 개념을 없앱니다.

### 5.6 라우팅 — 에이전트가 실제로 쓰게 만들기

- `ziplex install claude [--hook] [--dry-run]`: MCP 등록에 더해 선택적으로 `PostToolUse(Edit|Write)` 훅을 설치합니다.
- `ziplex hook post-edit`의 동작:
  - 편집한 파일 하나만 증분 갱신합니다.
  - "의존자 N개 / 영향받는 테스트 M개 → `pytest ...`"를 출력합니다.
  - 삭제된 export를 아직 import하는 곳이 있으면 ⚠로 경고합니다.
  - 세션·파일당 한 번만 출력하고, 차단하지 않으며, 300자 미만, 0.7초 미만을 목표로 합니다.

### 5.7 CLI v2

| 구분 | 명령 |
|---|---|

## 10. 솔직한 위험

- **"검증된 해석" 주장은 아직 튜닝하지 않은 저장소에서 입증되지 않았습니다.** F1이 첫 관문입니다.
- **에이전트가 도구를 무시하는 문제는 업계 공통입니다.** 훅이 최선의 대비책이지만, 출력 빈도 조절을 잘못하면 소음이 됩니다.
- **probe 키 기반 증분 무효화에서 미묘한 stale 버그가 생기기 쉽습니다.** 속성 테스트를 생략하면 안 됩니다.
- **Phase 3는 코드베이스의 약 절반과 지금까지 노력의 대부분을 걷어냅니다.** 증거상 옳은 결정이지만, 릴리스 노트에 분명히 써야 합니다.
