# Experiment log — model / retrieval-approach comparisons

**English** | [한국어](EXPERIMENTS_ko.md)

Ad-hoc comparisons of ways to answer questions about *this or any target
project* -- Claude Code alone vs. Ziplex MCP/Skill, different LLM
providers/models, different `aif.json` packing settings. Deliberately not
called "benchmarks": there's no fixed, repeatable test suite here, and each
round's setup (which model, which project, how much prior context the
"alone" side already had) differs enough that two rounds are only
comparable once you've actually read what each one controlled for. Never
auto-loaded (same convention as `docs/HISTORY.md`) -- open it before
deciding which approach/model to use, or before running a new comparison
round, so a new round can reuse a prior one's project/setup where that
matters.

## Why this exists

A round's *conclusion* ("Ziplex was cheaper") is worth almost nothing on its
own a few months later without the conditions that produced it -- same
model on both sides? same project, actually packed how? had Claude Code
already seen this codebase earlier in the conversation (which would make
"alone" look artificially strong)? This file exists so that context isn't
lost the way it would be if only a one-line takeaway got written down.

## Known gap: packing cost isn't counted anywhere (entries #2-#5)

**Fixed for future rounds (main `27384c1`)**: `llm.py`'s `usage_tracker`
now captures every real provider's own billed input/output tokens
straight off each response (Gemini's `usageMetadata`, OpenAI's/Claude's
`usage` field); `pack()` resets it once per run and `cli.py`'s `pack`
subcommand prints the snapshot right after the existing "토큰 분석" block.
The dollar-normalization problem below is still unaddressed (this only
reports raw token counts per provider, not a cross-provider $ total), and
entries #2-#5 below were already run before this existed, so their own
packing cost is still unrecorded and can't be reconstructed without
re-running each pack. A #6+ round should capture and report this number
going forward.

Every entry from #2 onward excludes the cost of *producing* the pack
(`ziplex pack ... --auto --auto-correct`, real Gemini API calls) from
Condition A's measured cost -- explicit in each entry's own notes ("this
happened before either subagent was launched and is not counted"). That
convention is deliberate for measuring "given a pack already exists, is
querying it worth it," but it silently hides the real total cost of a
one-off, never-reused pack, which is the actual scenario every entry so
far has run (a fresh pack, used exactly once, then thrown away with the
rest of the temp clone).

What's recorded per entry is the *packed artifact's size* (`ziplex`'s own
"토큰 분석"/token-analysis line, e.g. "GPT-4o: 168,711 → 3,501") -- that's
original-file-tokens vs. compressed-output-tokens, a measure of how small
the artifact ended up, **not** how many tokens Gemini's API actually
billed across the batched summarization calls that produced it (which
includes every batch's full input -- signatures, dependencies, truncated
content -- not just the final summary text). `llm.py` doesn't currently
capture or log Gemini's own `usageMetadata` (prompt/candidates/total
token counts) anywhere, so that real number was never recorded for any of
entries #2-#5's packs and can't be reconstructed after the fact without
re-running the pack.

There's also a unit-mismatch problem waiting even if that number existed:
packing spends Gemini tokens, querying spends Claude Sonnet tokens, and
the two aren't priced the same -- a fair "total real cost" comparison
needs dollar-normalization, not a raw token sum across providers.

Not yet fixed as of this note. The straightforward fix (log Gemini's real
`usageMetadata` per call, sum it across a pack run, print it alongside the
existing token-analysis block) is a real, valuable addition to `pack()`
itself, independent of this experiment log -- tracked as a follow-up, not
done here.

## How to add an entry

Copy the template block below into a new `### #N YYYY-MM-DD <short title>`
entry, fill in every field (write "n/a" rather than deleting a field you
didn't vary), and add a matching row to the summary table so the log stays
skimmable without opening every entry. Record raw numbers (token counts,
turn counts, pass/fail) in the entry -- "Ziplex was cheaper" with no number
isn't reusable later, and can't be re-checked if a later round's result
seems to disagree with it.

Keep this file and `EXPERIMENTS_ko.md` in sync -- add the same entry to
both (translated, not just copy-pasted English into the Korean file or
vice versa) rather than letting one drift ahead of the other.

### #2 2026-09-16 — Ziplex-packed context vs. Claude Code alone, on a real large external project

- **Compared**: Condition A "Ziplex-assisted" -- given an already-generated Ziplex pack (`aif.json`/`detail.json`/`cache.json`) for the target project plus the `ziplex` CLI, told to use both as the primary way to understand the codebase before falling back to raw Grep/Read. Condition B "Claude Code alone" -- explicitly told not to use the `ziplex` CLI or any pre-packed file; pure Grep/Glob/Read/Edit/Bash. (No Claude Skill this round -- see the note on that below.)
- **Ziplex version**: main @ `57a412a` (`ziplex 0.5.0`). Note: the pack run for this round is what surfaced and forced a same-day fix (`57a412a` itself) -- see notes.
- **Model(s) used**: `claude-sonnet-5` on both sides (explicit `model: "sonnet"` on both subagent launches, so this is pinned and recorded, unlike round 1's gap)
- **Project analyzed**: [scrapy/scrapy](https://github.com/scrapy/scrapy) (real, actively-maintained open-source Python web-scraping framework), cloned at commit `86bec33cd3e6311b8481eac7d02e3ab0ec06f394` (2026-09-15). 502 `.py` files, 696 files total, ~8.7MB. Chosen deliberately over Ziplex's own repo (round #1) to test whether the "baseline is cheaper" finding was an artifact of testing on a codebase small enough for grep alone to cover cheaply -- picked by the user's own explicit choice of "well-known large open-source repo" over reusing an already-packed real project, accepting the tradeoff that a well-known repo may be partially present in the model's training data (see notes).
- **Claude Code's prior exposure**: two genuinely fresh `general-purpose` subagents (not forks), each given its own isolated copy of the clone (`scrapy_A`/`scrapy_B`, plain directory copies, not git worktrees -- the agents edit files outside the Ziplex repo entirely, so Ziplex-repo worktree isolation doesn't apply here). Neither subagent had seen this exact clone before. Both were explicitly instructed not to rely on general/training knowledge of Scrapy's internals without verifying it against the real code in front of them, to partially mitigate the training-data-familiarity risk noted above (this instruction can reduce but not eliminate that risk).
- **Ziplex packing state**: `ziplex pack <scrapy_A> --auto --auto-correct` (real Gemini calls, `gemini-3.5-flash`, default output dir `.ziplex/`) -- required two resumes from checkpoint (see notes) before completing. Final pack: 665 files summarized, token analysis reported `GPT-4o: 1,148,518 → 42,122 (96.3% reduction)` / `Claude (approx): 1,200,250 → 39,927 (96.7% reduction)`. This packing happened *before* either subagent was launched, so it is not counted in Condition A's measured cost -- same convention as entry #1.
- **Metrics measured**: harness's own subagent-completion `<usage>` block (`subagent_tokens`/`tool_uses`/`duration_ms`), never self-reported. Correctness was independently re-verified by the coordinating session: (1) diffed each copy's change against the pristine clone, (2) ran a fresh verification script (not either agent's own repro) covering 5 cases including two neither agent's own script covered, (3) ran the target project's own real, pre-existing test files (`tests/test_utils_response.py`, `tests/test_http_response_text.py`, `tests/test_linkextractors.py`) against both patched copies and the pristine baseline.
- **Result**:
  - Condition A (Ziplex-assisted): 65,565 tok / 16 tool calls / 262.6s (~4.4 min)
  - Condition B (Claude Code alone): 63,876 tok / 19 tool calls / 214.9s (~3.6 min)
  - Baseline was both cheaper (**~2.6% fewer tokens**) and faster (**~18% less wall-clock time**) despite making *more* tool calls (19 vs. 16) -- suggests A's `ziplex` CLI subprocess calls were individually costlier/slower than B's native Grep/Read for this task shape, not that A did less work.
  - Both conditions found the exact same root cause (the same real, still-open bug: [scrapy/scrapy#3017](https://github.com/scrapy/scrapy/issues/3017), filed 2017 -- `get_base_url()`/`get_meta_refresh()` in `scrapy/utils/response.py` hard-truncate the response body to the first 4096 characters before searching for a `<base>`/meta-refresh tag) equally fast. Condition A found it via one `ziplex search` call that landed directly on the truncation line; Condition B found it via a repo-wide Grep for `base href|<base|_baseurl|...` that also landed on it almost immediately. **Unlike round 1's rounds 2/3, the two conditions did not diverge on which bug they found this time** -- this particular bug was locatable fast either way.
  - **Correctness diverged, though**: independent verification (the coordinator's own 5-case script, covering both `get_base_url` and `get_meta_refresh`, a document with no `</head>` at all, a regression check, and a no-`<base>`-tag fallback check) showed BOTH fixes passing all 5 cases. But running the *target project's own pre-existing test suite* against each copy found that **Condition A's fix broke a real, existing test** (`tests/test_utils_response.py::test_get_meta_refresh`, specifically a malformed-HTML fixture where a `<meta>` tag sits inside `<noscript>` and a literal `</head>` string appears before the noscript's real closing tag) -- A's fix truncates the search text at the first `</head>` match, which in that fixture cuts off the closing `</noscript>` tag before `w3lib`'s `ignore_tags` stripping logic ever sees it, so the meta tag that should be ignored gets picked up instead. Condition B's fix (removing the 4096-char truncation entirely rather than replacing it with a different boundary) has no such failure mode and passed the full existing suite (26/26 in that file, 277/277 across the two broader files) with zero regressions. The pristine baseline also passes all 26 (none of the existing fixtures are large enough to trigger the original bug), confirming this is a regression A's fix introduced, not a pre-existing flaky test.
- **Notes**:
  - **A real Ziplex bug was found and fixed as a direct side effect of just trying to pack a 500+ file real project for this round**: `packager._extract_rules()` fed every collected file's signatures into `analyze_rules()`'s prompt with no size cap at all (unlike `_build_architecture_summary()`'s existing `MAX_ARCHITECTURE_FILES` cap for a *different* prompt). For this project the uncapped `signatures_map` repr alone ran to ~94k tokens, which the model could not return as a complete JSON response -- and because this "succeeded" at the HTTP level every time (not a 429/503 `generate()` would retry), non-interactive `pack()` had no way to tell it apart from a real, permanent failure, so it checkpointed and exited deterministically on *every* attempt, twice, before this was diagnosed and fixed (commit `57a412a`, same day, 897/897 tests passing after the fix). Without this fix, Condition A's pre-packed context for this round would not exist at all -- this is exactly the kind of large-real-project gap round #1 (self-pack on Ziplex's own ~115-file repo) could never have surfaced.
  - **Reinforces round #1's "tests pass ≠ fix complete" lesson, but this time on the higher-effort side**: Condition A's fix was the more elaborate of the two (a new regex + helper function, explicitly reasoned about a `</head>`-boundary rationale, and included 3 self-described "edge case" checks) and still shipped a real regression; Condition B's fix was the simpler one (delete the truncation, rely on existing per-response caching to keep it cheap) and had none. Neither agent's own testing caught A's regression -- it surfaced only when the coordinator ran the *target project's own* pre-existing test suite against the patched code, not either agent's self-written repro script. "More thorough-looking self-reported verification" was not a reliable signal of actual correctness here.
  - **Methodological gap from the plan**: Condition A was designed to use "the pre-exported Claude Skill" the same way entry #1 did, but Claude Code's Skill auto-discovery is scoped to the *main session's* project root (this Ziplex repo), not a subagent's own working directory in an unrelated external path -- there was no way to make a "scrapy" skill auto-available to a subagent operating outside this repo. Substituted with direct `aif.json`/`detail.json` file paths + the `ziplex` CLI instead, explained to the agent as its primary tool. This is arguably a more direct test of the underlying packed data's usefulness (no skill-packaging/discovery layer in between), but it is a real deviation from entry #1's design worth knowing about before comparing the two entries too literally.
  - **Training-data-familiarity risk, accepted not eliminated**: scrapy is a well-known library; either subagent could in principle answer from memorized training data rather than genuinely investigating this exact copy. Both were explicitly instructed to verify claims against the real code rather than trust recollection, and the recorded tool-call counts (16/19) plus the specific request to inspect the real `w3lib` source (which Condition B did) suggest real investigation happened rather than a memorized answer -- but this risk is mitigated, not ruled out, and is exactly the tradeoff the "well-known OSS repo" choice accepted over reusing an already-packed private project.
  - n=1 on this bug/project, same caveat as entry #1 -- this establishes that for *this* bug in *this* project, baseline was cheaper, faster, and (via an unrelated solution-design choice, not a tooling-caused difference) more correct. It does not establish that Ziplex-assisted investigation is generally slower, costlier, or lower-quality than baseline.

### #3 2026-09-18 — Ziplex-packed context vs. Claude Code alone, comprehension (fixed Q&A) instead of debugging

Motivation: entries #1/#2 both measured a *debugging* task, where the answer is self-verifying (tests pass/fail). This entry switches to measuring raw project-comprehension quality per token, since "Ziplex reduces the tokens needed to understand a project" is the actual headline claim being tested -- not just "the packed artifact is small" (which `ziplex tokens` already proves on its own and was never in question), but "an agent that uses it ends up cheaper/more accurate at answering real questions about the project."

- **Compared**: Condition A "Ziplex-assisted" -- given an already-generated Ziplex pack (`aif.json`/`detail.json`) plus the `ziplex` CLI, told to use both as the primary way to orient before falling back to raw Grep/Read. Condition B "Claude Code alone" -- explicitly told there is no pre-processed summary and to use only Glob/Grep/Read/Bash. Both were given the *same fixed list of 12 questions* about the codebase (architecture, specific function behavior, dependency/config facts) in one shot, and asked to answer all 12 in a single pass with no back-and-forth.
- **Ziplex version**: main `7b4857b` (`ziplex 0.5.0`)
- **Model(s) used**: `claude-sonnet-5` on both sides (explicit `model: "sonnet"` on both subagent launches)
- **Project analyzed**: [spf13/cobra](https://github.com/spf13/cobra) (real, actively-maintained open-source Go CLI-building library), cloned at commit `adbc8813901bba65827259daa8e22ff94ec1f30e`. 36 `.go` files, 66 files total -- deliberately chosen as a *less globally famous* real OSS project than scrapy (entry #2) to reduce training-data-memorization risk, while still being real and non-trivial. Picked from a shortlist the user reviewed (over e.g. `pallets/click`) specifically to also diversify away from Python (entries #1/#2 were both Python) and exercise Ziplex's Go support.
- **Claude Code's prior exposure**: two genuinely fresh `general-purpose` subagents (not forks), each given its own isolated plain-directory copy of the clone (`cobra-a`/`cobra-b`, `.git` stripped from both). Neither subagent had seen this exact clone before.
- **Ziplex packing state**: `ziplex pack <cobra-a> --auto --auto-correct` (real Gemini calls). First attempt's rules-extraction step failed and checkpointed (non-interactive mode always checkpoints-and-exits on an LLM failure rather than guessing); resumed once and completed cleanly. Final pack token analysis: `GPT-4o: 168,711 → 3,501 (97.9% reduction)` / `Claude (approx): 159,095 → 3,326 (97.9% reduction)`. Packing happened before either subagent was launched and is not counted in Condition A's measured cost.
- **Metrics measured**: harness's own subagent-completion `<usage>` block (`subagent_tokens`/`tool_uses`/`duration_ms`), never self-reported. Correctness: a 12-question, 24-point (0/1/2 per question) answer key was written by the coordinating session *from the real source directly* (command.go, args.go, flag_groups.go, active_help.go, the completion-generator files, go.mod, doc/*.go) *before* either subagent was launched, so the key couldn't be biased by either side's answer. Each subagent's final answers were graded against that same fixed key.
- **Result**:
  - Condition A (Ziplex-assisted): 84,785 tok / 13 tool calls / 65.6s -- 24/24 (all 12 questions fully correct, with accurate file/line/function citations)
  - Condition B (Claude Code alone): 64,926 tok / 21 tool calls / 85.3s -- 24/24 (same, all fully correct)
  - **Accuracy was a dead tie** -- both sides answered every question correctly, including subtle ones (e.g. the exact three `flag_groups.go` annotation constants and which method sets each one, or the precise `legacyArgs` branching between a no-subcommand command / a root command with subcommands / a non-root command with subcommands).
  - **Baseline was ~23% cheaper on tokens** (64,926 vs. 84,785) despite making *more* tool calls (21 vs. 13) -- the same "Ziplex CLI subprocess calls cost more individually than native Grep/Read" pattern already seen in entry #2, but with a wider gap this time.
  - Ziplex-assisted was faster in wall-clock time (65.6s vs. 85.3s) despite costing more tokens -- fewer, more expensive round-trips vs. more, cheaper ones.
- **Notes**:
  - This is the first entry to test *comprehension* rather than debugging, and the first to find a **dead-even accuracy tie** rather than any divergence between conditions -- a genuinely different outcome shape from #1 (where conditions sometimes found different bugs or one side's fix was worse) and #2 (where one side's fix regressed).
  - Possible explanation for the tie, not confirmed: cobra's source has unusually thorough doc comments on nearly every function referenced by the question set (Go convention at its best), which may have made every question answerable correctly either way regardless of *how* the answer was found -- i.e. this question set may not have been hard enough to reveal a real comprehension-depth gap. A harder set (requiring synthesis across multiple files, not just locating one well-documented function) is a natural next iteration.

### #6 2026-09-19 — Does packing pay off across repeated reuse? (amortization test)

Prompted directly by the user asking, after #5, whether Ziplex's core token-reduction pitch still holds up given #1-#5's mostly-negative/mixed results -- and, separately, whether the "no filesystem access" niche (rejected after #4/#5 as weak and shrinking) had a better replacement in "pack once, reuse across many queries." This entry is the first real test of that hypothesis, using godot-open-rpg (same project/commit as #4) so it could reuse #4's own already-measured per-query costs as a starting point rather than establishing them from scratch.

**Design, in two phases:**

- **Phase 1 (algebraic, cheap)**: get godot-open-rpg's real one-time packing cost for the first time ever (previous entries only had the packed *artifact's* size, not what the LLM API was actually billed -- see the "Known gap" section above), then compute the break-even reuse count `N` at which Condition A's amortized average cost (pack_cost/N + A's own per-query cost) would drop below Condition B's flat per-query cost, using #4's already-recorded token gap.
- **Phase 2 (empirical)**: run 2 more independent 10-question rounds (deliberately covering *different* subsystems than #4's original 12 -- see below) against the *same* already-generated pack, to check whether the per-query cost gap Phase 1's calculation depends on is actually stable across different real queries, or was specific to #4's one particular question set.

- **Ziplex version**: main `4adf379` -- includes the `usage_tracker` feature (`27384c1`, built earlier this same session specifically to make Phase 1 possible) that logs every real provider's own billed input/output tokens during `pack()`.
- **Model(s) used**: `claude-sonnet-5` for every subagent (both conditions, both new rounds); `gemini-3.5-flash` for packing (`describe_active_provider()` confirmed this is what `GEMINI_MODEL`'s floating default currently resolves to).
- **Project analyzed**: [gdquest-demos/godot-open-rpg](https://github.com/gdquest-demos/godot-open-rpg), re-cloned at the *same* commit as #4 (`19bd328fae9e4b534d3bb6db380a3d871d6ea58f`) -- the original #4 clones/pack had already been deleted per that entry's own cleanup, so this is a fresh clone+pack, not a literal reuse of #4's files, but the same project state.
- **Claude Code's prior exposure**: 4 more genuinely fresh `general-purpose` subagents (not forks) across the 2 new rounds, same isolated-plain-directory-copy pattern as #3/#4/#5 (`rpg-a`/`rpg-b`).
- **Ziplex packing state**: `ziplex pack <rpg-a> --auto --auto-correct`, real Gemini calls. Unlike #3/#4/#5's first-attempt-always-fails pattern (3-for-3 rules-extraction checkpoint failures noted in #5), this run's first attempt succeeded outright -- so that failure pattern isn't universal/deterministic either, another data point for whoever eventually investigates it. **Real packing cost, measured for the first time**: 572 real LLM requests, 370,010 input tokens, 67,475 output tokens (`llm.get_usage()`'s snapshot) -- at `gemini-3.5-flash`'s published rate ($1.50/1M input, $9.00/1M output, looked up live on 2026-09-19, not assumed from memory) that's **$1.1623**.
- **Round 2 questions** (10, Inventory/Cutscene/UI subsystem -- deliberately different files from #4's Combat/Overworld-core set): `Inventory` (extends `Resource`, 6-value `ItemTypes` enum, persists to `user://inventory.tres`), `Trigger`/`Interaction`'s shared `Cutscene extends Node2D` base, `UIInventory extends HBoxContainer`, `PlayerController extends GamepieceController extends Node2D`, `Pathfinder extends AStar2D`, `MusicPlayer extends Node`/`ScreenTransition extends CanvasLayer`. Answer key written from the real source before either subagent ran, same as #3-#5.
- **Round 3 questions** (10, camera/events/utility subsystem, a third distinct area): `FieldCamera extends Camera2D`, all 7 live signals on the `FieldEvents` autoload signal bus, `CollisionFinder`/`Directions` both `extends RefCounted`, `Directions.Points`'s 4 values and its `angle_to_direction()` conversion function, `Pathfinder extends AStar2D` (re-asked from a different angle than round 2), which `FieldEvents` signal a UI would listen to for input-pause vs. interaction-selection.
- **Metrics measured**: same harness `<usage>` block as every prior entry for per-round subagent cost; real pack cost via the new `usage_tracker`. Dollar conversion used official, live-looked-up pricing (not assumed): Gemini 3.5 Flash $1.50/$9.00 per 1M input/output tokens; Claude Sonnet 5 $2/$10 per 1M input/output tokens (both fetched 2026-09-19, both subject to change later without this entry being updated). **A real limitation hit immediately**: the harness's own subagent `<usage>` block reports only a single combined `subagent_tokens` figure, with no input/output split exposed anywhere -- Claude Sonnet 5's 5x input/output price asymmetry means an exact per-round dollar cost can't be computed without that split, so Phase 1's break-even table reports a *range* across assumed input fractions (0%-100%) rather than one number, explicitly flagged as an assumption, not a fact the way the packing-cost fix made Gemini's side exact.
- **Result**:
  - **Phase 1 (algebraic)**: using #4's own token gap (A: 66,692 vs. B: 70,322 tok) and the $1.1623 real pack cost, break-even `N` ranges from 32 (unrealistic 100%-output assumption) to 160 (unrealistic 100%-input assumption) queries, landing around **100-133** at the two most plausible input-heavy fractions for an agentic coding task (85%-95% input). That is: even in the best real-world-plausible case, the same pack would need to be independently reused in over 100 separate queries before its one-time cost is paid back by #4's observed per-query savings.
  - **Phase 2 (empirical) -- and this is the real finding**: #4's own per-query advantage did not replicate. Round 2: A 65,015 tok / 19 calls / 41.6s vs. B 62,460 tok / 13 calls / 33.1s -- **baseline cheaper**. Round 3: A 59,935 tok / 8 calls / 30.7s vs. B 57,527 tok / 9 calls / 29.9s -- **baseline cheaper again**. Averaged across all 3 independent rounds against the same pack (#4 + round 2 + round 3): Condition A 63,881 tok, Condition B 63,436 tok -- **baseline cheaper on average, by ~0.7%**, essentially a dead tie with a slight edge to baseline, not the ~5% Ziplex-favoring gap #4 alone suggested.
  - Accuracy stayed tied throughout: 12/12 (#4) + 10/10 (round 2) + 10/10 (round 3) = 32/32 for both conditions, no divergence at any point across this entire entry.
- **Notes**:
  - **The headline finding isn't "amortization doesn't work" -- it's that the thing being amortized was never actually there.** Phase 1's break-even math assumed #4's ~5% Ziplex-cheaper gap was a real, stable, exploitable property of this project; Phase 2 shows that gap doesn't survive being re-measured with different (but equally real) questions against the identical pack. Sample size matters more than which condition "won" any single round -- #3/#4/#5's own single-round comparisons should now be read with the same caution: a single round's winner may just as easily be noise as a real effect, something this project's own experiment log hadn't directly tested until now.
  - **A concrete methodological lesson for future rounds**: don't trust a single question-set's cost comparison as a project-level verdict. Where feasible, run at least 2-3 independent rounds (different, non-overlapping questions) against the same project/pack before drawing a directional conclusion -- exactly what this entry did, and what revealed the instability #3/#4/#5 individually couldn't have shown.
  - **The subagent input/output-split gap is a real, currently-unfixable-from-here limitation** (unlike the packing-cost gap, which was fixable in `llm.py` since Ziplex owns that code) -- the harness's own `<usage>` block would need to expose the split for an exact dollar figure on the Claude side. Flagged, not fixed, in this entry.
  - This result also updates how the user's own "is this project still worth it" question (asked directly, same session, right before this entry was designed) should be read: the reuse-amortization angle -- floated as the most promising untested efficiency angle after #4/#5's project-dependent split-decision result -- turns out to depend on a per-project cost edge that, at least for godot-open-rpg, isn't real once measured properly. This doesn't rule out amortization working for some *other* project (one where Ziplex's per-query edge is real and reproducible across multiple independent rounds, not just one), but it does mean the edge has to be *verified* multi-round before an amortization argument can be built on top of it -- a single favorable round, as #4 was, isn't sufficient evidence on its own.

### #8 2026-09-19 — Same tools, same project, synthesis questions instead of facts (2 rounds)

Direct follow-up to #7's finding: if natural-language summaries lose on *factual* questions because they're a lossier, costlier re-encoding of facts the raw code already states directly, do they instead win on *synthesis* questions -- ones that need reasoning across many files into something no single file states outright (architecture, risk assessment, "where would I even start")? This is exactly the question type folder summaries, confidence scores, and the relationship graph were built for, and it had never been tested until now -- every prior entry (#1-#7) asked either debugging or factual-lookup questions.
