# src/ziplex/extract/text/ — non-Tree-sitter compressors

Scoped notes for `registry.py`/`json.py`/`yaml.py`/`markdown.py`/`txt.py`. See the root `CLAUDE.md` for how these fit into the overall `pack` pipeline, and `src/ziplex/extract/code/CLAUDE.md` for the sibling Tree-sitter-based code extraction/compression these fall back to when there's no grammar for a file's extension.

- **`registry.py`** — `TEXT_COMPRESSORS: dict[ext, Callable[[str], str]]`. `compress_file()` in `extract/code/compressor.py` falls back here when there's no Tree-sitter grammar for the extension. To support a new text format, write a `compress_*(text) -> str` function and register it here.
- **`json.py`** — parses and keeps structure (keys), eliding only long strings (`MAX_STRING_LEN`) and long arrays (`MAX_ARRAY_ITEMS`, keeps the leading items + a marker). Falls back to returning the original text unchanged if `json.loads()` fails — never crashes on malformed JSON.
- **`yaml.py`** (2026-08-24, added after an "does Ziplex handle infra/server projects, not just app code?" discussion surfaced YAML as the one genuinely addressable gap) — same idea as `json.py` (keep keys, elide long strings/arrays via the same `MAX_STRING_LEN`/`MAX_ARRAY_ITEMS` thresholds) but **deliberately not built the same way**. `json.py`'s "parse into plain Python objects, then re-dump" approach is safe for JSON only because JSON's grammar is unambiguous; applying the same strategy to YAML via PyYAML's `safe_load`/`safe_dump` was tried first and rejected after live-reproducing a real, silent data-corruption bug -- YAML 1.1's implicit scalar typing turns an unquoted `3.10` into the float `3.1` and an unquoted `NO` into `False` (the "Norway problem", a well-known real gotcha for GitHub-Actions-style `python-version: 3.10` lines). That's not a compression-quality issue, it's a *wrong value silently shipped as ground truth* issue, worse than not compressing the file at all. Built on `ruamel.yaml`'s round-trip mode instead (`YAML()`, `preserve_quotes = True`, `width = 4096` to stop it from cosmetically rewrapping an untouched long line): every scalar `_compress_value()` doesn't touch keeps its **exact original text** (quoting, numeric formatting), confirmed live against the same `3.10`/`NO` inputs. Also gets three things PyYAML's `safe_load`/`safe_dump` never would have: key order preserved (PyYAML's `safe_dump` defaults to alphabetizing, which would scramble a Kubernetes manifest's conventional `apiVersion`/`kind`/`metadata`/`spec` order), comments preserved (PyYAML drops them entirely), and anchors/aliases (`&x`/`*x`, common in Docker Compose/CI matrices for shared config blocks) kept as references instead of being fully expanded -- expansion would make an anchor-heavy file *larger* after "compression," the opposite of the point.

  `_compress_value()` mutates the loaded `CommentedMap`/`CommentedSeq` nodes **in place** rather than rebuilding plain `dict`/`list` the way `json.py`'s does -- ruamel attaches comments to the container instance itself, so rebuilding from a comprehension silently drops them (confirmed live: a trailing `# comment` survives an in-place `d[key] = new_value` reassignment but not a `{k: v for k, v in d.items()}` rebuild). That in-place strategy itself surfaced a second real bug before this shipped, not just a theoretical risk: a `CommentedMap` materialized via a `<<: *anchor` merge key already has every merged-in key sitting in its own storage at load time (`.keys()` can't tell an explicitly-written key apart from one that only exists because of the merge) -- so the recursive pass's `value[key] = _compress_value(value[key])`, even when it reassigns the *exact same* untouched value, made ruamel treat that key as newly explicit and spell it out redundantly alongside the `<<:` reference, duplicating every merged key in every service of a real `docker-compose.yml` fixture. Fixed by reading each map's `.merge` attribute (the list of source dicts a `<<:` pulled in) and skipping any key whose name appears there entirely -- the rare cost is a key that both merges *and* explicitly overrides with a long value just doesn't get compressed, traded off against not duplicating every single merge use.

  Handles multi-document files (`---`-separated, common for Kubernetes manifests bundling several resources in one file) via `load_all()`/compress-each/rejoin-with-`---`, except a single-document file, which gets no leading separator, matching how most real single-resource YAML is actually written. Falls back to the original text unchanged on a `YAMLError` (malformed YAML) or an empty/whitespace-only file (`load_all()` yields no documents) -- same contract as `json.py`'s on invalid JSON. Registered for both `.yaml` and `.yml` in `registry.py`. Adds `ruamel.yaml` as a new dependency (`pyproject.toml`/`requirement.txt`) -- deliberately not `pyyaml`, per the corruption bug above.

  **A third real bug, caught by `/code-review low` on the diff, not written defensively in advance**: a plain `*alias` referencing a whole list/map (not a `<<:` merge -- that's the separate key-level guard above) isn't a copy in ruamel's round-trip mode, it's the exact same Python object as the `&anchor` it points to -- so without a visited-object guard, `_compress_value()`'s in-place mutation touched the shared container twice, and the second pass saw the marker string the first pass had already appended as if it were real list data, re-truncating around it and *understating* how much was actually elided (reproduced live: a 5-item list aliased twice reported "1개 항목 생략" instead of the correct "2개 항목 생략"). Fixed with `_seen` (a `set()` of `id()`s threaded through the recursion, reset fresh per top-level `_compress_value()` call -- an alias never crosses a `---` document boundary, so multi-document files don't need to share one across documents): a dict/list already visited in this pass just returns as-is instead of being processed again.

  Live-verified end to end via `ziplex compress` against a hand-built `docker-compose.yml` fixture (a `version: "3.10"`/`country_note: NO`-style ambiguous-scalar line, a `&defaults`/`<<: *defaults` anchor shared by two services, a 5-item `ports` list) -- every value preserved exactly, the anchor stayed a single reference with no duplicated keys, and the long `ports` list correctly truncated to 3 items + a marker. All three bugs above (corruption-avoidance, merge-duplication, double-compression-via-alias) have their own regression tests in `tests/test_text_compressors.py`, each written to fail without its fix first.
- **`markdown.py`** — line-oriented regex approximation (no Markdown AST available). Headings/blank lines always kept as structure. Lists/tables/paragraphs get the same "keep the lead, elide the rest with a marker" treatment past their own thresholds (`MAX_LIST_ITEMS`, `MAX_TABLE_ROWS`, `MAX_PARAGRAPH_LEN`). Code fences with a language tag `extract/code` recognizes (`_FENCE_LANG_TO_EXT` — kept in sync with `languages.py`'s keys) get real structural compression by calling `compress_code()` first; if the result is still long, it's truncated by line count same as everything else. Untagged/unrecognized languages skip straight to line-count truncation.
- **`txt.py`** — no structure to preserve at all beyond blank-line paragraph breaks; just the two generic rules (long block elided past `MAX_BLOCK_LINES`, long line truncated past `MAX_LINE_LEN`) that `markdown.py`/`json.py` also use for their own "body" content.
- **Circular import note**: `extract/code/compressor.py` → `extract.text.registry` → `extract.text.markdown` → (for code blocks) `extract.code.compressor.compress_code` again. Both directions import the other module's function inside the function body, not at module top, specifically to break this cycle — don't "clean up" those into top-level imports.
