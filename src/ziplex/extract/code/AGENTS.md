# src/ziplex/extract/code/ — Tree-sitter extraction & compression

Scoped notes for `languages.py`/`parser.py`/`extractor.py`/`compressor.py`. See the root `AGENTS.md` for how these fit into the overall `pack` pipeline, and `src/ziplex/extract/text/AGENTS.md` for the sibling non-Tree-sitter (JSON/YAML/Markdown/plain-text/Dockerfile) compressors. Detailed per-language history (why each `LanguageConfig` field exists, every real bug found adding a language): `docs/HISTORY.md`.

## languages.py

Single source of truth per language: `LANGUAGE_CONFIGS: dict[ext, LanguageConfig]`, each with:
- `language` — the compiled Tree-sitter grammar.
- `function_types` — node types targeted for signature extraction + body compression.
- `dependency_handler` — a `(Node, list) -> bool` callback recognizing that language's import syntax.
- `api_handler` — same shape, recognizing a REST-route-declaration convention if the language has one (`None` by default; only `.py`/`.ts`/`.js` have one today).
- `field_handler` — a `(Node, list) -> None` callback (no "stop recursing" return value, unlike `dependency_handler`/`api_handler` — see its own comment in `languages.py` for why) recognizing a class-level field whose initializer is itself worth surfacing as a signature (a call, not a plain literal) — `None` by default; only `.java` has one today. See `extractor.py`'s bullet below for why this is folded straight into `extract_signatures()`'s own output, in document order, rather than a fourth, separately-wired extraction function.
- `implicit_names` (`dict[node_type, name]`, empty by default) — a fallback name for a `function_types` node whose grammar gives it neither its own `"name"` field nor a named wrapper (GDScript's `constructor_definition`).
- `name_prefixes` (`dict[node_type, prefix]`, empty by default) — a prefix to prepend onto a name that *was* found (C#'s `destructor_declaration` → `"~"`).
- `zero_arg_types` (`frozenset[node_type]`, empty by default) — node types whose grammar omits the `"parameters"` field entirely for a real zero-argument function, where substituting `"()"` is structurally guaranteed correct (Ruby's parens-less `def foo`).

Supporting a new extension is one `LanguageConfig` entry — `extractor.py`/`compressor.py` never hardcode per-language node types.

Currently supported: `.py`, `.java`, `.ts`/`.js` (`.js` via the TSX grammar), `.lua`, `.gd`, `.go`, `.cpp`/`.cc`/`.cxx` (one shared config), `.rs`, `.cs`, `.php`, `.rb`, `.sh`/`.bash` (one shared config).

### Per-language notes

- **`.py`**: `api_handler` (`_py_api_handler`) matches a Flask-style `@app.get("/path")` decorator by `.get`/`.post`/etc. appearing anywhere in the decorator text. `_py_dependency_handler` filters a stdlib import out via `_is_stdlib_import()` (checked against the running interpreter's own `sys.stdlib_module_names`, 3.10+) before ever appending it — a plain `import json` is otherwise structurally identical to a path-based dependency and can misresolve onto a same-named local file. Scoped to stdlib only, never third-party packages (a target project's own installed packages are its own business, same scope limit `tech_stack.py` takes). A relative import (`.file.collector`) is never affected.
- **`.java`**: `method_declaration` exposes `"name"`/`"parameters"`/`"body"` directly; its own `"type"` field (its return type) is a distinct field-naming convention from Python/TS/GDScript's `"return_type"` — checked only when a C++-style declarator unwrap actually happened (never true for Java), so Java signatures never get a spurious `-> type` suffix. `field_handler=_java_field_handler` additionally captures a class-level field whose initializer is a `method_invocation` (`public static final Item RUBY_TOOL = register("ruby_tool", ...);`) as `"RUBY_TOOL = register(\"ruby_tool\", ...)"`, appended in document order into `extract_signatures()`'s own results — a registry-style class's *actual* primary behavior (defining a whole set of constants via a factory call) is otherwise entirely invisible to `method_declaration`-only extraction. A plain literal- or `object_creation_expression`-initialized field (`private int count = 0;`, `new ArrayList<>()`) is deliberately excluded — only a genuinely call-shaped initializer counts. `children_by_field_name("declarator")` (plural) handles a single field declaration defining several comma-separated declarators at once (`A = f(), B = g();`); the captured value's text is whitespace-normalized to one line (including inside a string-literal argument — a documented, accepted imprecision), since a real registration call routinely wraps across several indented source lines (a lambda argument) and every other signature here is single-line. Recurses into a matched field's own children regardless (a field initializer can legally contain its own nested `field_declaration`, e.g. an anonymous class body) rather than stopping — see `field_handler`'s own bullet above for why this handler's return-value contract differs from `dependency_handler`/`api_handler`'s.
- **`.ts`/`.js`**: `function_types` includes `arrow_function`/`function_expression` alongside `function_declaration`/`method_definition` — the dominant way modern JS/TS is actually written. `_traverse_signatures()` threads the current node's parent through its recursion; `_resolve_signature_name(node, parent)` checks the node's own `"name"` field, then the parent's `"name"` (`variable_declarator` for `const add = (a,b) => ...`, `public_field_definition` for a class-field arrow) or `"key"` (`pair`, for an object-literal method). A bare single-identifier-parameter arrow with no parens (`x => x * 2`) has no `"parameters"` field at all and is a documented, deferred gap — no signature produced. `api_handler` (`_js_api_handler`) matches an Express-style `app.get("/path", ...)` call by property name, requiring a plain (non-template-literal) string first argument starting with `"/"`.
- **`.lua`**: no import *statement* — `_lua_dependency_handler` recognizes `require(...)` by matching a `function_call` node whose callee is literally `"require"`. `function_types=["function_declaration"]` covers `local function f()`, `function Tbl.f()`, and `function Tbl:method()` uniformly; `child_by_field_name("name")` already returns the qualified text, and `"body"` already excludes the closing `end`.
- **`.gd` (GDScript)**: sourced from `tree-sitter-language-pack`'s bundled copy (no dedicated PyPI package with a Python binding exists). `_gdscript_dependency_handler` recognizes `preload(...)`/`load(...)` (read positionally, this grammar's `call` node has no callee field name) and `extends "res://Base.gd"` (path-based inheritance; a bare `extends Node`/`extends SomeClass` is left uncaptured). `preload`/`load`/`extends` arguments are `res://`-prefixed file paths, normalized to their bare stem before `resolve_dependency()` sees them. `constructor_definition` (`_init`) has no `"name"` field at all — `implicit_names={"constructor_definition": "_init"}` supplies it.
- **`.go`**: `function_types=["function_declaration", "method_declaration"]`. Go's grammar names its return-type field `"result"`, not `"return_type"` — `_traverse_signatures()` checks both generically. A receiver method (`func (s *Server) Start() ...`) exposes `"name"`/`"parameters"`/`"result"`/`"body"` directly; its `"receiver"` field is never read. `_go_dependency_handler` matches `import_spec`'s `"path"` field, ignoring any alias/blank-`_` `"name"`, and returns it as-is (still just a raw path string, resolved one layer up by `go_packages.py` — a project-wide module, not scoped to this directory; see the root `AGENTS.md`'s own bullet for it).
- **`.cpp`/`.cc`/`.cxx`**: one shared config (all three parse identically). `function_types=["function_definition"]` covers a free function, in-class method, out-of-class `Class::method`, constructor, and destructor uniformly. This grammar nests a function's identifier/parameters one level inside a `"declarator"` sub-node (`function_declarator`) rather than exposing them directly — `_unwrap_declarator()` detects this structurally (falls through unchanged for every other language) and hands the inner node to name/parameter resolution; the inner node's identifier field is itself called `"declarator"`, not `"name"`. Return type sits on the outer node under a fourth convention, `"type"` — `None` for a constructor/destructor. `"type"` is only consulted when `sig_node is not node` (i.e. an unwrap actually happened), since Java's own `"type"` field (its return type) would otherwise get the same treatment by accident. `_cpp_dependency_handler` matches `preproc_include`, normalizing both `<iostream>` and `"utils.h"` shapes to their bare stem. Scoped to implementation files only — a header with only prototype declarations produces zero signatures under this config, since a bodyless declaration never parses as `function_definition`.
- **`.rs`**: `function_item` exposes `"name"`/`"parameters"`/`"return_type"`/`"body"` directly — no declarator indirection, matches Python/TS/GDScript's own convention exactly. `function_types` also includes `function_signature_item` (a trait method with no body). `_rust_dependency_handler`: `mod foo;` (`mod_item`, gated on an *absent* `"body"` field — a body-having `mod foo { ... }` is an inline submodule, not a file reference, and must keep recursing into its own contents rather than stopping) is the most precise dependency Rust has, read straight off `"name"`. `use path::to::Item;` (`use_declaration`) is a symbol import handled by `_append_rust_use_paths()` — text-based, depth-aware comma-splitting for `use_list`/`scoped_use_list` groups (`use std::{fmt, collections::HashMap}`), checking for a group *before* stripping an `as` alias (stripping first would truncate a group containing an aliased sibling). `"::"` normalizes to `"."`. No `api_handler` — no single dominant routing convention across actix-web/axum. Known limitation: a `use` path's last segment often names a type (PascalCase), not the file that defines it (snake_case) — `mod_item` resolution carries most of the real internal-dependency precision; `use_declaration` is a bonus on top.
- **`.cs`**: `method_declaration`/`constructor_declaration`/`destructor_declaration` expose `"name"`/`"parameters"`/`"body"` directly. Return-type field is `"returns"` — a fourth naming convention alongside `"return_type"`/`"result"`/`"type"`. `destructor_declaration`'s own `"name"` is the bare identifier (`"Widget"`, not `"~Widget"`) — `name_prefixes={"destructor_declaration": "~"}` restores it. `_csharp_dependency_handler` reads every `using` variant positionally (none expose a consistently-named path field): the *last* identifier/qualified_name child is the real path, scoped to children *after* `"="` for an aliased `using X = Y;` (searching the whole node there would find the alias name itself for a non-identifier target like `using MyInt = int;`). No `api_handler` — ASP.NET has no single dominant routing shape. Known gap: `tech_stack.py`'s fixed-filename manifest list doesn't match a variable `<ProjectName>.csproj`, so a C# project's `tech_stack` entry is silently absent.
- **`.php`**: uses the `language_php` grammar variant (not `language_php_only`) since a real collected file has the usual HTML-plus-`<?php`-tags shape. `function_definition`/`method_declaration` expose `"name"`/`"parameters"`/`"return_type"`/`"body"` directly. Deliberately excludes anonymous/short closures (`function() {...}`/`fn() => ...`) from `function_types` — neither has a `"name"` field, and their wrapping `assignment_expression` names its target under a `"left"` field the existing wrapper-fallback doesn't check. `_php_dependency_handler`: `use Foo\Bar;`/aliased/grouped `use Foo\{Bar, Baz as B}` forms all parse as `namespace_use_declaration` with two different internal shapes (direct `namespace_use_clause` children vs. a `namespace_use_group` needing its prefix re-attached per clause); the first `qualified_name`/`name` child is always the real path, read positionally. `"\\"` normalizes to `"."`. `require`/`require_once`/`include`/`include_once` are dedicated node types with a real relative file-path argument, normalized to its bare stem. No `api_handler` — Laravel/Symfony/Slim each have a different routing shape.
- **`.rb`**: `method`/`singleton_method` expose `"name"`/`"parameters"`/`"body"` directly, no return-type field at all (handled for free by the existing convention chain finding nothing). Idiomatic Ruby commonly omits parens for a zero-arg method (`def initialize`) — this grammar then has no `"parameters"` field, indistinguishable at the field-presence level from TS/JS's bare single-param arrow (which *does* take an argument Ziplex just doesn't capture). `zero_arg_types={"method", "singleton_method"}` opts these two node types into the empty-`"()"` substitution without touching TS/JS's own gap. Also covers Ruby 3.0+ endless methods (`def square(x) = x * x`) for free. `_ruby_dependency_handler` recognizes `require`/`require_relative` as an ordinary receiver-less `call` (callee field is `"method"`, not `"name"`); a `require_relative` path's `.rb` extension is conventionally omitted already. No `api_handler` — Rails/Sinatra/Grape share no one dominant shape.
- **`.sh`/`.bash`**: one shared config (both parse identically). `function_definition` covers Bash's two equivalent declaration forms (`function deploy() { ... }` and the POSIX-compatible `deploy() { ... }`) uniformly, `"name"`/`"body"` as direct fields. A shell function's `()` is fixed syntax, never a real parameter list (arguments are read via `$1`/`$2`/`$@` inside the body, not declared) — this grammar has no `"parameters"` field at all for any function, ever, so `zero_arg_types={"function_definition"}` substitutes `"()"` unconditionally (unlike Ruby's opt-in-per-parens-omitted-spelling use of the same field). `_bash_dependency_handler` recognizes `source file.sh` / `. file.sh` as an ordinary `command` node matched by its `"name"` field's text (`"source"`/`"."`), reading only the first `"argument"` child (confirmed against the real grammar that this field is always just the first argument regardless of how many follow, so a sourced script's own positional args aren't mistaken for part of the path) — normalized to its bare stem, same restraint as GDScript's `preload()`/C++'s `#include`. No `api_handler` — no established routing convention for shell scripts.

## parser.py

`get_parser_by_ext`/`get_parser` just wrap `languages.py` to hand back a ready `Parser`.

## extractor.py

Walks the parsed AST for three things, each its own traversal:
- **`extract_signatures`** — per `function_types`, builds `name(params) -> return_type` strings. `_resolve_signature_name(node, parent)` checks the node's own `"name"`, then the parent's `"name"`/`"key"`, then `implicit_names` (keyed by `node.type`). `name_prefixes` (same key) is applied right after a name resolves. The return-type check is one small `or`-chain (`"return_type"` → `"result"` → `"returns"` → conditionally-gated `"type"`), not a per-language branch. A signature is only appended when `params` is present *or* `node.type` is in `zero_arg_types` — the latter is a structural guarantee of real zero arity, not a guess. When a language's config carries a `field_handler`, the *same* traversal also checks it on every non-function node it visits, appending straight into the same results list in actual source order — deliberately not a second, separate tree walk: appending field entries only after every function signature (regardless of where they actually sit in the file) let a field-registration entry be silently pushed past `corrector.py`'s/`summarizer.py`'s fixed-count display caps by enough preceding methods, and a naive "stop recursing once matched" return on the field side missed a field legally nested inside another one's own initializer (an anonymous class body). Folding into this one function, rather than a fourth, separately-named extraction function, also means every real consumer of `signatures` (`confidence.py`, `corrector.py`'s review display, `summarizer.py`'s prompts) picks this up for free, with no second call site anywhere that could forget to also call an `extract_field_registrations()`-shaped sibling (see `go_packages.py`'s own docstring for a real, adjacent case where exactly that kind of miss happened).
- **`extract_dependencies`** — delegates node recognition to the language's `dependency_handler`.
- **`extract_api`** — delegates to the language's own `api_handler`; `[]` outright for a language with none configured.

## compressor.py

`compress_code(code, ext)` strips function bodies, replacing each with a single marker line (`"    ⋮----"`), keeping signatures/imports/decorators verbatim. Two brace-language subtleties: if the body's opening `{` sits on the same line as the signature (JS/TS/Java), the marker starts on the *next* line; the body's closing `}` (if present as the body's last child) is excluded from the stripped range. Returns `None` for an unsupported extension so callers (`compress_file()` here, and Markdown code-block compression in `extract/text/markdown.py`) can fall back to something else — both share this function, so a fix here fixes Markdown-embedded code too (see `src/ziplex/extract/text/AGENTS.md`'s circular-import note for why that import lives inside a function body). `_collect_bodies` only needs a matched node's `"body"` field, no name. A concise (brace-less, single-line) arrow needs no special-casing — its body sits on the same source line as the signature, so the "same line" check already leaves it untouched.

`compress_file()`'s own extension lookup goes through `_effective_ext(file_path)`, not a bare `Path(file_path).suffix` — a real Dockerfile is almost always named with no extension at all (`Dockerfile`, `Dockerfile.dev`) rather than something Ziplex's purely suffix-based dispatch could ever match on its own. `_effective_ext()` recognizes that shape by filename (case-insensitive `dockerfile`/`dockerfile.*`/`*.dockerfile`) and maps it to the fixed `.dockerfile` key, which resolves through `get_text_compressor()` in `extract/text/registry.py` — a file already spelled with a literal `.dockerfile` extension needs no help from this function at all, since `Path.suffix` already produces the same key.
