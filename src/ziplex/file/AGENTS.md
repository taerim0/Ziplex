# src/ziplex/file/ — collection, security scan, selection, dependency graph

Scoped notes for `file/collector.py`, `file/scanner.py`, `file/relationship.py`, `file/textutil.py`, `file/media.py`. See the root `AGENTS.md` for how these fit into the overall `pack` pipeline. Detailed history (real bugs found and fixed in each module): `docs/HISTORY.md`.

## textutil.py

Two shared low-level helpers everything else in the pipeline builds on: `read_text()` (safe UTF-8 read, `None` on anything that isn't decodable text) and `relative_key(file_path, root)` (a file's path relative to `root`, as a stable dict key — falls back to the bare filename if `file_path` isn't under `root`). `search.py` (outside `file/`) also depends on it; `packager.py` imports it as `relative_key as _rel_key`.

## collector.py

`collect_files(root_path, include=None, ignore=None)` walks the tree and excludes several ways:
- **`DEFAULT_IGNORE`** — a curated pattern list (node_modules/, build caches, OS junk, `.env`/`.env.*` except the `.env.example`/`.sample`/`.template`/`.dist` templates) plus the project's own `.gitignore` (and every nested `.gitignore`, each applied to paths under its own folder, relative to it), compiled via `pathspec.PathSpec.from_lines("gitignore", ...)` (not `"gitwildmatch"`, deprecated in the installed version). Cheap, skips whole directories before reading content, so it's the first filter, not the only one.
- **`ignore`** — extra patterns beyond `DEFAULT_IGNORE`/`.gitignore`, merged into the same `pathspec` (prunes directories the same efficient way). Typically sourced from `.ziplex.json` (`config.py`) or a `--ignore` flag.
- **`include`** — the inverse: if given, a file must match at least one pattern to survive. Applied as a post-filter on the already-collected list, deliberately *not* used to prune directories during the walk — an include pattern like `"src/**/*.py"` says nothing about whether some unrelated intermediate directory might still hold a matching file deeper inside. `None`/`[]` both mean "no include filter."
- **Content-based binary filter** — any file `read_text()` can't decode as UTF-8 is dropped, **except** a recognized media asset (`file/media.py`'s `is_media_file()` — image/video/audio/font by extension), which survives despite being binary. This is the actual safety net for everything else: no fixed ignore list can enumerate every binary format a project might contain, but non-text is directly checkable.

## media.py

Free (no LLM call, no image decode, no third-party imaging dependency) metadata-only handling for binary media assets `collector.py`'s binary filter would otherwise drop entirely. `MEDIA_EXTENSIONS` maps a lowercase extension to a broad kind (`"image"`/`"video"`/`"audio"`/`"font"`) — deliberately excludes SVG (valid UTF-8 text, already collected/compressed as a real text file).

Two gates, not one:
- **`is_media_file(file_path)`** — extension only, no content check. Correct on its own only for `collect_files()`'s OR-style "keep if text OR media" filter, where `read_text()` already independently checks content as the other half.
- **`classify_media_file(file_path)`** — the strict version: the kind only if the extension matches *and* `read_text()` confirms the file is actually undecodable as text. Required anywhere a caller is about to *treat* a file as media (skip security scanning, skip a real text/LLM summary) — extension alone would misclassify a file that merely carries a media extension but is genuinely text (a Git LFS pointer, a secrets file renamed to `.mp3`). `scanner.py` and `packager.py`'s per-file loop both call `classify_media_file()`. `freshness.py`'s `hash_file()` is the one deliberate exception, staying on the cheap `is_media_file()` — see below for why that's still correct there.

`describe_media_file(file_path, kind)` reads a file's size, plus — for `kind == "image"` — pixel dimensions parsed from just the format's own header bytes (`_image_dimensions()`/`_jpeg_dimensions()`): hand-rolled parsers for PNG/GIF/BMP/JPEG only, `None` for anything else or an unparseable header (the caller still has a file size either way). `media_summary(file_path, kind)` formats the result into the deterministic string (`"[image asset, 1920x1080, 340KB]"`) `packager.py` uses directly as the file's `summary` — checks `width`/`height` via `is not None`, not bare truthiness, so a legitimately-parsed dimension of exactly `0` isn't treated as "couldn't parse." Never a description of what the asset actually *shows* (that needs a real, costly vision-model call, out of scope here). Always non-empty, so it never collides with the summary-failed placeholder.

Wired into three places beyond `collector.py`'s own exception: `scanner.py`'s `scan_file()` skips a media file outright (no secretlint/pattern spawn against opaque binary bytes); `freshness.py`'s `hash_file()` falls back to hashing raw bytes instead of decoded text; `packager.py`'s per-file loop builds a media file's whole `files_data` entry (empty `signatures`/`dependencies`/`api`/`compressed`) and fills `summary` with `media_summary()`'s output during extraction, keeping it out of the LLM/structural `pending` set. `classify_media_file()` is called exactly once per file, reused for both the text-reference-scan skip and the media-branch check. Other files' real references to a media file (a `.tscn`'s `ext_resource`, an `<img src>`, a README mention) still resolve correctly — `text_references.py` already matches against the collected-file-name list, and a media file simply being *in* that list is the whole mechanism.

`collect_files()` and `hash_file()` both check `is_media_file()` *before* attempting `read_text()` — a real binary file's decode attempt only fails after reading the whole file, wasted I/O a cheap extension check upfront avoids. `hash_file()`'s raw-byte fallback reads in fixed-size chunks, not one whole-file `f.read()` — this function runs at least twice per `pack()`, and `MEDIA_EXTENSIONS` has no size cap (video/audio included).

Deliberately out of scope: any actual vision-model description of an image's content, and video/audio entirely (no frame sampling, no transcription) — a separate, opt-in-only future addition, not something this free/structural tier tries to approximate.

## scanner.py

`scan_file(file_path) -> dict | None` tries `secretlint` as a subprocess first (`_scan_with_secretlint`) -- only when `_secretlint_command(root)` finds a `.secretlintrc*` in the project root and resolves the executable via `shutil.which()`; if there's no config, it isn't installed, it errors, or its JSON output doesn't parse, falls back to `_scan_with_pattern()` (the `SENSITIVE_PATTERNS` regex list, checked line-outer/pattern-inner so the *first offending line in file order* wins). `None` means safe; a match returns `{"reason": ..., "line": 1-based or None, "matched_text": that line's own text or None}` — not just a bare flag, so a reader (the pack log, `project.security_scan`, the GUI) can show why`) sees *why* without opening the file. `reason` is built through `progress_i18n.pick()`, not a hardcoded literal (`_scan_with_pattern()`'s reason follows the GUI's display language; `list_selectable_files()` renders it straight into the GUI, unlike "CLI output" which is allowed to stay Korean by convention — see `progress_i18n.py`'s own module docstring). `_scan_with_secretlint()`'s reason is secretlint's own message when it has one (always English) or the same `pick()` treatment for its own no-message fallback string. `scan_files()` keys this detail under `"file"` in its `"dangerous"` list (`[{"file": path, "reason": ..., "line": ..., "matched_text": ...}, ...]`) — a match no longer *unconditionally* excludes a file from Tree-sitter/LLM stages, just excludes it by default. Each `SENSITIVE_PATTERNS` entry captures just the value token after `=` (a quoted string, or an unquoted run limited to characters a real key/path could actually contain, not a bare `\S+`/`\S.*`, which sweeps up trailing Markdown/prose punctuation) and `_looks_like_a_real_secret(value, keyword)` judges it before a match counts at all — filters out a doc's placeholder ellipsis (`` `GEMINI_API_KEY=...` ``), a too-short placeholder (`"x"`), or an unquoted value that's really a reference to another similarly-named variable (`self._explicit_api_key = api_key`) rather than a literal. The self-reference check specifically looks for the matched keyword (normalized) *inside* the unquoted value itself, rather than rejecting every bare identifier-shaped unquoted value outright — a real unquoted secret (`.env`'s own convention, `API_KEY=abc123`) is indistinguishable in shape from a bare variable reference (`API_KEY=api_key`) by itself, but a real secret's text essentially never happens to spell out the name of the field holding it. A quoted placeholder-shaped test value (`"abc123"`) is deliberately still flagged — this stays a heuristic, not a verifier. Patterns accept `:` as well as `=` (JSON/YAML), but an unquoted value after `:` only counts in a YAML or `.env`-style file (elsewhere it's a type annotation or a variable reference); a value containing whitespace never counts unless the keyword is `PASSWORD` (help text under a key-named field). `_SECRET_SHAPES` additionally flags a line by the secret's own shape regardless of any keyword (PEM private key header, GitHub/AWS/Slack/Google/Stripe token formats). In a `.env`-style file every value is a literal: the unquoted charset widens to `\S+` and the self-reference check is skipped. In a source-code file (`_is_code_file()`: any `LANGUAGE_CONFIGS` extension except shell) the opposite holds — an unquoted value is always an expression (`database_url = str(value)`, `const recoverPassword = async ...`) and never counts. A keyword directly followed by a quote must end a quoted key (`_keyword_is_a_whole_quoted_key()`: `"db_password":` yes, `"Hide password" :` in a JSX ternary no), and a value that is one whole template slot (`"{{ password }}"`, `${X}`, `%(x)s`, `<x>`) is a placeholder. Quoted test values (`"password123"`) are still flagged by design. Field names are regex families (`*API_KEY`, `*PASSWORD`/`*PASSWD`, `*SECRET[_KEY]`, `*TOKEN`, `*PRIVATE_KEY`, `DATABASE_URL`) matched as a whole identifier (`_KEY_BOUNDARY_LEFT` also excludes `-`/`.`: `id-token: write`, `registry-auth-token:`), with an optional type annotation before `=` (`API_KEY: str = "..."`), and every match on a line is checked (`re.finditer`), not just the first. The reason names the matched field (`Pattern match: JWT_SECRET is assigned a literal value`). Values of 4 chars or fewer, placeholder shapes (`sk-...`, `changethis`, `your_...`, `xxx`, `<...>`), and interpolations (`${X}`, `$(cmd)`, or a value running into one) never count; unquoted values in Markdown/rST prose don't either, and comment lines are skipped for both `:` and `=`. `.env.example`/`.sample`/`.template`/`.dist` (`_is_env_template()`) skip field-name patterns entirely -- only `_SECRET_SHAPES` apply there, which now also cover Anthropic `sk-ant-`, OpenAI `sk-`/`sk-proj-`, Hugging Face `hf_` and npm `npm_` tokens. `_scan_with_secretlint()` reads the line from `loc.start.line` (`range` is a character-offset list).

The config gate is what made the Windows fix possible: a global npm secretlint is a `.cmd` shim a bare `"secretlint"` argv[0] can't run, and resolving it via `shutil.which()` had been reverted because it then spawned Node on every file of every project, config or not. With the gate, secretlint spawns only for projects that configured it. `scan_files()` caches each file's result per process, keyed by (path, content hash -- size+mtime above 1MB, language, secretlint command), so the repeated freshness checks behind MCP and the GUI watcher rescan only what changed (Ziplex's own scan: 1.24s cold before, 0.81s cold now with precompiled patterns, 0.04s warm); `tests/conftest.py` clears it per test.

## relationship.py

The pure dependency-graph API — no I/O.

- **`build_stem_map`/`resolve_dependency`** — matches a raw import string against the actual collected file names, via the last dotted segment. A `./`/`../` dependency is path-relative instead (`_resolve_relative_path()`): resolved against the importing file's folder, trying the literal name, TS ESM's `.js`→`.ts`, each `_RELATIVE_IMPORT_EXTENSIONS` suffix, then `index.*` (`resolve_module_path()`, shared with `ts_paths.py`'s aliases) — and never falls back to stem matching. A Python relative import (`.mod`/`..pkg.mod`, leading dots kept by the extractor, `.py`/`.pyi` source only) is resolved against the importing file's package first (`_resolve_python_relative()`: `mod.py`/`.pyi`/`mod/__init__.py`), falling back to stem matching only on a miss (`from . import helper` naming a function) — otherwise two same-named modules in different packages were a coin flip. From a Python source the stem heuristic only ever considers `.py`/`.pyi` candidates (`tests.utils.user` used to land on `frontend/tests/utils/user.ts`, `import pytest` on `pytest.ini`); absolute Python imports are normally already rewritten to exact files upstream by `py_imports.py`. A bare specifier from a TS/JS source is never stem-matched at all (it names a package; aliases/workspace packages are already rewritten to exact file names by `ts_paths.py`) — `from "react"` used to land on a local `trpc/react.tsx`. `build_stem_map()` maps a stem to a *list* of every file sharing it, not a single file name — a stem is not guaranteed unique across a project (a header/implementation pair sharing a base name, `Config.h`/`Config.cpp`, is a common C/C++ convention). A `.d.mlua` declaration file additionally gets a second, doubly-stripped alias key (`Path.stem` alone only strips one suffix, leaving `"AIComponent.d"` rather than `"AIComponent"` — see `extract/code/AGENTS.md`'s `.mlua` bullet), so a real script's bare `extends AIComponent` still resolves. `resolve_dependency()`'s exact-filename check searches every candidate; a genuinely ambiguous bare-stem match falls to `_pick_candidate()`, which prefers a header extension (`.h`/`.hpp`/`.hh`/`.hxx`) over an implementation one, since an include overwhelmingly names what's declared, never what implements it.
- **`build_tree(files)`** — for each file, splits its `dependencies` into `internal` (resolves to another collected file) and `external` (doesn't), deduping and dropping self-references entirely. This becomes the final `relationships` field in `aif.json`. Also emits a third list, `internal_text_refs` — the subset of `internal` reached *only* via `text_references.py`'s free filename-mention matching (packager.py records which raw `dependencies` entries came from that as each file's own `text_dependencies`), never also via a real Tree-sitter-resolved import to the same target; a target reached both ways counts as a genuine edge, not a text reference. This is what lets a prose mention be told apart from a structural reference once both reach `relationships` — previously a documented, permanent limitation of `text_references.py`. `get_dependents(relationships, file, include_text_refs=True)`/`get_blast_radius(...)` take that same flag (`False` excludes a dependent reached only through a text reference, at every hop of the transitive walk for `get_blast_radius`) — threaded through `query_service.py` and from there every MCP tool/GUI route built on them.
- **`get_blast_radius`** builds one reverse index and BFSes it (it used to call `get_dependents()` per visited node, O(V·E)). **`certain_edges(entry, include_text_refs)`** and **`graph_summary(relationships, *, include_text_refs, top_n, scope)`** are the shared building blocks for `query_service.get_graph_summary()` and the exports' graph-summary block; the SCC pass is iterative so a deep import chain can't hit the recursion limit.
- **`print_tree`** — recursive renderer for the CLI's `tree` subcommand.
