# src/ziplex/file/ — collection, security scan, selection, dependency graph

Scoped notes for `file/collector.py`, `file/scanner.py`, `file/selector.py`, `file/relationship.py`, `file/textutil.py`, `file/media.py`. See the root `AGENTS.md` for how these fit into the overall `pack` pipeline. Detailed history (real bugs found and fixed in each module): `docs/HISTORY.md`.

## textutil.py

Two shared low-level helpers everything else in the pipeline builds on: `read_text()` (safe UTF-8 read, `None` on anything that isn't decodable text) and `relative_key(file_path, root)` (a file's path relative to `root`, as a stable dict key — falls back to the bare filename if `file_path` isn't under `root`). `search.py` (outside `file/`) also depends on it; `packager.py` imports it as `relative_key as _rel_key`.

## collector.py

`collect_files(root_path, include=None, ignore=None)` walks the tree and excludes several ways:
- **`DEFAULT_IGNORE`** — a curated pattern list (node_modules/, build caches, OS junk) plus the project's own `.gitignore`, compiled via `pathspec.PathSpec.from_lines("gitignore", ...)` (not `"gitwildmatch"`, deprecated in the installed version). Cheap, skips whole directories before reading content, so it's the first filter, not the only one.
- **`ignore`** — extra patterns beyond `DEFAULT_IGNORE`/`.gitignore`, merged into the same `pathspec` (prunes directories the same efficient way). Typically sourced from `.ziplex.json` (`config.py`) or a `--ignore` flag.
- **`include`** — the inverse: if given, a file must match at least one pattern to survive. Applied as a post-filter on the already-collected list, deliberately *not* used to prune directories during the walk — an include pattern like `"src/**/*.py"` says nothing about whether some unrelated intermediate directory might still hold a matching file deeper inside. `None`/`[]` both mean "no include filter."
- **Content-based binary filter** — any file `read_text()` can't decode as UTF-8 is dropped, **except** a recognized media asset (`file/media.py`'s `is_media_file()` — image/video/audio/font by extension), which survives despite being binary. This is the actual safety net for everything else: no fixed ignore list can enumerate every binary format a project might contain, but non-text is directly checkable.

## media.py

Free (no LLM call, no image decode, no third-party imaging dependency) metadata-only handling for binary media assets `collector.py`'s binary filter would otherwise drop entirely. `MEDIA_EXTENSIONS` maps a lowercase extension to a broad kind (`"image"`/`"video"`/`"audio"`/`"font"`) — deliberately excludes SVG (valid UTF-8 text, already collected/compressed as a real text file).

Two gates, not one:
- **`is_media_file(file_path)`** — extension only, no content check. Correct on its own only for `collect_files()`'s OR-style "keep if text OR media" filter, where `read_text()` already independently checks content as the other half.
- **`classify_media_file(file_path)`** — the strict version: the kind only if the extension matches *and* `read_text()` confirms the file is actually undecodable as text. Required anywhere a caller is about to *treat* a file as media (skip security scanning, skip a real text/LLM summary) — extension alone would misclassify a file that merely carries a media extension but is genuinely text (a Git LFS pointer, a secrets file renamed to `.mp3`). `scanner.py` and `packager.py`'s per-file loop both call `classify_media_file()`. `freshness.py`'s `hash_file()` is the one deliberate exception, staying on the cheap `is_media_file()` — see below for why that's still correct there.

`describe_media_file(file_path, kind)` reads a file's size, plus — for `kind == "image"` — pixel dimensions parsed from just the format's own header bytes (`_image_dimensions()`/`_jpeg_dimensions()`): hand-rolled parsers for PNG/GIF/BMP/JPEG only, `None` for anything else or an unparseable header (the caller still has a file size either way). `media_summary(file_path, kind)` formats the result into the deterministic string (`"[image asset, 1920x1080, 340KB]"`) `packager.py` uses directly as the file's `summary` — checks `width`/`height` via `is not None`, not bare truthiness, so a legitimately-parsed dimension of exactly `0` isn't treated as "couldn't parse." Never a description of what the asset actually *shows* (that needs a real, costly vision-model call, out of scope here). Always non-empty, so it never collides with the summary-failed placeholder or trips `confidence.py`'s check for it; `signatures` is always `[]` for a media file, so `estimate_confidence()` gives it the same free `1.0` a trivial text file gets.

Wired into three places beyond `collector.py`'s own exception: `scanner.py`'s `scan_file()` skips a media file outright (no secretlint/pattern spawn against opaque binary bytes); `freshness.py`'s `hash_file()` falls back to hashing raw bytes instead of decoded text; `packager.py`'s per-file loop builds a media file's whole `files_data` entry (empty `signatures`/`dependencies`/`api`/`compressed`) and fills `summary` with `media_summary()`'s output during extraction, keeping it out of the LLM/structural `pending` set. `classify_media_file()` is called exactly once per file, reused for both the text-reference-scan skip and the media-branch check. Other files' real references to a media file (a `.tscn`'s `ext_resource`, an `<img src>`, a README mention) still resolve correctly — `text_references.py` already matches against the collected-file-name list, and a media file simply being *in* that list is the whole mechanism.

`collect_files()` and `hash_file()` both check `is_media_file()` *before* attempting `read_text()` — a real binary file's decode attempt only fails after reading the whole file, wasted I/O a cheap extension check upfront avoids. `hash_file()`'s raw-byte fallback reads in fixed-size chunks, not one whole-file `f.read()` — this function runs at least twice per `pack()`, and `MEDIA_EXTENSIONS` has no size cap (video/audio included).

Deliberately out of scope: any actual vision-model description of an image's content, and video/audio entirely (no frame sampling, no transcription) — a separate, opt-in-only future addition, not something this free/structural tier tries to approximate.

## scanner.py

`scan_file(file_path) -> dict | None` tries `secretlint` as a subprocess first (`_scan_with_secretlint`); if it errors, isn't installed, or its JSON output doesn't parse, falls back to `_scan_with_pattern()` (the `SENSITIVE_PATTERNS` regex list, checked line-outer/pattern-inner so the *first offending line in file order* wins). `None` means safe; a match returns `{"reason": ..., "line": 1-based or None, "matched_text": that line's own text or None}` — not just a bare flag, so a human reviewing it (`selector.py`'s `review_dangerous_files()`, `gui/pack_service.py`'s `list_selectable_files()`) sees *why* without opening the file. `scan_files()` keys this detail under `"file"` in its `"dangerous"` list (`[{"file": path, "reason": ..., "line": ..., "matched_text": ...}, ...]`) — a match no longer *unconditionally* excludes a file from Tree-sitter/LLM stages, just excludes it by default.

Known gap: on Windows, secretlint's global npm install is a `.cmd` shim `subprocess.run()` can't resolve without `shell=True`/`shutil.which()` first, so every call raises `FileNotFoundError` and falls back to the regex path. Resolving via `shutil.which()` was tried and reverted — it also makes secretlint actually spawn (a real Node process) on every scanned file on every platform, even a project with no `.secretlintrc` at all, meaningfully slower. Left as today's fast-but-Windows-broken behavior.

## selector.py

`select_files()`: thin interactive terminal prompt over the scanner's `"safe"` list. Skipped entirely by `pack --auto` (or the `tokens`/`collect` CLI subcommands, which never call it).

`review_dangerous_files(dangerous, root_path) -> list[str]` — prints each flagged file's reason + matched line and lets specific ones be included anyway, returning their raw paths for `packager.pack()` to fold into `safe_files` before selection runs (so `--auto`, the interactive picker, and `preselected` all treat an approved file exactly like any other safe one from that point on). Gated by `interactive` (`--auto-correct`'s *absence*), not `auto` — the same switch as every other "can we ask the terminal something" decision in the pipeline. Non-interactive callers (`--auto-correct`) keep the old behavior: excluded, no prompt.

The GUI reaches the same outcome without a terminal: `pack()`'s `preselected` handling trusts a name from `dangerous` exactly like one from `safe_files`, since the GUI's file-selection screen already showed the identical reason/matched-line detail as a checkbox before ever calling `start_pack_job()`.

## relationship.py

The pure dependency-graph API — no I/O, callable from a terminal flow (`corrector.py`) or the GUI.

- **`build_stem_map`/`resolve_dependency`** — matches a raw import string against the actual collected file names, via the last dotted segment. `build_stem_map()` maps a stem to a *list* of every file sharing it, not a single file name — a stem is not guaranteed unique across a project (a header/implementation pair sharing a base name, `Config.h`/`Config.cpp`, is a common C/C++ convention). `resolve_dependency()`'s exact-filename check searches every candidate; a genuinely ambiguous bare-stem match falls to `_pick_candidate()`, which prefers a header extension (`.h`/`.hpp`/`.hh`/`.hxx`) over an implementation one, since an include overwhelmingly names what's declared, never what implements it.
- **`build_tree(files)`** — for each file, splits its `dependencies` into `internal` (resolves to another collected file) and `external` (doesn't), deduping and dropping self-references entirely. This becomes the final `relationships` field in `aif.json`.
- **`has_cycle(files, stem_map, from_file, to_file)`** — checks whether `from_file` already (transitively) depends on `to_file`. **Direction matters and is easy to get backwards**: `move_file()` is about to add the edge "`to_file` depends on `from_file`" (a dependency entry is a *child* in the tree), and that closes a cycle exactly when `from_file` can already reach `to_file` by walking its own existing dependency chain — so the walk starts at `from_file`, not `to_file`. `tests/test_relationship.py::test_has_cycle_detects_transitive_cycle_through_a_third_file` is the regression guard for this exact direction — keep it passing if you touch this function.
- **`move_file(files, file_name, new_parent)`** — reparents `file_name`, first stripping it from wherever it's currently listed as a dependency, then appending it to `new_parent`'s `dependencies`. Raises `ValueError` for an unknown/self target, `CycleError` (via `has_cycle`) if the move would close a loop. CLI-only (`corrector.py`'s `correct_relationships()`) — the GUI uses `add_dependency`/`remove_dependency` instead, since `move_file`'s "strip from every existing reference" step is wrong for a file with more than one real parent.
- **`add_dependency(files, file_name, target)`** / **`remove_dependency(files, file_name, target)`** — the pure link/unlink pair `gui_server.py`'s relationship editor is built on. Each touches only `file_name`'s own `dependencies` list, unlike `move_file`, since `dependencies` is a graph, not a tree — a file can legitimately have more than one real parent. `add_dependency` runs the same `has_cycle` guard, walked in the direction matching the edge being added (`file_name -> target` closes a cycle when `target` can already reach `file_name`); it blocks a *newly* introduced cycle but never touches an already-existing one it didn't create. `remove_dependency` never needs a cycle check. Both no-op when there's nothing to do.
- **`print_tree`** — recursive renderer for the CLI's `tree` subcommand; separate from (but shaped like) `corrector.py`'s own interactive tree renderer, which needs per-line index numbers for file selection.
