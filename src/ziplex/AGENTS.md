# src/ziplex/ — core pipeline (LLM layer, checkpointing, orchestration, editing API)

Scoped notes for the modules living directly under `src/ziplex/*.py` — everything `pack()` calls that isn't already covered by a more specific nested doc (`extract/code/`, `extract/text/`, `file/`, `gui/` each have their own `AGENTS.md`, linked from the root `AGENTS.md`). The root file keeps the numbered pipeline overview (steps 1-10) short and points back here for steps 3-7 and 9; read this file before touching any of the modules below.

## Step 3 — `tokenizer.py`

Counts tokens per model. `MODEL_ENCODINGS` (GPT-4o/GPT-3.5/GPT-4) are exact `tiktoken` counts; `MODEL_MAX_TOKENS` additionally carries Claude and Gemini, which have no public tiktoken-compatible tokenizer — `_count_for_model()` falls back to a character-based estimate (`APPROX_CHARS_PER_TOKEN`, ~Anthropic's own documented rule of thumb) for those, and every result dict carries `approx: bool` (`is_approx_model()`) so a caller (the `tokens`/`pack` CLI printers append "(근사치)") never presents a guess with the same confidence as a real count. `analyze_tokens_with_compression` (the `tokens` command) measures original vs. compressed body; `analyze_tokens_with_payload` (used by `pack`) measures original vs. just the per-file `summary` — the only per-file field that ships in `aif.json`. A media asset has no readable "original" (correctly 0 there) but its real `summary` is still counted on the payload side.

## Step 4 — `llm.py`

Three providers today (`GeminiProvider` default, `OpenAIProvider`, `ClaudeProvider`) + `MockProvider` for tests, behind `PROVIDERS`/`_active_provider()`. `GeminiProvider` calls Gemini's REST API directly (not the SDK). Model/key resolution is re-resolved fresh on every call, not cached at construction — explicit constructor arg → `settings.py` (GUI Options page) → env var → `GeminiProvider.DEFAULT_MODEL` (`gemini-flash-latest`, a floating alias; pin `GEMINI_MODEL`/the GUI's model field if you hit persistent 503s). Every Gemini request sends `generationConfig.thinkingConfig.thinkingBudget: 0` — none of this file's prompts (short, single-shot, "JSON only" extraction) need Gemini's extended "thinking" mode, and leaving it on bills real hidden output tokens. `analyze_batch_summaries(items)` bundles several files' signatures/dependencies (or truncated content) into one prompt/response, cutting request *count* (what drives 429/503) roughly by `summarizer.BATCH_SIZE`; `analyze_file_summary`/`analyze_text_summary` are the batch's per-file fallback. Every provider retries HTTP 429/5xx and transport-level failures (`requests.exceptions.RequestException`/`json.JSONDecodeError`) with backoff — `min(5*(attempt+1), MAX_RETRY_WAIT_SECONDS)` (50s cap), logged as a wait time plus a `[label]` prefix naming which file/batch/call is retrying, not an attempt counter — and carries an explicit `timeout=REQUEST_TIMEOUT` (60s), since `requests` has no default. Every `analyze_*()` function takes `lang: str = "en"` (`llm.LANGUAGE_NAMES`) and appends a one-line "write the value in {language}" instruction — the JSON *key* always stays English, the *value* follows `lang`. The three per-file summary prompts also carry `_IDENTIFIER_FIDELITY_NOTE` ("keep function/class/variable/file names exactly as written, don't translate them") — `confidence.py`'s word-overlap scoring can only find a match when the summary literally shares vocabulary with the source, which for non-English `lang` mostly only happens via an untranslated identifier. `analyze_prompt()`'s own instruction explicitly tells the model to focus on the project's purpose and not center the summary on the `rules` param's coding-style/naming conventions — see `packager.py`'s own bullet below for why `architecture` (its other input) needed a real data fix too, not just a wording one. `analyze_folder_summaries(folders, lang)` is the newest `analyze_*()` function — one call covering every folder in a project at once (see `folder_summary.py`'s own paragraph below).
`OpenAIProvider` speaks the Chat Completions shape (works against real OpenAI, Ollama, LM Studio, vLLM, llama.cpp, OpenRouter, Groq — point `base_url`/`model`). `ClaudeProvider` is Anthropic's Messages API. `LLMProvider` (a `typing.Protocol`) is the seam for adding another provider — implement `generate(prompt, retry, label) -> str` and register it in `PROVIDERS`. `PROVIDERS["mock"]` (`MockProvider`) pattern-matches the JSON field name in a prompt's trailing example, network-free. Select the process-lifetime default via `LLM_PROVIDER=mock`/`openai`/`claude`; `settings.py`'s `resolve_llm_provider_name()` (the GUI Options page) wins over that when set, constructing a fresh provider instance per call so a switch takes effect on the very next pack. `DEFAULT_PROVIDER_NAME` (`"gemini"`) is the one named constant behind that `os.getenv("LLM_PROVIDER", ...)` fallback — `cli.py`'s `ziplex settings` imports it (plus each provider's own `DEFAULT_MODEL`/`DEFAULT_BASE_URL`) to print its unset-field hints, rather than a second hardcoded copy of the same defaults that could drift out of sync (a real code-review finding). `GeminiProvider.resolved_model` is a property split out of what used to be inlined only in its `url` property, for the same single-source-of-truth reason. `describe_active_provider()` is a read-only snapshot of what the *next* `generate()` call would actually do (provider name, resolved model, whether an API key is present — never the key itself) without spending a real request — built on `_active_provider()`'s own real precedence rather than a second reimplementation of it; `doctor.py` is its one caller.

## Step 5 — `checkpoint.py`

`pack()`'s checkpoint/resume system, split out of `packager.py`. `handle_llm_failure()` lets a failing LLM call be retried, answered manually, or checkpointed to `checkpoint/<project_name>-<hash>.json` (hash = first 8 hex of sha256 of the resolved absolute path — prevents two different projects sharing a folder basename from colliding; safe to key on the raw path since this file is purely local/ephemeral, deleted on success, never committed the way `aif.json`/`detail.json`/`cache.json` are). `resume_checkpoint_choice()` is the matching question for a checkpoint found at a run's *start*. `pack(interactive=False)` skips every prompt either could raise, defaulting to checkpoint-and-exit / always-resume. `build_snapshot()` builds the `{project, rules, files_data}` dict, keyed by relative name; `pack()`'s `check_cancelled` reuses the same `build_snapshot()`/`save_checkpoint()` pair for a user-requested stop. `build_snapshot(lang=...)`/`unpack_snapshot()` also carry `project.language` — a resumed run's restored `rules`/`prompt`/per-file `summary` are only trusted when the checkpoint's own `lang` matches the resuming run's (`lang_matches`); a mismatch discards just that content, not the checkpoint's other data. A missing `lang` field defaults to `"en"`. `list_checkpoints()`/`clear_all_checkpoints()` back the `ziplex checkpoint`/`ziplex checkpoint clean --all` CLI subcommand (`cli.py`) — the former reads each leftover file's own recorded `project.name`/`files_data` rather than the filename (the hash suffix is a one-way sha256 digest, unrecoverable back into a project path), listing rather than dropping a file that fails to parse so `clean --all` still has something to remove.

## Step 6 — `summarizer.py`

`generate_summaries(pending, root, lang)` is `pack()`'s entry point when an LLM is available: batches `pending` into `BATCH_SIZE`-sized chunks (`chunked()`, by relative name), submits one future per chunk to a `MAX_WORKERS` thread pool. `request_batch_summaries()` falls back to per-name `request_summary()` for anything a batch response missed. `generate_structural_summaries(pending, root, lang)` is the `use_llm=False` counterpart — no network, each summary a deterministic one-liner from the file's own already-extracted `signatures`/`dependencies` (`_structural_summary()`), synchronous. `lang` feeds both `llm.py`'s prompts and `_STRUCTURAL_LABELS` (Ziplex's own fixed labels follow the chosen language too). `SUMMARY_FAILED_PLACEHOLDERS: dict[lang, str]` + `is_summary_failed_placeholder(summary)` (recognizes the placeholder in *any* supported language, since a cached previous-pack summary may be from a different `lang` than the one checking it) is the fallback for a failed summary. The per-file progress log prints `✅ <name>` for a real summary, `❌ <name> (...)` for a placeholder — never the same line for both.

## Step 7 — `packager.py` (`pack()`)

Orchestrates every other step in this file plus `text_references.py` for non-code files and `folder_summary.py` for per-folder summaries: the pipeline stitcher, not owner of checkpointing or summary generation. `tech_stack` (`detect_tech_stack()`) is computed once, before rules/prompt, not just at final assembly — `_build_architecture_summary(rel_files_data, tech_stack)` feeds it plus every file's already-generated `summary` (capped at `MAX_ARCHITECTURE_FILES`) into `analyze_prompt()`'s `architecture` param, which used to always be `[]` (a dead parameter, never populated) -- the confirmed root cause of a real, reported problem: the AI guide reading like a coding-style blurb rather than a "what is this project" summary, since project_name plus a coding-rules list was *all* it ever had to work with. `use_cache=True` (default; `--no-cache` disables) auto-detects a previous successful pack at `RESULT_DIR` and reuses its `summary` for any file whose content hash still matches (`freshness.load_previous_summaries()`) — only `summary` is reused; `signatures`/`dependencies`/`api`/`compressed` are always freshly extracted (so a human's prior manual reparenting via `corrector.py`'s `move_file()` never rides along with stale dependency data), and `relationships` is always rebuilt from scratch. `use_cache=False` also discards a leftover checkpoint before it's ever unpacked (no interactive prompt either) -- `discard_checkpoint: bool | None = None` overrides just this half independent of `use_cache`: `None` (every CLI call, and the GUI's own fresh pack-form submission) keeps that behavior; an explicit `False` (only ever sent by the GUI's "다시 시도" retry button, see `gui/pack_service.py`'s `start_pack_job(resume=...)`) forces a leftover checkpoint to always resume regardless of what `use_cache` says -- without it, retrying a job that started with "완전히 재패킹" checked discarded the very checkpoint that same job's own failure had just saved, re-billing every file's summary on every retry. That forced resume still verifies the checkpoint's own restored file set is a subset of `preselected` before trusting it, unconditionally discarding it on a mismatch (never falling back to `not use_cache` there -- "does this checkpoint belong to me" and "should I trust my own summary cache" are independent questions, and a positively-identified mismatch must be discarded regardless of `use_cache`) -- checkpoints are keyed by project path only, never by which job produced them, so two overlapping pack attempts for the same project (a second tab, or a stale error screen retried after a different job already ran) could otherwise silently resume the wrong one's partial progress instead of failing safe. If a reused summary is a failure placeholder (any language), `pack(interactive=True)` asks once whether to regenerate those specific files (`_confirm_regenerate_failed_summaries()`); non-interactive callers leave it cached, since `confidence.py`'s forced `0.0` already flags it for review either way. `use_llm=False` (CLI `pack --no-llm`) skips every LLM call: summaries fall back to `generate_structural_summaries()`, `rules` stays `[]`, `prompt` becomes the fixed `STRUCTURAL_ONLY_NOTE[lang]` — a checkpoint's own restored `rules`/`prompt` are only honored when `use_llm and lang_matches` both hold, never partially. `check_cancelled` is `pack()`'s only way to be told to stop from outside its own thread — polled at three points (per-file during extraction, before the LLM summary step, right after it) via `_maybe_stop()`, which checkpoints before returning `{}` unless told to discard. Only meaningful for a caller running `pack()` on a background thread (the GUI); a synchronous CLI run leaves it unset. `result_dir` overrides where the `use_cache` lookup looks — not where *this* run's own output saves (`save_aif()`'s `output_path` handles that, separately). `lang: str = "en"` (CLI `--lang`, GUI dropdown) picks which language every LLM-written value — each file's `summary`, `rules`, `prompt` — is actually written in, independent of the GUI's own display-language switcher (`js/i18n.js`, which only ever translates the GUI's own chrome). Silently normalized to `"en"` for an unrecognized value. Recorded verbatim as `project.language`.

`packager.py` (`save_aif()`) is also step 10 of the pipeline — splits `compressed` per file → `<name>.detail.json` (so the saved `aif.json` only ever carries `summary`) and the flat `_manifest` (a `{file: content hash}` map, see `freshness.py` below) → `<name>.cache.json`.

## Step 9 — `corrector.py`

The thin interactive CLI wrapper around the pure editing API (`edits.py`, `file/relationship.py` — see `src/ziplex/file/AGENTS.md`): walks the user through project name/guide/rules/summaries/folder summaries/reparenting, calling the matching pure function per accepted change. `--auto-correct` skips it entirely, calling `edits.finalize_aif()` directly. Per-file review is triaged by `confidence.triage()` — only files below `REVIEW_THRESHOLD` get prompted, each with its real extracted `signatures` (capped at 10, "+N more") shown alongside the summary. Per-folder review (via `edits.set_folder_summary()`) is triaged the same way, on `folder_summary.group_confidence_by_folder()`'s aggregate score (the average of the folder's own member files' already-scored confidence, not an independently verified signal — a folder summary's own wording is never checked against anything) — same triage, same threshold, just one level up; only flagged folders are prompted, the rest auto-kept and printed same as `pack_service.py`'s GUI review screen. `correct_relationships()`'s own reparent loop (one `move_file()` per numbered pick, no search) doesn't scale past a handful of files — a real, reported pain point, not just a theoretical one — so it now prints a one-line pointer at the top toward `ziplex-gui`'s relationship editor or the post-pack `ziplex link`/`ziplex unlink <aif_path> <file> <target>` CLI commands (`cli.py`'s `_edit_saved_relationship()`, wrapping `add_relationship`/`remove_relationship` directly — no interactive loop, no locking machinery a one-shot invocation doesn't need) for anything past a quick fix or two; the loop itself stays as the fallback for a GUI-less environment.

## Relationship enrichment beyond code imports

**`text_references.py`** extends `relationships` past code files, for free (no LLM call). A file with no Tree-sitter grammar always got `dependencies=[]` from `extract_dependencies()`. `find_text_references_for_file(file_path, name, all_names)` matches a non-code file's raw text against the *actual* collected-file list (full relative path, or bare filename+extension, both word-boundary anchored) — a bare stem alone is never matched (too much noise from common words). A match goes straight into that file's `dependencies`, same as a resolved import. `pack()` keeps matches in a side dict (`text_refs_by_path`) through the whole per-file loop and the LLM summary step, merging into `files_data[fp]["dependencies"]` only afterward — `summarizer`'s summary prompt switches from content-based to signature/dependency-based the moment `dependencies` is non-empty, so merging earlier would swap a text file's content-based prompt for a signatures-empty/dependencies-only one before it's ever actually summarized. Also wired into the standalone `tree` CLI subcommand. The same merge step also records the match separately as `files_data[fp]["text_dependencies"]` (a subset of `dependencies`, exact file names only) — this is what lets `build_tree()` tag a prose mention apart from a structural/import reference once both reach `relationships` (see `file/relationship.py`'s bullet in `src/ziplex/file/AGENTS.md`), closing what used to be a documented, permanent limitation here.

**`go_packages.py`** — closes a different, Go-specific gap the same way `text_references.py` closes its own: `_go_dependency_handler` (`extract/code/languages.py`) only ever returns a Go import's raw path string, but that path names a *package* (typically a whole directory of files), not a single file the way every other supported language's imports resolve — `resolve_dependency()`'s file-stem matching has nothing to match it against, so an internal multi-package import used to always resolve as "external." `read_go_module_path(root_path)` reads go.mod's own `module` directive (root-level only, same scope limit `tech_stack.py`'s own manifest scan takes); `build_go_package_index(all_names)` groups every collected `.go` file by its own directory; `expand_go_dependencies(deps, self_name, module_path, index)` is the one place that turns a package import into the concrete files that make it up, run on every `.go` file's raw `extract_dependencies()` output before it ever reaches `resolve_dependency()`. Free (no LLM call), and zero-cost for a non-Go project (`read_go_module_path()` returns `None` the moment there's no go.mod, and every real caller gates on that). `packager.py`'s per-file loop and `cli.py`'s `tree` subcommand are today's only two callers — both call it the same way, on purpose: `text_references.py`'s own equivalent merge step already drifted between two call sites once (a real bug caught by code review), and the CLI's now-removed `analyze` subcommand was itself missed on this feature's first pass for exactly that reason, caught by the very next code review before it shipped — a cautionary example of the maintenance cost a near-duplicate CLI code path carries, not just this one feature's own gap.

## Project-level fact blocks (free, no LLM call)

**`tech_stack.py`** — manifest-file-based fact block: `detect_tech_stack(root_path)` scans the project root's top level (not recursive) for known package-manager manifests (`package.json`/`requirements.txt`/`pyproject.toml`/`Cargo.toml`/`go.mod`/`Gemfile`/`composer.json`/`pom.xml`) and reads out each one's declared top-level dependency names (version specifiers stripped, capped at `MAX_DEPENDENCIES`, deduped). `package_manager` for `pyproject.toml` is derived per-manifest (`_pyproject_package_manager()`) rather than a flat label — `[tool.poetry.dependencies]` present → `"poetry"`, `[project]` present → `"pip"`, neither → the old `"poetry/pip"` fallback for a genuinely ambiguous manifest. Attached unconditionally as `project.tech_stack` (`[]` if none found); `skill_export.py`'s `references/overview.md` renders it when present, and the GUI's Overview page renders it too. Deliberately shallow — no lockfile resolution, no transitive walking. Note: this field only ever reflects what a manifest *declares as a dependency* — it is not a general "what languages/frameworks does this project use" signal, and in particular is not where Ziplex's own supported-language list lives (that's `extract/code/languages.py`'s `LANGUAGE_CONFIGS`, a completely separate table never exposed through `tech_stack`).

**`folder_summary.py`** — the aggregate-level counterpart to per-file summaries: one sentence per folder describing its role, attached as `aif["folders"] = {folder path: {"summary": ..., "confidence": float}}`. `group_files_by_folder(files_data)` groups by each file's *immediate* parent directory (`Path(name).parent.as_posix()`, `"."` for a root-level file — not a special-cased sentinel). `generate_folder_summaries()` is a single batched LLM call covering every folder at once (a project's folder count is always far smaller than its file count, so this never needs `summarizer.py`'s own chunking/thread-pool machinery) — falls back to a free structural sentence (`"Contains N file(s): ..."`, capped list) per folder the response didn't cover, rather than a retry loop. `generate_structural_folder_summaries()` is the `use_llm=False` counterpart, same shape as `summarizer.generate_structural_summaries()`. `group_confidence_by_folder(files_data)` is the folder-level counterpart to `confidence.estimate_confidence()` — not an independently verified signal (a folder summary's own wording is never checked against anything), just the average of its own member files' already-computed per-file `confidence`, surfaced one level up so `packager.py` can attach a `confidence` to every folder and `corrector.py`/`pack_service.py`'s review flow can `confidence.triage()` folders exactly like files instead of always showing every one. Deliberately lighter-weight than rules/prompt/per-file summaries in one respect still: a folder-summary failure is *not* wired into `checkpoint.handle_llm_failure()` at all (no checkpoint schema footprint for this).

`cli.py`'s `pack --max-tokens N [--max-tokens-model MODEL]` is a CI-guard flag: after a normal pack completes, `_check_max_tokens()` (pure, testable without argparse) compares the chosen model's actual packed-payload token count against `N`; `main()` turns a failing/unknown-model result *or* a missing `aif` entirely (a checkpoint-and-exit, or a cancelled/empty run) into a non-zero exit — either way should fail a CI pipeline expecting a real, complete pack.

## Freshness, confidence, search

**`freshness.py`** sits outside the `pack` sequence but is also called by it: `check_freshness(file_paths, root, manifest)` re-hashes a project's current files and diffs them against a loaded manifest into a `FreshnessReport` (`changed`/`added`/`removed`/`unchanged`, plus `is_stale`), no Tree-sitter parsing, no LLM calls. `hash_file()` hashes a recognized media asset's raw bytes instead of decoded text. `freshness_candidate_files(scan_result, root, manifest)` is what every real caller passes as `file_paths`: unions `scan_result["safe"]` with any `scan_result["dangerous"]` entry whose relative key is already present in `manifest` — a file a human included anyway despite being flagged sensitive gets re-flagged as dangerous on every later scan regardless, so without this it would be reported as permanently `removed` even though it's unchanged and on disk; checked against the manifest specifically so a dangerous file that's genuinely never been packed doesn't flip to spurious `"added"` noise. `check_freshness_scoped(project_path, manifest, extra_include=None, extra_ignore=None)` wraps `collect_and_scan() → freshness_candidate_files() → check_freshness()` in one call — every real freshness caller (the `freshness` CLI subcommand, `query_service.check_freshness()`, `query_service._stale_warning()`, `gui/watcher.py`'s recompute) goes through this now rather than open-coding the sequence itself. `extra_include`/`extra_ignore` are `collect_and_scan()`'s own same-named params, threaded through so a project packed with a one-off `pack --include`/`--ignore` CLI extra (on top of whatever `.ziplex.json` already says) doesn't get diffed here against an unscoped file tree — `.ziplex.json` is already reproducible from disk on its own, but a CLI-only extra isn't persisted anywhere *except* `project.scope` (see `packager.py`'s aif assembly), which every real caller now reads back via the shared `load_pack_scope(aif_path)`. `load_previous_summaries(root_path, selected, result_dir, lang)` is the actual staleness-stage-2 cache-reuse lookup `pack()` calls before deciding what's `pending`: returns `{}` outright (full cache miss) when the previous pack's own `project.language` doesn't match the requested `lang`, and requires at least `_MIN_OVERLAP_RATIO` (0.5) of the *current* file set to already appear in the previous manifest before trusting any of it (guards against two unrelated projects sharing a result-directory basename).

The `freshness` CLI subcommand exits 1 when `report.is_stale` — doubles as a free PR/CI gate (no LLM calls, no `GEMINI_API_KEY`) for a project that commits its Ziplex output (README's Team use section). Template: `docs/ci/freshness-gate.yml`.

**`doctor.py`** — network-free environment sanity check behind `ziplex doctor [project_path]`. `run_diagnostics()` is pure (returns a dict, no printing — `cli.py`'s `_print_doctor()` is the only renderer): Python version vs. `_min_python()`'s minimum, `llm.describe_active_provider()`'s snapshot, `settings.SETTINGS_PATH.exists()`, `checkpoint.list_checkpoints()`'s count, plus (only when `project_path` is given) that project's own `.env`/`.git` presence. `_min_python()` reads the real minimum straight off `pyproject.toml`'s own `requires-python` (same `tomllib`/`tomli` fallback `tech_stack.py`'s own TOML parsing already uses) rather than a hardcoded second copy — a code-review finding: a stale duplicate here would keep reporting `python_ok=True` even after `pyproject.toml` itself raised its minimum; degrades to `_FALLBACK_MIN_PYTHON` (never raises) when `pyproject.toml` isn't reachable (a real installed wheel doesn't bundle it) or doesn't parse. `_secretlint_available()` is the one bit of real I/O beyond file/env reads — a `secretlint --version` subprocess probe mirroring `scanner.py`'s own real invocation shape (not just `shutil.which()`, which doesn't reliably catch the same documented Windows `.cmd`-shim gap `scanner.py` already has); unavailable reports informationally, never as an error, since `scan_file()` already has a working regex fallback either way.

**`search.py`** sits outside the `pack` sequence — pure query functions over an already-collected file set or an already-generated `detail.json`. `search_files()` regex-searches original file content, not `compressed` (a match inside a body-stripped function would otherwise be invisible). `read_detail_range()` slices a `detail.json` entry's `compressed` text by 1-based line range. Exposed via `search`/`detail` CLI subcommands and wrapped directly by the MCP server.

**`confidence.py`** — a free (no LLM call) heuristic for whether a summary is worth trusting: `estimate_confidence(summary, signatures)` tokenizes both (camelCase/snake_case-aware, single-suffix-"s" stemmed) and scores 0.0-1.0 by keyword overlap, capped at 3 matches so a file with many functions isn't penalized for a summary that abstracts over most of them. `1.0` when there are no signatures to check at all (text files) — **except** when `summary` is exactly a failure placeholder, forced to `0.0` regardless of signature count. `triage(files)` splits by `REVIEW_THRESHOLD` (0.34) into (needs_review, auto_kept) for `corrector.py`'s per-file loop. Not a correctness guarantee — a summary using different (but accurate) words for the same idea scores exactly like a wrong one, and this can't tell the difference. Known, currently unresolved limitation: systematically under-scores non-English `lang` output even with `_IDENTIFIER_FIDELITY_NOTE` in place, since a good one-line summary is *supposed* to abstract away from literal identifier names — tracked as an open GitHub issue, not something a pure word-overlap heuristic can close without either an LLM re-verification call (breaks the "free" design) or a hand-maintained glossary that only ever covers generic vocabulary, not a project's own domain-specific terms.

## Read-only query layer

**`query_service.py`** — the transport-agnostic read-query core `mcp_server.py` and `gui_server.py` both sit on top of. Nine functions (`get_overview`, `list_files`, `get_folders`, `get_relationships`, `get_dependents`, `get_blast_radius`, `get_detail`, `check_freshness`, `search_project`) over `edits`/`file/relationship`/`search`/`freshness`'s existing pure functions -- `get_folders` is the one exception reading a raw `aif.json` field directly (`aif.get("folders", {})`, `{}` for a project packed before the field existed) rather than wrapping a function from one of those modules, same shallow shape `list_files`'s own `files` read already has. Read-only by design — every function reads an already-packed `aif.json`/`detail.json`/`cache.json`, or (for `search_project`/`check_freshness`) re-collects and re-scans fresh from disk; none of them re-pack or re-correct a project. `get_dependents`/`get_blast_radius` are graph queries over the *human-corrected* `relationships` tree (`get_blast_radius` can legitimately include the queried file itself when it participates in an import cycle). `get_overview`/`list_files` take an optional `project_path` — when given, `_stale_warning()` (built on `check_freshness_scoped()`) adds a `"_stale"` key only if the pack has actually drifted. `search_project(..., max_results=DEFAULT_SEARCH_MAX_RESULTS)` caps its match count (returning `{"matches": [...], "truncated": bool}`, not a bare list) — a broad/common pattern against a real project can otherwise return hundreds of matches in one call at real per-token cost to an MCP client; `search_files()` (`search.py`) itself stops scanning early once the cap is hit rather than truncating a fully-collected list, and `max_results=None` restores the old unlimited behavior (what `gui_server.py`'s `/api/search` route passes, unwrapping `["matches"]` back to a bare list for its own unchanged response shape — a human browsing the GUI pays no per-token cost). `check_freshness()` reports `"unchanged_count"` (an int), not the full `unchanged` file list — nothing on the reading end ever used the names themselves (the GUI never rendered them; `freshness.py`'s own `load_previous_summaries()` reads `FreshnessReport.unchanged` directly for cache-reuse, a separate, internal consumer of the pure `freshness.py` layer this dict has nothing to do with), and the list was measured to be the majority of the whole response's size for a real, mostly-unchanged project. `list_files(..., folder=None, confidence_below=None)` and `get_relationships(..., files=None)` close the same "response grows with project size" gap for the two tools `search_project`/`check_freshness` didn't cover — measured directly against Ziplex's own 115-file self-pack: an unscoped `list_files` costs ~5,000 tokens, an unscoped `get_relationships` ~9,400 (the single priciest of the nine tools). Both new params are opt-in (no forced cap, unlike `search_project`'s) since there's no one "too many files" threshold that fits every project size; `folder` matches `get_folders()`'s own path convention (`"."` for root-level files, with a trailing slash or `""` normalized to match rather than silently matching nothing) for drilling into one folder after `get_folders()` names it, `confidence_below` takes any cutoff a caller wants rather than a fixed on/off switch — pass `confidence.REVIEW_THRESHOLD` for the same triage `corrector.py` already applies in its own human-review loop, or a stricter/looser one — and `get_relationships`'s `files` param silently skips a name not present in the graph rather than raising, since a caller scoping it is narrowing a graph it can already see the keys of (typically via `list_files()`), not looking one up blind the way `get_detail()` does. `parent_folder(name)` (`file/textutil.py`) is the one shared place "a file's immediate containing folder, POSIX-normalized, `.` for root" is computed — `folder_summary.py`'s `group_files_by_folder()`, `go_packages.py`'s `build_go_package_index()`, and this `folder` filter all call it instead of each re-deriving `Path(name).parent.as_posix()` inline, so the root convention can't drift between them.

## Per-user / per-project config

**`config.py`** — an optional per-*target*-project `.ziplex.json` (in whatever project `pack` is pointed at, not Ziplex's own repo): `load_config()` never raises, falling back to `DEFAULT_CONFIG`. Scoped to just `include`/`ignore` glob-pattern lists. `pack()` loads it via `load_config(root_path)` and unions it with any CLI `--include`/`--ignore` — CLI flags augment the config file, never replace it. `pack_service.py`'s `list_selectable_files()` (GUI) loads the same config the same way. `init_config()` (the `init` CLI subcommand) scaffolds a starter file; idempotent.

**`settings.py`** — `config.py`'s per-*user* counterpart: one `~/.ziplex/settings.json` holding where the GUI's new-pack screen saves by default (a global `output_dir` plus per-project pins in `project_output_dirs`, a pin only ever written when a human types an explicit output path while packing that project) and every LLM provider's credentials/model (`gemini_api_key`/`gemini_model` and the `openai_*`/`claude_*`/`llm_provider` siblings). Resolved fresh on every LLM call, not cached — a key/model/provider switch in the GUI Options page has to take effect on the very next pack. `load_settings()` never raises. `EDITABLE_FIELDS` is the one shared whitelist of directly-writable fields (`project_output_dirs` deliberately excluded — see its own docstring), read by both `gui_server.py`'s `POST /api/settings` and the `ziplex settings`/`ziplex settings set <key> <value>` CLI subcommand (`cli.py`) — a CLI-only user's counterpart to the Options page, for anyone switching LLM provider/model or the default output folder without ever opening the GUI. `ziplex settings` masks every `*_api_key` field to its last 4 characters on print (`cli._mask_secret()`); the value is still stored and sent to the provider in full, only display is masked. See `src/ziplex/gui/AGENTS.md` for the Options-page wiring.

## Distribution channels

**`skill_export.py`** — a third distribution channel alongside the MCP server and the GUI: `export_skill(aif_path)` turns an already-corrected `aif.json` (+ `detail.json`) into a Claude Agent Skill directory (`.claude/skills/<slugified project name>/` — `SKILL.md` plus `references/overview.md`/`files.md`/`relationships.md`/`detail.json`), which Claude Code progressively loads on its own with no server process running. Deliberately narrower than repomix's own `--skill-generate` — `references/files.md` stays to summaries + confidence (matching `aif.json` itself); the *compressed* (not raw) per-file body only ships as `references/detail.json`. Pure generation (`generate_skill_files(aif, detail)`) is split from the I/O wrapper. Exposed via the `skill` CLI subcommand.

**`mcp_server.py`** — wraps each of `query_service`'s nine functions in a thin keyword-only function that makes `aif_path`/`project_path` optional, defaulting to whatever `ziplex-mcp --aif PATH --project PATH` was started with (`_defaults`, set once by `main()`, read fresh on every call so registration order doesn't matter) -- a real session is almost always one Claude Code project talking to one already-packed project, so re-typing the same absolute path on every single tool call was both friction and a real place for a typo to silently point at the wrong file. An explicit call-time `aif_path`/`project_path` always overrides the default; omitting both raises a clear `ValueError` naming which CLI flag would fix it, rather than a confusing downstream file-not-found. Each wrapper's `__doc__` is assigned from the matching `query_service` function's own docstring *before* `mcp.tool()(wrapper)` registers it (the decorator reads `__doc__` at registration time) -- a live reference to the same string, not a second copy that could drift, so the tool description the MCP SDK shows still only lives in `query_service.py`. Uses the official `mcp` SDK's `MCPServer` (`from mcp.server import MCPServer`; not the older `FastMCP`, which no longer exists in the installed SDK version). Run with `ziplex-mcp` (stdio transport), optionally `ziplex-mcp --aif <path> --project <path>` (the same `--aif`/`--project` flag names `ziplex-gui` already uses) -- `claude mcp add ziplex -- ziplex-mcp --aif result/Ziplex.json --project .` bakes them into the registration itself.

---

Every LLM-facing function in `llm.py` follows the same contract: prompt says "JSON only, nothing else," caller does `json.loads()` and falls back to a default (`{}`, `[]`, `""`) on `JSONDecodeError` — callers in `packager.py` loop until they get a non-empty result or the user intervenes via `checkpoint.handle_llm_failure`.

**`project.security_scan`/`project.format_notes`** — two small, free additions to `project`, both attached unconditionally, since `aif.json` is meant to survive outside any one tool session (committed to a repo, handed to a colleague, pasted cold into a web chat with none of Ziplex's own docs loaded alongside it). `security_scan` (`{flagged, included_anyway, excluded}`) is computed from `scan_files()`'s `dangerous` result intersected against the *final* `selected` list (not any CLI-only intermediate variable, so a GUI/`preselected` caller naming a dangerous file directly is still counted correctly); `{0, 0, 0}` when nothing was ever flagged. `format_notes` is a single fixed constant per language explaining the format itself to a cold reader: what `confidence`'s threshold means, and what `detail.json`'s `⋮----` marker stands for. `project.language` is the same "always attached, cheap fact" pattern applied to which language `prompt`/`rules`/every file's `summary` were actually written in. `project.scope` (`{include: [...], ignore: [...]}`, `{[], []}` when neither was given) records this specific pack's one-off `--include`/`--ignore` CLI extras (on top of whatever `.ziplex.json` already says) — a code-review finding: `.ziplex.json` is already reproducible from disk on its own, but those CLI-only extras weren't persisted anywhere, so a later freshness check (CLI, MCP, GUI) had no way to reconstruct the exact scope a pack used and would diff against an unscoped file tree instead. `freshness.load_pack_scope(aif_path)` is the shared read-back every freshness caller now uses (see that module's own bullet above).
