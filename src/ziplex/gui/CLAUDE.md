# src/ziplex/gui/ — local GUI (pack + browse), Flask + pywebview

Scoped notes for `gui_server.py`, `pack_service.py`, `watcher.py`, and the static frontend (`index.html`, the `js/` ES-module tree, `style.css`). See the root `CLAUDE.md` for how this fits into the overall pipeline; see the `ziplex-roadmap` memory for why this exists (a local browse/search companion for environments where Claude Code/MCP isn't available but browser-based AI chat is) and what it deliberately doesn't do (autonomous web-chat querying — see that memory's "explicitly decided not to build" note).

This directory is the `ziplex.gui` subpackage, one level under the `ziplex` package root -- every module it imports from there (`query_service.py`, `file/`) is reached via a relative import one level up (`from .. import query_service`, `from ..file.relationship import CycleError`), not a bare `import query_service` the way a pre-packaging flat `src/` layout would have needed. `gui_server.py` imports its own siblings (`pack_service.py`, `watcher.py`) via `from . import pack_service` / `from . import watcher`. Run directly via the `ziplex-gui` console script (`pip install -e .`) or `python -m ziplex.gui.gui_server` — see the root `CLAUDE.md`'s Commands section.

## gui_server.py

The Flask app + CLI entrypoint. Two halves, split by read vs. write:

- **Read-only routes** (`/api/overview`, `/api/files`, `/api/relationships`, `/api/dependents`, `/api/blast_radius`, `/api/detail`, `/api/freshness`, `/api/search`) are thin adapters over `query_service.py` — the same core `mcp_server.py` sits on — translating query params to function calls and JSON responses, nothing more. A human uses these pages to browse an already-packed project and copy what's useful (each page has a Copy button) into a separate web chat by hand; that hand-off is deliberate, not something this GUI automates (see the roadmap memory).
- **The write path** (`/api/select_files`, `/api/pack`, `/api/pack/review`, `/api/pack/link`, `/api/pack/unlink`, `/api/pack/finalize`, `/api/pack/cancel`, `/api/pack/status`, plus `/api/relationships/link`/`/api/relationships/unlink` — see `pack_service.py` below for why those two aren't just the job-based pair reused) runs `packager.pack()`/`pack_service.py`'s edit functions directly, so a project can be packed *and* have its relationships fixed after the fact from the GUI without a prior CLI run. `/api/pack/link`, `/api/pack/unlink`, `/api/relationships/link`, and `/api/relationships/unlink` share one body (`_relationship_edit_route(id_field, result_key, fn)`) for parsing `{id_field, file, target}` and mapping `CycleError`/`ValueError` to 409/404 — factored out after a code review flagged the four routes as near-identical copies of the same mapping.
- **`/api/settings`** (GET/POST) is neither of the above -- not a `packager.pack()`/`query_service.py` adapter at all, just a thin wrapper over `src/ziplex/settings.py`'s `load_settings()`/`save_settings()` for the Options page (see Frontend below). POST merges a partial body onto whatever's already saved (`output_dir` and/or `gemini_api_key`, whichever the Options page's two independent save buttons actually sent) rather than requiring the whole shape back, so saving one field can't accidentally wipe out another -- including `project_output_dirs`, the per-project pins, which this route never touches at all regardless (see `start_pack_job()`'s own note on how those get set).

Runs as a local Flask server wrapped in a native window via `pywebview` by default (`main()`'s windowed branch) — `--no-window` (or a bare `flask run`/`app.run()` against the same `app` object) drops straight to a plain browser tab instead, useful for development where webview's window makes debugging fiddlier. `static_folder="."` (not `"gui"` — this file already lives in the directory `index.html`/the `js/` module tree/`style.css` sit in) serves the frontend. Flask's static route handles the nested `js/pages/` path the same as a top-level file, so no extra config was needed for the module split. Binds to `127.0.0.1` only, no `--host` flag, on purpose — the same reasoning the roadmap memory applied to rejecting a tunneled MCP server; exposing this would open local project data (including original source, via `search_project`) to the network.

**Native OS dialogs**: the windowed branch exposes a `_Api` bridge (`js_api=...`) with three methods — `choose_folder()` (project-folder fields), `choose_aif_file()` (an OPEN dialog, `.json`-filtered, for `renderCheck()`'s aif.json field), and `choose_save_file()` (a SAVE dialog for the pack form's output-path field, since that target doesn't exist yet — `save_aif()` creates it). `window.pywebview.api` only exists in the native window; `--no-window`/bare-`flask run` mode has no bridge at all, so the frontend's picker buttons (`js/app.js`'s `hasApi()`) fall back to asking for a typed path. `_Api` is a module-level class, not nested inside `main()` (where it originally lived) — it takes the lazily-imported `webview` module as a constructor argument (`_Api(webview)`) rather than closing over a `main()`-local import, since `webview` itself deliberately stays a lazy, windowed-branch-only import (`--no-window` mode has no reason to require the package, or trigger whatever native-backend probing importing it does). Module-level also means it's directly unit-testable against a fake `webview`/window stand-in, which nesting it inside `main()` made impossible.

**Native window-close guard**: `window.events.closing` is wired to `_confirm_close_if_reviewing(window)` (also module-level, same reasoning as `_Api`), which checks `pack_service.has_reviewing_job()` and, if a job is mid-review, shows a native confirmation dialog (`window.create_confirmation_dialog`, the same mechanism pywebview's own built-in `confirm_close` option uses internally — confirmed by reading the installed package's source) that can cancel the close by returning `False`. This exists because `js/pack.js`'s own `beforeunload` guard (see below) only fires on an in-page reload/navigation — clicking the native window's own close button tears the webview down directly, bypassing the DOM entirely, so nothing browser-side catches it there.

## pack_service.py

Background pack-job runner backing `gui_server.py`'s `/api/pack*` routes. `packager.pack()` is long-running (real LLM calls) and talks via `print()`/`input()` — wrong to run straight inside a Flask request handler — so this runs one pack per background thread and gives the routes something to poll: a job id, a `running`/`reviewing`/`finalizing`/`done`/`error` state, captured log lines, and (once analysis finishes) a pause point for review.

- **`list_selectable_files(project_path)`** — the read-only step before a job exists: runs `collect_files()`/`scan_files()` and returns the safe/dangerous split, since `file/selector.py`'s terminal picker reads from stdin, which doesn't exist over HTTP. `"dangerous"` entries carry `scan_file()`'s full reason/matched-line detail (relative-keyed), not just a name -- `renderPackHome()`'s file-selection screen renders each as its own row with a normally-unchecked "include anyway" checkbox (see Frontend below), the browser equivalent of the CLI's `review_dangerous_files()` prompt. Whatever's checked from either list becomes `start_pack_job()`'s `selected_files`, which feeds `pack()`'s `preselected` param (bypassing both `auto` and the terminal picker) -- `pack()` trusts a name from `dangerous` exactly like one from `safe_files` there, since checking the box already *is* the human decision `review_dangerous_files()` represents for the CLI path. Also returns `default_output_path` (`settings.resolve_output_path()`) -- what `start_pack_job()` will actually save to if the pack form's own "출력 경로" field is left blank, so `renderPackHome()` can show it (as a placeholder, not a value -- see Frontend below) instead of a human having to guess.
- **`start_pack_job()`'s output-path resolution** (`src/ziplex/settings.py`): a caller-given `output_path` (the pack form's field, non-blank) is used as-is for this job and also pins the project to its parent folder going forward (`settings.set_project_output_dir()`) -- an explicit choice, remembered from then on. Left blank, it resolves through `settings.resolve_output_path()` instead (this project's own pin, else the Options page's global default) into a concrete path if either is configured, or stays `None` (`packager.py`'s own `RESULT_DIR`-based default applies, exactly as before `settings.py` existed) if neither is. Either way, the same folder is what `packager.pack()`'s `result_dir` param is given too (see root `CLAUDE.md`'s `packager.py`/`settings.py` bullets), so this run's incremental-reuse cache lookup and the actual save destination (`submit_review()`, via `resolve_output_path()`/`save_aif()`) never drift apart.
- **`start_pack_job()`** runs `pack(..., interactive=False, preselected=...)` — non-interactive so a *repeated* LLM failure can't block on stdin (`checkpoint.handle_llm_failure()`'s non-interactive path) — but does **not** follow it with `finalize_aif()`. The job instead pauses in state `"reviewing"` with the raw `aif` attached, mirroring `corrector.py`'s `correct_aif()`: project name/prompt/rules, and per-file summaries triaged by `confidence.triage()` into `needs_review` (shown with real `signatures`, capped at 10) vs. `auto_kept`. `no_llm` (`renderPackHome()`'s "LLM 사용 안 함" checkbox) threads straight to `pack(..., use_llm=False)` — CLI `pack --no-llm`'s GUI equivalent — and needed zero review-screen changes: `get_review()`/the summary-edit fields just render whatever `pack()` produced, structural or LLM-written, the same way either shape already flows through `confidence.triage()`. `lang` (2026-08-26, `renderPackHome()`'s packing-language `<select>`, English default/first option) threads straight to `pack(..., lang=...)` — CLI `pack --lang`'s GUI equivalent, see the root `CLAUDE.md`'s `packager.py` bullet for what it controls (which language every LLM-written value, plus Ziplex's own fixed strings, is actually written in). `gui_server.py`'s `/api/pack` route validates it against `llm.LANGUAGE_NAMES` before it ever reaches here, falling back to `"en"` for anything else -- `start_pack_job()`/`pack()` itself normalizes defensively too, so this is belt-and-suspenders, not the only check. Deliberately a **different** concept from the display-language switcher below: that one (`js/i18n.js`) translates only this GUI's own chrome and never touches an LLM; this one is what language the *packed project's own content* ends up written in. `job["lang"]` is echoed back in `get_job_status()`'s `retry_params` alongside `no_cache`/`no_llm`/`selected_files`, so `js/pack.js`'s error-screen retry reposts it verbatim on a checkpoint-resume, same as every other retry param.
- **`add_dependency_in_job()`/`remove_dependency_in_job()`** wrap `file/relationship.py`'s `add_dependency`/`remove_dependency` — a per-edge link/unlink pair, not `move_file()`. An earlier drag-and-drop version built on `move_file()` was tried and rejected: `move_file`'s "strip from every existing reference first" step is exactly wrong for a file with more than one real parent, silently severing a shared file's other references whenever one occurrence got dragged. See `src/ziplex/file/CLAUDE.md` for the pure-function side of this.
- **`submit_review()`** applies whatever the human changed through `edits.py`'s setters (the same seam `corrector.py` itself is built on), then finalizes and saves — the non-terminal equivalent of `correct_aif()`'s ending.
- **`get_review()`** recomputes `_build_review(job["aif"])` fresh on every call rather than caching it — an earlier version cached at the moment the job first paused and never invalidated it, so a page reload after a link/unlink edit could show a stale relationship graph.
- **`get_job_status()`'s `retry_params`** — always present (not just on `"error"`), a straight echo of `start_pack_job()`'s own argument shape (`project_path`/`output_path`/`no_cache`/`no_llm`/`selected_files`). Exists for item 8: a repeated rules/prompt LLM failure lands a GUI job in state `"error"` via `checkpoint.handle_llm_failure()`'s non-interactive default (checkpoint and stop -- `pack()` always runs `interactive=False` here, see `start_pack_job()`'s own bullet below), and until this existed the pack-progress screen's error state had no buttons at all -- no way forward except abandoning the job and reselecting files from scratch. `js/pack.js`'s `showErrorState()` reposts this dict verbatim to `/api/pack` on its "다시 시도" button, letting `pack()`'s own checkpoint auto-resume (`resume_checkpoint_choice()`, always-yes when non-interactive) pick up from exactly where it left off -- proven end to end (not just that `handle_llm_failure()` itself works, which `test_checkpoint.py` already covered) by a `_EmptyRulesProvider` that fails every rules-shaped prompt, in both `test_pack_service.py` and `test_gui_server.py`. `output_path` here is the *original* caller-given value (possibly `None`), not `start_pack_job()`'s own resolved one -- retrying a job that started with a blank field must stay blank on retry too, or it would read as an explicit choice and silently pin the project via `set_project_output_dir()` (see that bullet) even though nothing was ever typed.
- **`request_cancel(job_id, save)`** — the "running"-state counterpart to `cancel_job()` (which only ever applies to a paused "reviewing" job — nothing's actually running by then). Sets `job["cancel_action"]`, which `_check_cancelled_for(job)` hands to `pack()` as its `check_cancelled` callback (see `packager.py`'s own doc for exactly where that gets polled) -- the only way to interrupt a background pack thread at all, since a real Python thread can't be safely killed from outside once started. `save=True` checkpoints wherever analysis has gotten to (the same `checkpoint.build_snapshot()`/`save_checkpoint()` pair `handle_llm_failure()` already uses, so a stopped-and-saved job auto-resumes on the next `pack()` for that project exactly like a failed one would); `save=False` just discards it. Not instant: the job keeps reporting `"running"` until `pack()` actually reaches its next checkpoint. `_run()` tells the two apart afterward via `job["cancel_result"]` (set once, never cleared, unlike `cancel_action` which is consumed on read) to surface a specific "사용자가 취소함" message instead of the generic empty-`aif` one a repeated LLM failure would leave.
- **`link_saved_relationship()`/`unlink_saved_relationship()`** — the *post-pack* counterparts to `add_dependency_in_job`/`remove_dependency_in_job`, for a project that's already been packed and saved (no live job at all, just an `aif_path` on disk). Backs the GUI's Relationships browse page (see Frontend below). Wraps `file/relationship.py`'s `add_relationship()`/`remove_relationship()` -- the `relationships`-shaped counterparts to `add_dependency()`/`remove_dependency()`, needed because `finalize_aif()` prunes each file's working-state `dependencies` list once `relationships` is built, so the job-based functions (which edit `dependencies`) have nothing left to operate on for an already-saved aif.json. The shared `_edit_saved_relationships(aif_path, edit)` helper reads aif.json, applies `edit(relationships)`, and writes it straight back -- deliberately *not* via `packager.save_aif()`, which expects the in-progress pack shape (splitting `compressed` into detail.json, `_manifest` into cache.json) and would blank both sibling files out on an already-finalized aif with neither field left.

**Concurrency**: each job gets its own `threading.Lock` (`job["lock"]`), acquired for every read/mutation of that job's own fields — not one global lock for every job's fields, which is what closed a real set of races caught by a two-pass code review: `get_review()`'s stale-cache bug above; `add_dependency()`'s cycle check and the actual write not being atomic (two concurrent link requests could both pass the check before either wrote, committing a cycle the guard exists to prevent); `cancel_job()`/`submit_review()` racing (a cancel arriving after `submit_review()` had already started committing could flip an already-saved job back to `error`); and a mutation dereferencing a job `cancel_job()` had just nulled out, surfacing as a raw 500. `submit_review()` moves a job out of `"reviewing"` into a transient `"finalizing"` state *before* its mutators would release `job["lock"]` — that ordering is what closes all four races together, without unrelated jobs ever contending with each other (the module-level `_jobs_lock` only guards inserting into / looking up from the `_jobs` dict itself). `has_reviewing_job()` (used by `gui_server.py`'s native-close guard) follows the same discipline: never holds `_jobs_lock` while acquiring a job's own lock. `print()`-capturing (`_capture_for_job`/`_LogWriter`) is the one deliberate exception to per-job independence — it serializes across *all* jobs via a single `_stdout_capture_lock`, since `sys.stdout` is one process-wide global no per-job lock can partition; the cost is that two jobs' analysis phases can't log concurrently, acceptable for a single-user local tool.

The on-disk writes above (`link_saved_relationship`/`unlink_saved_relationship`, and `submit_review()`'s finalize-and-save) aren't jobs, so `job["lock"]` doesn't cover them -- a second code-review pass caught that `_edit_saved_relationships()`'s read-modify-write had no guard at all, unlike every job mutation. `_lock_for_path(path)` gives each resolved aif.json path its own `threading.Lock` (not one global lock, same "unrelated files never contend" reasoning as `_jobs_lock`), run through `os.path.normcase()` on top of `Path.resolve()` since `resolve()` alone only normalizes an *existing* file's on-disk case on Windows -- two callers naming the same not-yet-created file with different case would otherwise get two different locks right at the moment (a brand-new file) this guard matters most. `submit_review()` locks `packager.resolve_output_path(aif, output_path)` -- the same path-fallback logic `save_aif()` itself uses internally, factored out so the two can't silently compute different paths -- so a live job's finalize and a Relationships-page edit aimed at the same file can't race each other either. `_file_locks` is bounded the same way `_jobs` is (`_evict_old_file_locks()`, mirroring `_MAX_FINISHED_JOBS`), but only ever evicts an *unlocked* entry other than the one currently being requested: evicting a lock a thread still holds (or the path a caller is mid-lookup for) would just hand a second caller a fresh `Lock` for the same file, reintroducing the exact race this locking exists to prevent.

Jobs live in memory only (module-level `_jobs` dict) — gone on server restart, same lifetime as `gui_server.py`'s `_default_config`.

## watcher.py

Live filesystem watching backing `/api/watch/start`/`/api/watch/status` -- makes the Overview/Files staleness badge update on its own while that page stays open, instead of only ever being checked once at page-load time the way `query_service.py`'s `_stale_warning()` (still there, unchanged, for the initial on-load check) always has. Built on `watchdog`'s `Observer` (OS-level file-system-change notifications -- inotify/FSEvents/`ReadDirectoryChangesW` depending on platform, *not* polling), so idle CPU/memory cost is effectively zero; the real cost is one background OS-notification thread per watched project plus a cheap debounced recompute (`freshness.check_freshness()`, the exact function the on-demand check already uses) whenever something relevant actually changes. Confirmed live against a real running server, not just unit tests: editing a tracked file, and separately adding a brand-new one, both showed up in `/api/watch/status` within about 2 seconds with no reload.

`start_watch(project_path, aif_path)` is idempotent -- (re)starting a watch for a project already being watched stops the old `Observer` first rather than stacking a second one on top of it, so a GUI page calling this once per visit (`js/app.js`'s `startStaleWatch()`) can't leak observers by navigating back and forth to the same project. `MAX_WATCHERS` (5) bounds a long GUI session that's opened many different projects over time by evicting the oldest-started watcher once the cap is exceeded -- the same reasoning `pack_service.py`'s job/lock eviction already applies elsewhere in this codebase, just for watchers instead of jobs/locks. One watcher per project path (a `dict` keyed by resolved absolute path, guarded by its own `threading.Lock`), not one global "whatever's currently open" slot -- avoids a subtle bug where opening a second project's Overview page (a second browser tab, say) would silently kill the first tab's watch.

Events are filtered before ever scheduling a recompute: `_build_ignore_spec()` builds the exact same `pathspec` `file/collector.py`'s `collect_files()` does (`DEFAULT_IGNORE` + the project's own `.gitignore`), and `_DebouncedHandler` checks a changed path against it before scheduling anything. Not needed for *correctness* -- `check_freshness()` already only ever re-hashes `collect_and_scan()`'s own already-filtered safe-file list, so an event from an ignored path would just correctly find nothing changed -- purely to avoid an unnecessary recompute for every internal `.git`/`node_modules`/`venv` write those directories generate constantly on their own, confirmed directly: writing to a `.git/HEAD`-equivalent path inside a watched project never flips `is_stale`, not even transiently. Debounced (`DEBOUNCE_SECONDS`, 1.0 default) on top of that -- a single save can fire several OS events in quick succession (some editors delete+recreate rather than write in place), and a git checkout/branch switch can touch hundreds of files at once, so a whole burst collapses into at most one recompute after it goes quiet rather than one recompute per individual event.

`start_watch()` also runs `recompute()` once synchronously before returning, so the very first `/api/watch/status` poll already has a real report instead of `None` -- otherwise a project already known to be stale would show its badge disappear for a few seconds right after the page opened, until the first (nonexistent, since nothing changed) file event would have triggered one.

**Frontend wiring** (`js/app.js`'s `startStaleWatch()`/`stopStaleWatch()`): called from `renderOverview()`/`renderFiles()` only (`js/pages/overview.js`/`files.js`) -- the same two "orientation" pages `_stale_warning()` itself is scoped to, not scope-creeping into Relationships/Search/the pack review flow. `startStaleWatch()` fires `/api/watch/start` (fire-and-forget) then polls `/api/watch/status` every 3 seconds via `setInterval`, calling `setStale()` (already shared with the on-load `_stale` field, same `{is_stale, changed, added, removed}` shape) only when a real report comes back -- a `null` report (watcher not started yet, or evicted) leaves whatever the page's own initial load already showed alone, rather than forcibly hiding a badge that's still correct. `router.js`'s `route()` calls `stopStaleWatch()` *unconditionally* at the top of every navigation, not just when leaving Overview/Files -- this hash router has no per-page "unmount" hook of its own, so `route()` itself is the one place every navigation is guaranteed to pass through; without this, switching pages while a project stayed loaded would leak one `setInterval` per visit, each still polling forever.

## Frontend (`index.html` / `js/*.js` / `style.css`)

No build step, no framework, but real ES modules now (native browser support via `<script type="module" src="js/router.js">` -- still no bundler, still no npm/package.json): a hand-rolled hash router (`route()`) over plain `fetch()` calls to `/api/*`. State (`aif_path`/`project_path`) lives in `localStorage`, not on the server — every `gui_server.py` route is stateless, same as `mcp_server.py`'s tools. Pages: the topbar's four global destinations -- the bare-logo home (`renderHome`, route `/`), pack-new-project (`renderPackHome`, route `/pack`), open-existing-project (`renderCheck`, route `/check`), and options (`renderOptions`, display language + the default output folder for new packs -- see below) -- plus the sidebar's project-scoped sections once a project is loaded: overview, files (sortable, filterable table), file detail, search, relationships (`renderRelationships`), and the pack job/review flow (`renderPackJob`).

What used to be one 1250-line `app.js`, then six flat `app-*.js` files sharing implicit global scope (load order mattering because nothing declared its own dependencies), is now `js/` -- the same six units of logic, but each a real module with explicit `import`/`export`: `js/i18n.js` (the display-language dictionary/`t()`, see below -- the lowest layer, no imports of its own), `js/app.js` (localStorage state, `api`/`apiPost`, `el`/`copyButton`/`showLoading`, native-picker buttons, `confidenceLevel`/`setStale`/`setActiveNav`/`setActiveTopbar`, the shared `app`/`nav`/`topbar`/`staleBadge` DOM refs), `js/graph.js` (the dependency-graph components below), `js/pack.js` (`renderPackJob`), `js/pages/` (one file per topbar/sidebar destination or tightly related group -- `landing.js` bundles `renderHome`/`renderPackHome`/`renderCheck`, since those three used to be one combined page before the topbar split grew a dedicated slot for each; `options.js`, `overview.js`, `files.js`, `relationships.js`, `search.js` each hold just their own page), and `js/router.js` (`route()`, the `DOMContentLoaded`/`hashchange` bootstrap, and the sole `<script>` tag index.html actually loads -- every other module gets pulled in transitively through the `import` graph rather than needing its own tag). Load order is no longer index.html's problem to get right: each module states exactly what it needs from exactly which sibling, and the browser's module loader resolves the graph itself. One genuine circular import exists (`js/pages/options.js` imports `route` from `js/router.js`, which imports `renderOptions` back from `options.js`) -- safe under ES modules because neither side touches the other's binding until well after both modules finish evaluating (each use is deferred inside a function body/event handler, never at a module's own top level). Split for the same reason `packager.py` got split into `checkpoint.py`/`summarizer.py` -- one file had grown far past every sibling in the project (next-largest was under 700 lines) with several genuinely separable concerns inside it, not because any one page's logic was individually too large.

**Display-language switcher** (`js/i18n.js`, edited from `js/pages/options.js`'s `renderOptions`): a hand-written `{ko: {...}, en: {...}}` dictionary plus `t(key, vars)`, not a runtime AI/translation-API call -- the GUI's own chrome is a small, fixed, already-known set of strings (~105 distinct keys as of this writing), so translating it once at dev time costs nothing per view and needs no API key/network, unlike translating an arbitrary *packed project's* own content. That packed-content question (2026-08-26, previously an open roadmap item) is now answered by a **separate** control -- `renderPackHome()`'s packing-language `<select>` (see `pack_service.py`'s `start_pack_job()` bullet above), which asks the summarization LLM to write in the target language from the start rather than translating already-packed content after the fact. The two are unrelated: this dictionary only ever affects what the GUI's own buttons/labels say, never a summary/rule/AI-guide value. Every user-facing string in every `js/` module goes through `t()` now -- `vars` is a plain object for the ~20 keys that interpolate a count/path/status code (`I18N`'s entry is a function for those, a plain string otherwise) rather than needing even a minimal template syntax. `getLang()`/`setLang()` persist to `localStorage` (`ziplex.lang`), not `settings.py`'s per-user config file -- this is a purely client-side rendering preference the backend never needs to know, unlike the output-folder setting right above it on the same Options page. Two things `t()`-driven `render*()` calls don't cover: index.html's own static topbar/sidebar markup (never touched by any `render*()`), handled by `data-i18n="key"` attributes + `applyStaticI18n()` (called once on `DOMContentLoaded` and again whenever the language `<select>` changes); and a stray local variable literally named `t` in `renderOverview()`'s token-table `.map()` callback, renamed to `tok` specifically to avoid shadowing this file's `t()` within that scope. Changing the language re-runs `route()` to redraw whatever page is current in the new language, rather than trying to patch already-rendered DOM text node by node.

**Sidebar, not a top hyperlink bar**: `#nav`'s CSS class is `.sidebar` (the id stays `nav` -- every `render*()` still just does `nav.classList.add/remove("hidden")`), fixed to the left with `.shell` (a flex row wrapping it + `main`) instead of a horizontal bar above `main`. Deliberate positioning choice, not just a visual refresh: this GUI is single-user, `127.0.0.1`-only, and launched as a native `pywebview` window by default -- a sidebar/toolbar reads as "a program on your machine" the way a top hyperlink nav bar reads as "a web dashboard," matching what it actually is. `js/app.js`'s `setActiveNav(routeName)` highlights the current section (`data-route` attributes on each `<a>`) -- called once per navigation from `js/router.js`'s `route()`, not from each individual `render*()`, since "which section is this route" is the router's own question, not every page's. `main`'s centering is conditional on the sidebar's own hidden state (`.sidebar.hidden + main` in `style.css`) so the landing page (nav hidden) still centers on the *full* window width instead of the space next to a hidden-but-still-flex-sized sidebar.

**Topbar** (`#topbar`, `.topbar` in `style.css`): a thin strip above `.shell` (so above the sidebar too, not inside it), present on every screen -- home, pack, check, options, mid-pack, and every browsed-project page -- unlike the sidebar, which only shows once a project is loaded. Deliberately doesn't undo the sidebar decision just above: it's a native-menu-bar-style strip (the app-name/logo link itself, `#/` → `renderHome()`, a deliberately empty screen that exists only so the logo has somewhere of its own to land; then three real links: "프로젝트 패킹" → `#/pack` → `renderPackHome()`, "프로젝트 확인" → `#/check` → `renderCheck()`, "옵션" → `#/options` → `renderOptions()`) rather than a wide tab strip, kept thin and sparse on purpose to stay "a program's own menu bar," not a second, competing nav layer that would read as a web dashboard's tab bar. `renderPackHome()`/`renderCheck()` used to be one combined landing page at `#/` (open-existing-project form + recent-projects list + new-pack form all on one screen) until the topbar grew a dedicated slot for each -- "packing a new project" and "opening/checking an already-packed one" are different enough activities to deserve their own destination rather than sharing a single scroll; `renderPackHome()` moved off `#/` to `#/pack` once `renderHome()` needed the bare route for the logo link. `js/app.js`'s `setActiveTopbar(name)` mirrors `setActiveNav()` one level up: `route()` (`js/router.js`) calls it with `"home"`/`"pack"`/`"check"`/`"options"`/`null` depending on which layer (topbar destination vs. sidebar section) the current route actually belongs to -- never more than one lit at once. All four topbar destinations are checked *before* `route()`'s "no project loaded yet, bounce to \[...\]" guard, since none of them should require a project already being loaded -- that guard itself bounces an unrecognized route to `#/check` (open a project) when nothing's loaded, since hitting e.g. `#/overview` directly implies wanting to view something already packed, not start fresh or see the bare logo; the same routing's final fallback (nothing matched at all, but *with* a project loaded) goes to `#/overview` instead, for the same "most useful default" reasoning.

**Sensitive-file review** (`renderPackHome`'s file-selection step): a flagged file no longer just disappears into a bare count -- each one renders its own row with `scan_file()`'s reason + matched line (not the whole file) and a checkbox, unchecked by default and tracked in a *separate* `dangerousCheckboxes` array so "전체" (select-all) can never sweep one in by accident. Checking one and packing sends its name in `selected_files` alongside the normal safe ones -- `packager.pack()`'s `preselected` handling (see `src/ziplex/file/CLAUDE.md`'s `selector.py` section) trusts either list equally, so no other wiring was needed once `list_selectable_files()` started returning the reason detail.

**Options page** (`renderOptions`, `js/pages/options.js`): display language, an AI provider selector, and the global default output folder -- three independent save actions. The display language (`js/i18n.js`'s `getLang()`/`setLang()`, `localStorage`-only, no server round-trip, applies on change with no save button) sits above the provider selector and the global default output folder (`src/ziplex/settings.py`'s `output_dir`, its own save button, edited via GET/POST `/api/settings` and a `browseButton()` folder picker, same native-picker pattern every other path field in this GUI uses) -- different persistence layers/save actions because language is a pure display preference the backend never needs, while the others are genuinely backend-facing settings a human would reasonably want to set independently.

The provider selector (2026-08-24, replacing what used to be a bare Gemini-API-key card) is a `<select>` (Gemini / OpenAI-compatible / Claude, mirroring `llm.py`'s `PROVIDERS` minus the test-only `"mock"`) whose `change` handler only ever toggles which of three field groups is visible (`showProvider()`, via the shared `.hidden` class) -- nothing is saved until the one shared save button underneath fires, and that save always POSTs `llm_provider` (the dropdown's current value) alongside whichever group's own fields are currently showing (`gemini_api_key`+`gemini_model`, or `openai_api_key`+`openai_base_url`+`openai_model`, or `claude_api_key`+`claude_model`). Bundling the provider choice into the same request as that provider's fields is deliberate: two separate saves (name field, then key) could otherwise land in a state where a key is stored but `llm_provider` still names the previous provider, or vice versa. On load, `GET /api/settings`'s `llm_provider` (default `"gemini"` if unset) both selects the dropdown and calls `showProvider()` directly, so the page opens already showing whichever provider is actually active rather than always defaulting to Gemini's fields visually. The Gemini model field specifically exists because of a real external-tester bug (2026-08-24, see `llm.py`'s own bullet in the root `CLAUDE.md`): a GUI-only user who'd only ever entered an API key had no way to move off `GeminiProvider.DEFAULT_MODEL` (a floating `-latest` alias with a documented 503-overload history) short of an env var on a machine they don't administer.

The OpenAI-compatible group's base-URL row (2026-08-25) also carries two preset buttons, "Ollama defaults"/"LM Studio defaults" -- `OpenAIProvider` already covers either with no code change (see the root `CLAUDE.md`'s `llm.py` bullet), but a human still has to know each tool's default local port off the top of their head to type `openai_base_url` correctly, prompted by a real user asking whether both were actually supported. Each button just fills the field with that tool's well-known default (`http://localhost:11434/v1` / `http://localhost:1234/v1`) and moves focus to the model field, since the model name is the one part that still varies by whatever's actually loaded on that server -- neither button touches the API key field, since both servers are usually keyless but a value someone deliberately typed (a reverse-proxied setup with its own auth) shouldn't be silently cleared as a side effect of a convenience click.

All three providers' credentials belong here rather than on the pack form for the same reason the output folder does: they're persistent, global config, not a per-pack-run parameter -- deciding *whether* to use an LLM at all is still the pack form's own "LLM 사용 안 함" checkbox, but *which provider/key/model* to use is a one-time setup concern. `type="password"` on every key field masks it visually only; `GET /api/settings` still echoes every real value back in plain JSON to prefill these fields, same 127.0.0.1-only single-user trust model every other part of this GUI already assumes. Deliberately doesn't expose per-project output-folder pins here at all -- typing an explicit path in `renderPackHome()`'s own "출력 경로" field is what creates one (`start_pack_job()`, see above), so this page only ever touches the fallback every *unpinned* project follows. `renderPackHome()`'s own "출력 경로" field shows `list_selectable_files()`'s `default_output_path` as a *placeholder*, not a filled-in value -- filling it in would make leaving the field untouched submit a non-blank `output_path` on every pack, silently pinning every project the first time it's ever packed instead of only pinning on a genuinely explicit choice.

- **Freshness badges** (`renderCheck`'s recent-projects list): each row with a known `project` path fires `/api/freshness` (`query_service.check_freshness()`, a hash comparison, no LLM calls) once per page visit and renders "✅ 최신" or "⚠️ N개 변경" once it resolves. Best-effort and per-row -- a moved/deleted project folder, or an entry with no `project` at all (opened by aif path alone, no folder ever recorded), just leaves that one badge blank instead of failing the whole list. Both this badge and the top-of-page `staleBadge` (below) used to show *only* the count, with no way to see which files actually changed -- a real, reported gap (2026-08-24), not a deliberate scope decision. Fixed with `app.js`'s `staleTooltip(stale)`, a shared helper both call: a one-line count on top (unchanged), then each category's real filenames underneath (`core.stale.changedLabel`/`addedLabel`/`removedLabel`), capped at `STALE_DETAIL_CAP` (15) per category with a "+N more" line past that -- the same capped-list convention `tech_stack.py`'s `MAX_DEPENDENCIES`/the relationship editor's `REL_GRAPH_MAX_NEIGHBORS` already use. Surfaced via the existing `title` attribute (a native hover tooltip, `\n`-separated -- Chromium renders multi-line `title` tooltips fine, confirmed live), not new markup, since the backend already returns full `changed`/`added`/`removed` filename lists in both `/api/freshness` and `/api/watch/status` -- nothing needed to change server-side. Live-verified against a real packed project (`testfiles/game-mod-project`, one file edited): both the top badge and the recent-projects badge correctly showed `title` = "변경 1\n\n변경됨:\n  CHANGELOG.txt".

**Follow-up, same day**: the `title`-tooltip fix above was itself flagged by the user as an accessibility gap -- a hover-only tooltip is invisible to keyboard and touch users, not just an inconvenience. Fixed by making both badges genuinely clickable/keyboard-operable rather than hover-only: `#stale-badge` is now a real `<button>` (was a `<span>`) with `aria-expanded`/`aria-controls`, toggling a sibling `#stale-detail-panel` div (`index.html`) that `app.js`'s new `renderStaleDetail(stale)` populates as real DOM (a summary line + one `<ul>` per category, same `STALE_DETAIL_CAP`) -- `staleTooltip()` stays too, as a hover-only bonus for mouse users, not the only way in anymore. `setStale()` tracks the current report in module state (`_currentStale`) so a click can render on demand, and keeps the panel's content fresh if it's already open when the live watcher pushes a newer report (rather than leaving stale filenames on screen under an up-to-date badge). The recent-projects badge (`landing.js`) got the same treatment -- a `<button disabled>` by default (nothing to expand until `/api/freshness` resolves), enabled once a report comes back stale, expanding a `.recent-detail` panel inline in the row. Needed care around event bubbling: the row itself is a giant `onclick` (`openProject()`), so both the badge's click handler and the detail panel's own (for text selection inside the expanded list) call `e.stopPropagation()`, the same pattern the pre-existing remove button (✕) already used. Live-verified via direct clicks (not just reading the diff) against a real running `--no-window` instance: both badges expand and collapse on click, `aria-expanded` toggles correctly, and clicking inside an expanded row's file list does not also trigger `openProject()`.

- **Dependency tree overview** (`renderDependencyTreeOverview`) is the *default* view wherever relationships are shown — a read-only, collapsible (native `<details>`/`<summary>`) whole-tree render, roots-first with the same cycle-guard traversal as `corrector.py`'s terminal `print_current_tree()` (kept in sync with it deliberately). Shown first so a human can spot what looks wrong across the *whole* project by eye before touching anything, instead of the earlier default of jumping straight into per-file edit mode for the first low-confidence file. Needs-review files (confidence below `confidenceLevel()`'s 0.34 threshold, the same one `confidence.triage()` uses) get a `⚠️` marker in the tree. Clicking a file's own row (not the disclosure triangle -- `event.preventDefault()` on the row specifically stops the click from also toggling the `<details>` it sits inside) switches to `renderRelationshipEditor` for that file, with a "← 트리로 돌아가기" button back to the overview; both share one mutable tree so an edit made in the detail view shows up immediately on return. The toggle's disclosure triangle is a custom `::before` triangle, not the native list-item marker -- the native one sat above-left of the row instead of beside it with a flex row as summary's content (a real cross-browser positioning quirk), reported directly and fixed by hiding the native marker (`list-style: none` + the `-webkit-` pseudo) and drawing one that's guaranteed inline.

**`buildNode()` memoization (2026-08-24 fix)**: `ancestors` (a `Set` threaded down the recursion, unchanged) guards against a true cycle -- the same file reappearing on the *current* root-to-here path. It does **not** guard against a file legitimately (or, before the `resolve_dependency()` fix in `src/ziplex/extract/code/CLAUDE.md`, *wrongly*) shared by many different dependents elsewhere in the graph -- every reference to that file re-expanded its *entire* subtree in full, and if that subtree itself shared files with siblings, the duplication compounded at every level. Not hypothetical: packing Ziplex's own repo (real, ~90 files, not a toy fixture) hung the GUI review screen outright -- the browser tab unresponsive to even a screenshot for 50+ seconds, traced to a file whose in-degree had been inflated to 27 by the `resolve_dependency()` bug above. Fixed with a second, flatter `seen` `Set` (unlike `ancestors`, shared by reference across *every* root's own call to `buildNode()`, not reset per-branch): the first time a file is rendered anywhere in the whole overview, it's added to `seen` before recursing into its children; any later reference to it -- from any parent, anywhere in the tree -- renders as a shallow row (`graph.tree.alreadyShown`, distinct from `graph.tree.cycleSkipped`'s message, since "shared" and "circular" are different, differently-actionable facts about a project) with no further recursion. Bounds total rendered nodes to the size of the graph (files + edges) regardless of how shared any one file is, the same way a real dependency-tree UI (`npm ls`, VS Code's explorer) dedupes a shared subtree instead of reprinting it in full at every reference.
- **Relationships page** (`renderRelationships`) is the *post-pack* counterpart: the exact same `renderDependencyTreeOverview`/`renderRelationshipEditor` pair, sourced from `/api/relationships` (an already-saved project) instead of a live job's `review.tree`, and edited via `/api/relationships/link`/`/api/relationships/unlink` (`pack_service.link_saved_relationship()`/`unlink_saved_relationship()` -- no job_id, edits aif.json on disk directly) instead of the job-based pair. Lets a human fix a relationship noticed after packing without re-running the whole pipeline.
- **Relationship editor** (`renderRelationshipEditor`, reached by clicking a file in either tree above, not shown by default) is master-detail, not a flat per-file list: a searchable file list on the left, and on the right only the *selected* file's own relationships — a small SVG ego-graph (`renderMiniGraph`: dependents on the left pointing in, dependencies on the right pointing out, capped at `REL_GRAPH_MAX_NEIGHBORS` (6) per side with a "+N more" overflow) plus the link/unlink controls. An earlier version rendered every file's full edge list at once with a giant unfiltered `<select>` per row to add a link — flagged directly by live user testing as unusable past a couple dozen files. Clicking a neighbor node in the graph jumps the selection to it, so a human can walk the graph instead of re-searching the file list per hop. Graph node labels show basename only (`shortLabels()`) — the full relative path was eating the fixed-width node boxes' truncation budget and clipping the actual filename — falling back to `parentDir/basename` only when two *currently displayed* neighbors' basenames collide, not project-wide.
- **Recent-projects list** (`renderCheck`, `ziplex.recent` in `localStorage`, capped at `RECENT_MAX` (8), deduped by aif path, most-recent-first) — `openProject()` is the one path that both opens a project and records it, called from `renderCheck`'s "열기" button, the pack-done screen's "결과 열기", and (indirectly, via `evaluate_js`) anywhere else a project gets opened programmatically.
- **Loading states** (`showLoading()`) on Overview/Files/file-detail fetches — factored out from the pattern `renderSearch()`'s inline "검색 중..." already used, so every page-level fetch gets a "불러오는 중..." placeholder instead of a blank `<main>` while in flight.
- **Review-screen guards**: a `confirm()` step before the "취소" button discards unsaved name/guide/rules/summary edits (relationship link/unlink edits hit the server immediately via `add_dependency_in_job`/`remove_dependency_in_job`, so those are already safe), and a `beforeunload` listener registered on entering `showReviewState()` and explicitly removed on both ways out (submit succeeds, cancel confirmed) so it doesn't linger and warn on an unrelated later navigation.
- **In-app navigation guard during an active pack job** (`pack.js`'s `confirmLeaveActivePackJob()` + `router.js`'s click-delegation, 2026-08-26): `beforeunload` only ever catches a real page reload/tab close, never an in-app hash-link click -- reported directly by the user clicking a topbar item mid-pack and landing on a different page with no warning at all, in either the `"running"` or `"reviewing"` state. Two things worth being precise about, since the fix doesn't change either: the background job itself is *not* stopped by leaving (`packager.pack()` runs on its own thread in the Flask/pywebview process, entirely decoupled from what the browser happens to be looking at -- confirmed live: navigating away mid-`"running"` and checking `/api/pack/status` afterward shows it kept progressing normally), and *reaching the result* afterward is what's actually at risk -- there's no jobs-list page, so nothing brings a human back to a `#/pack/<id>` URL once it's been navigated away from, and a `"reviewing"` job's edits (unlike relationship link/unlink) still only live in that page's JS state until submitted. `renderPackJob()` keeps a module-level `activeGuard` (`null | () => boolean`) current as the job moves through its states -- the `"running"` guard offers a `confirm()`/`confirm()` pair (leave at all? then: checkpoint-save via `requestStop(true)` first, or leave it running?), the `"reviewing"` guard reuses the Cancel button's own confirm text and calls `/api/pack/cancel` (fire-and-forget, not awaited -- see below for why), `null` once the job is `"done"`/`"error"`. `router.js` installs one `document`-level, capture-phase `click` listener (index.html's topbar/sidebar links are static markup, not something any `render*()` re-attaches a listener to) that calls `confirmLeaveActivePackJob()` before letting any `a[href^="#"]` click through, skipping it entirely when the link already points at the current hash. Every guard closure is deliberately synchronous, `confirm()`-only for the decision itself (never `await`ed) -- the click listener has to return a boolean *before* the click event finishes for `preventDefault()` to still work, and `confirm()`/`prompt()`/`alert()` are the one kind of dialog that's genuinely blocking, so the human has already answered by the time the closure returns; a save/cancel network call triggered by a "yes" is fired without awaiting it (same "best-effort" spirit `requestStop()`'s own button handlers already use), since navigation proceeds either way and the request completes server-side regardless of which page the browser has already moved on to.

A same-day `/code-review high` on the first version caught four real issues, all fixed before merge: (1) the `"running"` guard never cleared `activeGuard` on a confirmed leave -- decline "stop and save" (leave it running) and the closure stayed armed, so `poll()`'s still-ticking `setTimeout` loop (this render's own, orphaned once the human's navigated elsewhere) re-saw `"running"` a second later and popped the same confirm again, and again, on every subsequent unrelated click anywhere in the app until the job actually finished. Fixed by having the closure set both `activeGuard = null` *and* `stopped = true` on a confirmed leave -- the latter is what actually stops that orphaned `poll()` loop from rescheduling itself at all, not just from re-arming the guard. (2) the guard was wired only to `<a>` clicks, so the browser's own Back/Forward buttons (a direct `hashchange`, no click event) bypassed it completely -- exactly the scenario this feature exists to prevent, just via a different input. Fixed with a second, `hashchange`-level guard (`router.js`'s `guardedRoute()`, tracking `lastHash`): since a `hashchange` can't be `preventDefault()`'d (the hash has already changed by the time it fires), a declined guard reverts `location.hash` back to `lastHash` instead, whose own resulting `hashchange` re-enters `guardedRoute()` with `newHash === lastHash` and just re-renders the page already showing -- not a second prompt. Verified live via a raw `location.hash` assignment (no click involved, the same shape a Back button produces): declining reverts the hash, confirming lets it through. (3) `activeGuard` was armed with the `"running"` closure eagerly, before the render's own first `/api/pack/status` poll ever resolved -- a link click in that brief window (or a reload of a job that had already finished/errored server-side) could ask about a job that wasn't actually running anymore. Fixed by moving the arm point (`armRunningGuard()`) inside `poll()` itself, only once a response actually confirms `"running"`/`"finalizing"`, rather than unconditionally at the top of `renderPackJob()`. (4) the `"reviewing"` guard duplicated the adjacent Cancel button's confirm/remove-listener/cancel sequence as a second, already-diverging copy. Factored both onto one `discardReview()` (awaited by the button, so it can disable both buttons first and navigate only once the request settles; fire-and-forget by the guard, for the same synchronous-return reason described above).

The final `aif.json` shape and the LLM-facing-function JSON contract are documented at the bottom of the root `CLAUDE.md` — nothing GUI-specific about either.
