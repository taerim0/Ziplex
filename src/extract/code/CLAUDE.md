# src/extract/code/ — Tree-sitter extraction & compression

Scoped notes for `languages.py`/`parser.py`/`extractor.py`/`compressor.py`. See the root `CLAUDE.md` for how these fit into the overall `pack` pipeline, and `src/extract/text/CLAUDE.md` for the sibling non-Tree-sitter (JSON/Markdown/plain-text) compressors.

- **`languages.py`** — single source of truth per language: `LANGUAGE_CONFIGS: dict[ext, LanguageConfig]`, each with `language` (the compiled Tree-sitter grammar), `function_types` (node types targeted for signature extraction + body compression), and `dependency_handler` (a `(Node, list) -> bool` callback recognizing that language's import syntax), `api_handler` (same `(Node, list) -> bool` shape, recognizing that language's REST-route-declaration convention if it has one — `None` by default for a language with no established one, e.g. Java/Lua/GDScript/Rust/C# as of this writing), `implicit_names` (`dict[node_type, name]`, empty by default — a fallback name for a `function_types` node whose grammar gives it neither its own `"name"` field nor a wrapping node with one; see GDScript below), and `name_prefixes` (`dict[node_type, prefix]`, empty by default — a prefix to prepend to a name that *was* found, unlike `implicit_names`'s substitute for a missing one; see C# below). Supporting a new extension is one `LanguageConfig` entry here — `extractor.py`/`compressor.py` never hardcode per-language node types themselves. Currently `.py`, `.java`, `.ts`, `.js` (`.js` uses the TSX grammar via `tree_sitter_typescript`), `.lua`, `.gd`, `.go`, `.cpp`/`.cc`/`.cxx` (all three share one config object -- see C++ below), `.rs`, `.cs`. Lua's `dependency_handler` differs from the others in kind, not just detail: Lua has no import *statement* -- `require(...)` is an ordinary function call -- so `_lua_dependency_handler` recognizes it by matching a `function_call` node whose callee identifier is literally `"require"`, rather than a dedicated node type the way `import_statement`/`import_declaration` work for the others. `function_types=["function_declaration"]` covers all three named-function forms Lua's grammar folds into that one node type (`local function f()`, table-field `function Tbl.f()`, and colon/method `function Tbl:f()`) for free -- `child_by_field_name("name")` already returns the qualified text (`"Tbl.f"`, `"Tbl:method"`) needed for a readable signature, and `child_by_field_name("body")` already excludes the closing `end` keyword the way brace languages' `_collect_bodies` has to specially exclude `}` -- so no extractor.py/compressor.py changes were needed to add it, only the `languages.py` config entry.

`.py`'s `api_handler` (`_py_api_handler`) is the original Flask-style route detector, unchanged in behavior -- a `@app.get("/path")`-shaped decorator, matched by `.get`/`.post`/etc. appearing anywhere in the decorator's own text rather than a specific object name (`app`/`bp`/`blueprint` all decorate routes this way in real Flask code). `.ts`/`.js`'s `api_handler` (`_js_api_handler`) is the Express-style equivalent: an `app.get("/path", ...)`-shaped call, matched by the property name (`get`/`post`/`put`/`delete`/`patch`) on whatever object it's called on, with two guards against false positives -- only a plain string-literal first argument counts (a template literal with interpolation, `` `/users/${id}` ``, is left uncaptured, same "only capture what's statically resolvable" restraint `_lua_dependency_handler` takes for a dynamically-computed `require()`), and that string must start with `"/"` (the one signal telling an actual route registration apart from an unrelated same-shaped call like `someMap.get("key")`) -- still a heuristic, not a semantic guarantee, the same restraint every `dependency_handler` above already takes for its own language's import syntax.

**`.gd` (GDScript)** — sourced differently from every other entry: there's no dedicated `tree-sitter-gdscript` PyPI package (only a community grammar with no packaged Python binding), so `languages.py` pulls it from `tree-sitter-language-pack`'s bundled copy via `get_language("gdscript")` instead of a per-language import -- confirmed to load instantly offline (prebuilt in the wheel, no runtime compile/fetch) before committing to the dependency. `_gdscript_dependency_handler` recognizes two shapes: `preload(...)`/`load(...)` calls (like Lua's `require()`, an ordinary call recognized by callee name -- but this grammar's `call` node has no field name for its callee, read positionally as `children[0]` instead of `child_by_field_name("name")`), and `extends "res://Base.gd"` (path-based inheritance; `extends Node`/`extends SomeClass` -- a bare identifier/type with no resolvable file path -- is deliberately left uncaptured). The one thing GDScript actually needed beyond copying Lua's shape: its `preload`/`load`/`extends` arguments are `res://`-prefixed *file paths with an extension* ("res://scripts/config.gd"), not a dotted module name -- `file/relationship.py`'s `resolve_dependency()` splits on `"."` expecting a module path, which would grab the `.gd` extension instead of the filename here, so the handler normalizes to the bare stem (`Path(path).stem`) before appending. Everything else (signature extraction via `function_definition`'s `name`/`parameters`/`return_type`/`body` fields, indentation-based body stripping with no closing token to exclude, same as Python) needed zero special-casing -- except `constructor_definition` (Godot's `_init`), which parses as its own distinct node type whose grammar has no `"name"` field at all: the keyword `_init` is a literal token, not an identifier under a field. `implicit_names={"constructor_definition": "_init"}` supplies the one fixed name every constructor always has, rather than teaching `extractor.py`'s generic name-resolution a GDScript-specific string.
**`.go`** — a dedicated `tree-sitter-go` PyPI package, same shape as Python/Java/TS/Lua's own imports (no bundled-grammar workaround needed the way GDScript needs). `function_types=["function_declaration", "method_declaration"]` needed zero `extractor.py`/`compressor.py` changes beyond one: Go's grammar names its return-type field `"result"`, not `"return_type"` (Python/TS/GDScript's convention) -- `_traverse_signatures()` now checks both field names generically (not a per-language hardcode, just a second known naming convention). `method_declaration` (a receiver method, `func (s *Server) Start() ...`) exposes `"name"`/`"parameters"`/`"result"`/`"body"` directly on itself, same as a plain `function_declaration` -- its `"receiver"` field is simply never read, unlike TS/JS's arrow functions, which need the parent-fallback machinery because they have *no* name field of their own. `_go_dependency_handler` matches on `import_spec` (the common unit under both `import "fmt"` and a grouped `import (...)` block) and reads its `"path"` field's string content, ignoring an import's own `"name"` field (an alias or blank `_` -- irrelevant to dependency resolution). Known, accepted limitation: a Go import path names a *package* (typically a whole directory of files), not a single file, unlike every other language here -- `resolve_dependency()`'s file-stem matching means an internal multi-package import usually resolves as "external" rather than matching a specific file. Not fixed: proper resolution would need directory-level matching and reading `go.mod`'s own module path, a bigger change than one `dependency_handler` can make; many real Go projects are single-package anyway, which tempers how often this actually bites.

**`.cpp`/`.cc`/`.cxx`** — a dedicated `tree-sitter-cpp` PyPI package; all three extensions parse identically and share one config object (no per-extension difference to justify separate `Language()` instances, unlike `.ts`/`.js`'s genuinely different grammar variants). `function_types=["function_definition"]` covers every function shape uniformly -- a free function, an in-class method, an out-of-class `ReturnType ClassName::method(...)` definition, a constructor, and a destructor all parse as the same node type, unlike Java/Go's separate method node. What's genuinely new here, needing real `extractor.py` changes (not just a `languages.py` entry): this grammar nests a function's actual identifier and parameter list one level inside a distinct `"declarator"` sub-node (`function_declarator`) rather than exposing them as direct fields of `function_definition` the way every other supported language does -- the same "declarator" concept C-family grammars reuse for variable declarations too. `_unwrap_declarator()` checks for this shape (falls through unchanged for every other language, none of which have a `"declarator"` field on a function-type node) and hands the inner `function_declarator` to `_resolve_signature_name()`/the parameter lookup instead of the outer node; the inner node's own identifier field is *also* called `"declarator"` (not `"name"`), covered by the same third field-name fallback that reads `"name"` then `"declarator"`. The return type sits on the *outer* node regardless, under yet a third field-naming convention (`"type"`, alongside Python/TS/GDScript's `"return_type"` and Go's `"result"`) -- `None` for a constructor/destructor, which have no return type at all, correctly producing no `-> ...` suffix. Unlike `"return_type"`/`"result"`, `"type"` is deliberately *not* checked unconditionally: Java's `method_declaration` also has a field literally named `"type"` (its own return type), and a code-review pass caught that checking it unconditionally silently changed every Java signature from `add(int a, int b)` to `add(int a, int b) -> int` -- an unrelated, undocumented behavior change riding along with the C++ addition, with no test guarding against it (fixed with `tests/test_extractor.py::test_extract_signatures_from_java_file`, added specifically to close that gap). `"type"` is only consulted when `sig_node is not node` -- i.e. `_unwrap_declarator()` actually found and returned an inner `function_declarator` -- which is currently only ever true for C++, since Java's `method_declaration` has no `"declarator"` field at all and is therefore never unwrapped. Scoped by structural evidence (unwrapping happened), not a language-name check. `_cpp_dependency_handler` matches `preproc_include` (a preprocessor directive, not part of the grammar proper the way an `import_statement` is) and normalizes both its shapes -- `<iostream>` (angle-bracket `system_lib_string`, delimiters stripped directly) and `"utils.h"` (quoted `string_literal`, the usual nested `string_content`) -- to their bare stem, the same restraint `_gdscript_dependency_handler` already takes for its own path-based imports (a `#include` path is relative to the compiler's own `-I` search paths, not guaranteed to match the file's own collected relative-key path). Deliberately scoped to implementation files only, not `.h`/`.hpp` headers: a header with only prototype declarations (`void foo();`, or a pure virtual `virtual void foo() = 0;`, no body at all) parses as a plain `declaration`/`field_declaration`, never a `function_definition` -- so header-only files would extract zero signatures under this config regardless. Whether/how to also cover declaration-only headers (and the real C-vs-C++ ambiguity a bare `.h` extension carries) is left as a follow-up decision.

Adding C++ also surfaced a real, pre-existing bug in `file/relationship.py`'s `build_stem_map()`/`resolve_dependency()` -- see that module's own bullet in `src/file/CLAUDE.md` for the fix (a header/implementation pair sharing a stem, like `Config.h`/`Config.cpp`, is an extremely common C/C++ convention that no earlier supported language ever exercised, since none of them produce two collected files sharing an exact stem).

**`.rs`** — a dedicated `tree-sitter-rust` PyPI package. Unlike C++, this grammar exposes a function's `"name"`/`"parameters"`/`"return_type"`/`"body"` as direct fields of `function_item` itself -- no declarator indirection, so `extractor.py` needed zero changes at all to support it (not even a second return-type field name: `"return_type"` already matches Python/TS/GDScript's own convention). One `function_item` node type covers every shape uniformly -- a free function, an inline `impl` method, and a trait-`impl` method all parse identically, the enclosing `impl_item`/`trait_item` simply never read (unlike Java/Go's separate method node type, though here it's not even needed for that reason -- there's just one function node type, period). `function_types` also includes `function_signature_item` -- a trait's own method declaration with no body at all (`fn greet(&self) -> String;`), which still has `"name"`/`"parameters"`/`"return_type"` for a real signature; having no `"body"` field is harmless for compression, since `_collect_bodies`'s `if body:` guard just finds nothing to strip and leaves the one-line declaration untouched.

`_rust_dependency_handler` recognizes two distinct shapes. `mod foo;` (`mod_item`, the field-declaration form with no `"body"` field -- a body-having `mod foo { ... }` is an inline submodule, not a file reference, and is deliberately not matched, gated on an absent `"body"` field rather than matched unconditionally) is the most precise dependency Rust has: it declares a submodule backed by its own file (`foo.rs` or `foo/mod.rs`), read straight off the `"name"` field with no normalization needed, unlike every path-based handler above. A code-review pass caught this gate missing from the first version -- every `mod_item` matched unconditionally, so a real, common pattern (`#[cfg(test)] mod tests { use crate::...; }`) both emitted a bogus `"tests"` dependency for the inline module's own name *and* (since a match always stops recursion) hid every real `use`/`mod` declaration nested inside it; fixed by returning `False` (keep recursing) when a `"body"` field is present. `use path::to::Item;` (`use_declaration`) is a symbol import, not necessarily a file reference -- its argument node varies more than any other supported language's import syntax (a plain path, an aliased path via `use_as_clause`, a glob via `use_wildcard`, and -- unique to Rust here -- one statement naming several sibling paths under a shared prefix via `use_list`/`scoped_use_list`, which can itself nest arbitrarily deep, e.g. `use std::{fmt, collections::HashMap}`). `_append_rust_use_paths()` handles this with text-based parsing (depth-aware comma-splitting a `{...}` group and recursing per item, then -- only once a text is confirmed *not* a group -- stripping an `as` alias and a trailing `::*`) rather than a node-type traversal, the same restraint `_java_dependency_handler` already takes for its own raw-text import stripping. The group-check has to run *before* alias-stripping, not after: a code-review pass caught the first version splitting off `" as "` from the whole argument text up front, which truncated a group containing an aliased sibling (`use foo::{bar as baz, qux}`) mid-string into `"foo.{bar"` -- silently dropping `qux` entirely and leaving a dangling `"{"` that could never resolve. Every result is normalized to a dotted path (`"::"` → `"."`) so `resolve_dependency()`'s existing split-on-`"."`-take-last-segment fallback applies unchanged, no Rust-specific matching needed there. Known, accepted limitation shared with Go's own handler: a `use` path's last segment often names a *type* (PascalCase, e.g. `crate::models::User`), not the *file* that defines it (typically snake_case, `user.rs`) -- `resolve_dependency()`'s stem-matching will frequently miss this the same way Go's package-vs-file granularity mismatch does; `mod_item` resolution is what actually carries most of Rust's real internal file-dependency precision, `use_declaration` capture is a bonus on top, not the primary signal. No `api_handler` -- no single dominant route-declaration convention the way Flask/Express are (actix-web's attribute macros and axum's builder-style routing look nothing alike), same "no established convention" default as Java/Lua/GDScript. Live-verified end to end through a full mock-provider `pack()` run against `testfiles/rust-cli-project` (a `main.rs`/`counter.rs` split via `mod`) -- `mod counter;` correctly resolved as an internal dependency, `Cargo.toml` correctly detected by `tech_stack.py` (already supported it before this language existed, from the original manifest-list pass), 79.9% token compression on the packed payload. Both code-review findings above were reproduced live first (confirmed failing against the pre-fix code via `git stash`, not just written and assumed correct) before being fixed.

**`.cs`** — a dedicated `tree-sitter-c-sharp` PyPI package. `method_declaration`/`constructor_declaration`/`destructor_declaration` all expose `"name"`/`"parameters"`/`"body"` as direct fields, same shape as Java/Go -- no declarator indirection to unwrap. `method_declaration`'s return-type field is named `"returns"` -- yet a fourth field-naming convention this grammar happens to use, alongside Python/TS/GDScript's `"return_type"`, Go's `"result"`, and C++'s `"type"` -- `_traverse_signatures()` now checks all four generically. An interface's own method declaration (`string Greet();`, no body) is the *same* `method_declaration` node type as a class method, just missing a `"body"` field -- handled for free the same way Rust's `function_signature_item` is: still produces a real signature, and the missing body is harmless for compression (`_collect_bodies`'s `if body:` guard finds nothing to strip).

What's genuinely new here: `destructor_declaration`'s own `"name"` field is just the bare identifier (`"Widget"`, not `"~Widget"`) -- the `~` that actually distinguishes it from a same-named constructor tokenizes as a separate, unnamed sibling child, not part of the field, so without correction a class defining both would produce two identical `"Widget()"` signatures. Fixed with a new `LanguageConfig` extensibility field, `name_prefixes` (`dict[node_type, prefix]`) -- unlike `implicit_names` (a substitute for a *missing* name), this prepends a prefix onto a name that *was* found; C#'s config sets `name_prefixes={"destructor_declaration": "~"}`, and `_traverse_signatures()` applies it right after `_resolve_signature_name()` succeeds.

`_csharp_dependency_handler` -- every `using` variant (`using X;` / `using X.Y.Z;` / `using static X.Y;` / `global using X;` / `using Alias = X.Y;`) parses as one `using_directive` node type, but none of them exposes the actually-imported path under a consistently-named field: a plain/static/global using has no field name at all for its path child (a bare positional `"identifier"`/`"qualified_name"`), and the aliased form's own `"name"` field names the *alias*, not the real path (the real path is the identifier/qualified_name *after* `"="`, itself unfielded too). Read positionally instead, the same restraint `_gdscript_dependency_handler`/`_go_dependency_handler` already take for their own callee/path reads: the *last* identifier/qualified_name-typed child is the real path -- the only such child at all for a plain/static/global using (search runs over the whole node), and the one after `"="` for an aliased using, so the search is scoped to children after `"="` there rather than the whole node. That scoping isn't cosmetic: a code-review pass caught the first version searching the whole node unconditionally, which meant a type alias whose right-hand side isn't itself an identifier/qualified_name (`using MyInt = int;`, `using IntArray = int[];`, `using Nullable = System.Int32?;` -- predefined/array/nullable types are all real, common alias targets) found no path-shaped node after `"="` and silently fell back to matching the *alias name itself* (the identifier before `"="`), wrongly emitting it as a bogus dependency. Scoping the search to after `"="` makes that case correctly find nothing instead, reproduced live and fixed before merge. Already dot-separated (a `qualified_name`'s own text already uses `"."` as C#'s real namespace separator, unlike Rust's `"::"`), so no normalization is needed -- `resolve_dependency()`'s existing dotted-path matching applies directly. No `api_handler` -- ASP.NET's own routing conventions (attribute-based `[HttpGet("/path")]` on a controller method vs. Minimal API's `app.MapGet("/path", ...)`) don't share one dominant shape the way Flask/Express do, same "no established convention" default as Java/Lua/GDScript/Rust. Known, accepted gap: `tech_stack.py`'s manifest list (see that module's own bullet) only matches fixed filenames (`package.json`, `Cargo.toml`, etc.) -- a C# project's manifest is `<ProjectName>.csproj`, a variable filename that architecture doesn't support without a real glob-matching extension; not fixed here, so a C# project's `tech_stack` entry is silently just absent rather than detected. Live-verified end to end through a full mock-provider `pack()` run against `testfiles/csharp-cli-project` (a `Program.cs`/`Counter.cs` split across `WordCount`/`WordCount.Core` namespaces) -- signatures/dependencies/compression all correct, 78.2% token compression; `using WordCount.Core;` resolved as external (the known namespace-vs-filename gap above, not a bug -- `Counter.cs` doesn't share a stem with the namespace's last segment `Core`), while the README's own filename mentions still resolved both files as internal via the free text-reference pass.
- **`parser.py`** — `get_parser_by_ext`/`get_parser` just wrap `languages.py` to hand back a ready `Parser`.
- **`extractor.py`** — walks the parsed AST for three things, each its own traversal: `extract_signatures` (per `function_types`, builds `name(params) -> return_type` strings), `extract_dependencies` (delegates node recognition to the language's `dependency_handler`), `extract_api` (delegates to the language's own `api_handler`, same shape as `extract_dependencies`/`dependency_handler` — `[]` outright for a language with no `api_handler` configured at all, e.g. Java/Lua/GDScript as of this writing; see `languages.py` below for what `.py`'s Flask-style and `.ts`/`.js`'s Express-style handlers each match). `_traverse_signatures` threads the current node's parent through its own recursion and hands it to `_resolve_signature_name(node, parent)`, which checks the matched node's own `"name"` field first, then falls back to the parent's `"name"` field, then its `"key"` field — needed because TS/JS's `arrow_function`/`function_expression` nodes have no name of their own when anonymous; the readable name lives on whatever wraps them (`variable_declarator`'s `"name"` for `const add = (a,b) => ...`, `public_field_definition`'s `"name"` for a class-field arrow, `pair`'s `"key"` — not `"name"` — for an object-literal method). Before this, TS/JS's `function_types` was just `["function_declaration", "method_definition"]`, so arrow functions and function expressions were completely invisible to both signature extraction and body compression (a real, confirmed-by-direct-testing gap — most real-world TS/JS uses arrow functions far more than `function` declarations). One documented residual gap even after the fix: a bare single-identifier-parameter arrow with no parens (`x => x * 2`) has no `"parameters"` field at all (the identifier is an unnamed positional child, not wrapped in `formal_parameters`), so it still produces no signature — left alone rather than teaching the generic traversal a per-node-type positional fallback. Doesn't affect body compression either way, which only needs a `"body"` field, not a name or params. `_resolve_signature_name` takes one more fallback beyond the two above: `implicit_names` (from the language's own `LanguageConfig`, keyed by `node.type`) for a node whose grammar gives it neither a `"name"` field nor a named wrapper -- GDScript's `constructor_definition` (see `languages.py` below). Right after a name is resolved, `_traverse_signatures` also applies `name_prefixes` (same `LanguageConfig`, same `node.type` key) if the matched node's type has one -- unlike `implicit_names`, this only ever prepends onto a name that was *actually found*, never substitutes for a missing one; C#'s `destructor_declaration` is the one case that needs it (see `languages.py` below). The return-type field-name check (`"return_type"` then `"result"` then `"returns"`, plus C++'s conditionally-gated `"type"`) has grown to four conventions as more languages were added -- still one small `or`-chain in `_traverse_signatures`, not a per-language branch.
- **`compressor.py`** — `compress_code(code, ext)` strips function bodies, replacing each with a single `MARKER` line (`"    ⋮----"`), keeping signatures/imports/decorators verbatim. Two brace-language subtleties: if the body's opening `{` sits on the same line as the signature (JS/TS/Java), the marker starts on the *next* line so the signature survives; the body's closing `}` (if present as the body's last child) is excluded from the stripped range so it isn't swallowed either. Returns `None` for an unsupported extension so callers (`compress_file()` here, and Markdown code-block compression in `extract/text/markdown.py`) can fall back to something else — both share this function for "how to compress this language," so a fix here fixes Markdown-embedded code too. See `src/extract/text/CLAUDE.md`'s circular-import note for why `extract/text/markdown.py` imports this function inside a function body rather than at module top. `_collect_bodies` needs only a matched node's `"body"` field, no name — so adding `arrow_function`/`function_expression` to TS/JS's `function_types` (see `extractor.py` above) made them compress correctly with zero changes here. A concise (brace-less, expression-bodied) arrow — `const double = x => x * 2` — needed no special-casing either: its body sits on the same source line as the arrow itself, so the existing "same line as the signature" check already produces `start > end` and the body is left untouched, exactly as intended (there's no multi-line implementation detail to elide from a one-liner).
